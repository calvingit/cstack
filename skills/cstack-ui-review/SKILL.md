# 审查界面

## 目标

依据用户要求、设计参考和项目约定，判断实际界面的可见问题及相关交互风险。代码结构或最终截图不能代替真实渲染与操作。

## 方法

1. 确定审查的界面、候选版本、目标平台、视口或设备、关键状态和参考依据。用户未给设计稿时采用项目已有约定；不存在明确标准的风格偏好标为建议，不写成确定缺陷。
2. 在有权限且可隔离的环境中启动或打开实际界面，确认受测实例和候选的关系。使用当前 Runtime 可用的浏览器、模拟器或设备；缺少能力时说明未观察到的范围，不从源码推断界面已经正常。
3. 按目标场景观察布局、信息层级、文本截断、视觉一致性、响应式变化及必要的加载、空、错误等状态。需要比较设计时使用同一视口与状态，保留允许保存的截图及其对象、时间和环境。
4. 在获准范围内实际操作关键路径，检查可达性、焦点、可见反馈和必要的键盘或触控交互；注意操作会产生的副作用。单张截图只能证明当时的可见状态，不证明交互、动态行为或跨设备一致性。
5. 对每项问题写位置、复现条件、观察依据、影响和适用标准；区分功能缺陷、视觉不一致、可用性疑点及主观建议。运行条件或期望不可得时标为未知，不强行通过或制造问题。

## 停止与交接

报告候选、平台/视口、观察和实际交互、发现、证据位置及未覆盖范围。只要求审查时不修改界面；若用户同时要求修复，可在授权内修改并重新观察受影响的状态。本方法不替代逐项业务验收。
