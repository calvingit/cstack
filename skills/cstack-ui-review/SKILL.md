# UI Review - 审查界面

## 目标

根据用户要求、设计参考和项目约定，判断实际界面上有哪些看得见的问题，以及相关的交互风险。代码结构和最终截图都代替不了真实渲染和真实操作。

## 方法

1. 先确定审查哪些界面、哪一个候选版本、目标平台、视口或设备、关键状态和参考依据。用户没给设计稿，就按项目已有的约定来。没有明确标准可依的风格偏好，标为建议，不写成确定缺陷。
2. 在有权限、能隔离的环境里启动或打开实际界面，确认这个受测实例对应的是哪个候选版本。用当前 Runtime 能用的浏览器、模拟器或设备。缺这类能力时，说明哪些范围没有观察到，不要从源码推断界面已经正常。
3. 按目标场景观察布局、信息层级、文本截断、视觉一致性、响应式变化，以及必要的加载、空、错误等状态。要跟设计稿比对时，视口和状态都取同一份。截图在允许保存的前提下留下，并记下它对应哪个对象、什么时间和环境。
4. 在获准的范围内把关键路径实际操作一遍，检查可达性、焦点、可见反馈，以及必要的键盘或触控交互。操作会带来什么副作用，也要留意。单张截图只能证明那一刻看得见什么，证明不了交互和动态行为，也证明不了跨设备是否一致。
5. 对每项问题，写清位置、复现条件、观察依据、影响和适用标准，再分清它属于哪一类：功能缺陷、视觉不一致、可用性疑点，还是主观建议。运行条件或预期结果拿不到时，标为未知。不要强行判为通过，也不要制造问题。

## 停止与交接

报告要写清候选版本和平台/视口，说明观察到什么、实际操作过哪些路径、发现了什么、证据在哪，还有哪些范围没有覆盖到。用户只要求审查时，不修改界面。用户同时要求修复，可以在授权内修改，改完再重新观察受影响的状态。本方法不替代逐项业务验收。
