# 审查变更

## 目标

确定本次变更可能引入什么可达到、有实际影响的问题，为修复提供可核查依据。仅审查请求默认只读。

## 方法

1. 根据用户指定的提交、分支、工作树或路径确定候选与基线；涉及工作树时包含相关暂存、未暂存和未跟踪文件，区分既有改动。无法读取范围或 diff 为空时说明限制，不当作审查通过。
2. 读取要求、项目规则、完整差异以及必要的调用方、数据流、状态转换、错误处理、配置和测试。先查能够推翻疑点的保护条件；对不明确的业务期望不要编造需求。
3. 根据实际影响审查正确性、回归、权限、数据一致性、并发、兼容性和恢复。识别变更依赖的关键安全事实，必要时通过代码路径或安全的定向检查验证；不把所有可能性都升级为缺陷。
4. 每项发现给出具体位置、可触发条件、发生过程、影响、事实依据和最小修正方向；区分已复现、代码推断与未知。区分本次引入的问题和无关的历史问题，合并同一根因的重复症状。
5. 检查相关测试是否会暴露重要回归，但不要求先做完整测试审计，也不重复全套验收。已有证据可复用时核对其候选和范围；需要实测时只运行能回答疑点的检查。
6. 修复后复查受影响变化和未解决问题，按实际风险决定是否扩大范围；审查有合理预算。预算耗尽或关键问题未解时明确保留，不能自动变成通过。

## 结果与停止

按影响列出有证据的发现、范围、已检查内容和限制；没有发现时说明未覆盖部分，不声称证明代码无缺陷。不要自行修改产品、改写验收或执行交付；用户在同一任务中明确要求修复时，可在授权范围继续，修复后重新核对相关发现。
