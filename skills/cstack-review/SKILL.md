# Review - 审查变更

## 目标

找出这次改动可能引入的问题，判断其中哪些真能发生、也确实有影响，让修复有据可查。请求只做审查时，默认只读。

## 方法

1. 先从用户指定的提交、分支、工作树或路径确定候选和基线。涉及工作树时，把相关的暂存、未暂存和未跟踪文件一并算进来，并区分出哪些是既有改动。读不到范围，或 diff 是空的，就说明限制。这种情况不算审查通过。
2. 先读要求、项目规则和完整 diff，再看相关的调用方、数据流、状态转换、错误处理、配置和测试。能推翻疑点的保护条件要先查。业务期望不明确就问清楚，不要编造需求。
3. 按实际影响审查正确性、回归、权限、数据一致性、并发、兼容性和恢复。找出变更所依赖的关键安全事实。必要时沿着代码路径核对，或做安全的定向检查来验证这些事实。不要把所有可能性都升级成缺陷。
4. 每项发现都要给出具体位置、触发条件、发生过程、影响、事实证据和最小的修正方向，并分清哪些已经复现、哪些只是从代码推断、哪些还不知道。本次引入的问题要和无关的历史问题分开。同一根因的重复症状要合并。
5. 看相关测试能不能暴露重要回归。不要求先做完整的测试审计，也不重复全套验收。已有的证据能复用时，核对该证据对应的候选和范围。需要实测时，只跑能回答疑点的检查。
6. 修复后，复查受影响的改动和还没解决的问题，再按实际风险决定要不要扩大审查范围。审查有合理的预算。预算用完，或关键问题还没解决，就明确保留为未解决，不能自动变成通过。

## 结果与停止

按影响列出有证据的发现、审查范围、已检查的内容和限制。没有发现时，说明哪些部分没有覆盖到，不要声称已经证明代码没有缺陷。不要自行修改产品、改写验收或执行交付。用户在同一次任务里明确要求修复时，可以在授权范围内继续，修完再重新核对相关发现。
