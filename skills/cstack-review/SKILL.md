# CStack REVIEW

## 执行边界

- 将本文件作为实验版方法使用；只处理当前请求需要的阶段，不启动固定六步流水线。
- 先读项目指令、相关源码和已有契约。区分已观察事实、推断与未知；沿用现有事实来源，简单任务无需新建文档、账本或状态机。
- 按需求不确定性、影响范围、验证难度和可恢复性选择最小充分工作。默认单执行者，不把多模型一致当作证明。
- 沿用会话中仍有效的授权，不重复询问已授权事项；Skill 名称不扩大权限。保护用户未提交改动及他人工作。
- 缺少工具或权限时说明受阻的具体判断和最小下一步，不虚构执行、证据或成功结果。

## 输入与方法

1. 确定 diff、基线、实际候选（含未提交内容）、目标、项目规则及已有验证证据。读取受影响调用方、数据流和错误路径，不能只看摘要。
2. 按影响和不确定性选择深度。优先核对业务不变量、权限、数据一致性、并发、兼容性与恢复；同时检查删除断言、跳过检查、放宽阈值和占位实现是否有合理依据。
3. 对每项发现给出位置、可达触发条件、影响、支撑证据及最小修正。标明已验证事实与待验证推断；不能证明的故障作为具体证据缺口，不能编造为确定缺陷。既有问题与新增回归分开。
4. 复用适用的验收结果，仅为核实发现做针对性检查，不重跑整套 VERIFY。独立审查是否需要另一执行者依项目规则与风险决定；无法满足时披露，不自称独立。
5. 默认最多三轮：首轮审完整变更，后续只看修正、新变化和开放问题。用稳定问题编号记录解决或拒绝理由；修改候选后重新判断受影响结论。预算耗尽且问题未解，报告未解决，不能转为通过。

## 输出与停止

按影响列出发现、依据、候选适用范围和未检查区域；无发现也说明限制，不声称证明无缺陷。结束于审查结论，不自行修改产品、改写 AC 或执行合并。若原请求还包括修复，明确转入实现职责，修复后再核验受影响证据。
