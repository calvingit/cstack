# UI Review - 审查界面

## 硬约束

- 代码结构和最终截图都代替不了真实渲染和真实操作。
- 没有明确标准可依的风格偏好，标为建议，不写成确定缺陷。
- 受测实例必须对应明确的候选版本；观察不到的界面说明没有覆盖。
- 用户只要求审查时，不修改界面。

## 产物

- **读**：界面范围、候选版本、目标平台 / 视口 / 设备、关键状态、设计参考、项目约定。
- **写**：界面审查报告（候选与平台、观察到的状态、实际操作路径、发现、证据、未覆盖范围）。不写正式槽位。
- 需要与其他 Skill 统一槽位名和字段时，调用 `core` Skill；未安装时以本节作为最小可用版本。

## 目标

根据用户要求、设计参考和项目约定，判断实际界面上有哪些看得见的问题，以及相关的交互风险。

## 方法

1. 先确定审查哪些界面、哪个候选版本、目标平台、视口或设备、关键状态和参考依据。没有设计稿就按项目已有约定；没有明确标准的偏好只作建议。
2. 在有权限、能隔离的环境里启动或打开实际界面，确认实例对应的候选版本。用当前 Runtime 能用的浏览器、模拟器或设备；缺能力时说明哪些范围没观察到，不从源码推断界面正常。
3. 按目标场景观察布局、信息层级、文本截断、视觉一致性、响应式变化，以及加载、空、错误等必要状态。与设计稿比对时，使用相同的视口和状态；截图记下对象、时间和环境。
4. 在获准范围内实际操作关键路径，检查无障碍、焦点、可见反馈，以及必要的键盘或触控交互，留意副作用。单张截图只证明那一刻可见的状态，证明不了交互、动态行为和跨设备一致性。
5. 每项问题写位置、复现条件、观察依据、影响和适用标准，并分类：功能缺陷、视觉不一致、可用性疑点或主观建议。条件或预期拿不到时标未知，不强行判通过。

## 停止与交接

报告候选版本和平台 / 视口，说明观察到什么、实际操作过哪些路径、发现了什么、证据在哪，还有哪些范围没覆盖。只要求审查时不改界面；同时要求修复时按授权修改，改完重新观察受影响状态。本方法不替代逐项业务验收。
