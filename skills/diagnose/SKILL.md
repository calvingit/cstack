# Diagnose - 诊断故障

## 硬约束

- 先有能变红的反馈回路，再谈假设；没有回路，不猜根因。
- 复现必须对应用户描述的那个症状，不是旁边另一个错误。
- 诊断请求只到根因；修复要单独授权。
- 不把未验证的假设写成根因；真实环境做不了就说明限制。

## 产物

- **读**：症状与期望来源（SPEC `AC#` 或确认会话）、相关代码 / 日志 / 环境、PROFILE 的验证入口。
- **写**：诊断记录——症状、反馈回路命令、最小复现、已排除假设、根因证据、修复与复验结果。它是工作记录，**不是正式槽位**，也不能替代 `EVIDENCE`。
- 需要与其他 Skill 统一槽位名和字段时，调用 `core` Skill；未安装时以本节作为最小可用版本。

## 目标

本 Skill 由 **Explorer** 做事实调查、**Implementer** 在授权后修复（诊断方法，不单列角色）；轻量诊断不必另派独立实例（见 `core/ROLES.md`）。围绕用户描述的症状取得可观察的反馈，区分事实、假设和已证实的原因；修复拿到授权后才改产品。

## Phase 1：建立反馈回路（核心）

这一步是诊断的全部。只有一条能变红的反馈回路，后面的二分、假设和插桩才有意义。

- 尽量先自己复现。顺序：真实调用路径上的失败测试 → curl / CLI → 浏览器自动化 → 重放抓包 / 日志 → 一次性脚本。
- 回路必须**能变红**：驱动真实 bug 代码路径，断言用户的确切症状，修复后能变绿；不是“不报错”。
- 尽量可重复（同一输入得到同一结果）、够快（秒级）、无需人工值守；间歇问题记录观察到的复现率和条件，不追求人为制造的确定性。
- 做不出回路时，说明试过什么、卡在哪；请用户提供能复现的环境、脱敏产物或临时插桩授权。**不要直接进入假设。**
- 完成判据：能说出**一条命令**，已经至少跑过一次并变红。

## Phase 2：复现与最小化

- 跑回路，确认红的是用户描述的症状，不是附近的另一个失败。
- 逐个删输入、配置、步骤，直到每个剩余元素都是必要的。删掉任何一个就变绿，才算最小。
- 记录确切症状：错误信息、错误输出、慢的时序。

## Phase 3：假设

- 先列 3–5 条**可证伪**假设，每条带预测：“若 X 是原因，改 Y 会让 bug 消失，改 Z 会加重。”
- 把排好序的清单给用户看一眼（可以稍后再看，不必等回复），他们常能凭领域知识立刻调整顺序；不要因此阻塞。
- 最常见的失败是只盯一个假设。

## Phase 4：探测

- 每个探测对应一条预测，一次只改一个变量。
- 调试器 / REPL 优先；定向日志带唯一前缀 `[DEBUG-xxxx]`；禁止“全量打日志再 grep”。
- 性能问题先建基线测量，再二分。
- 只用能区分不同解释的运行证据确认根因，不把最先想到的机制直接写成根因。

## Phase 5：修复与回归

- 按根因做最小修改；同一模式在别处也存在时指出，但不顺手扩大。
- 有正确 seam，就把最小复现转成失败测试，先红后绿；没有正确 seam 本身就是发现（架构本身导致无法用测试锁定缺陷），不要为了测试而暴露内部实现，必要时交 design / codebase-design。
- 修复后复跑原始（未最小化的）场景，不能只跑新测试。

## Phase 6：清理与报告

- 删除所有 `[DEBUG-...]` 插桩和一次性脚本；清理只动自己创建的资源，保留必要证据。
- 报告：坏了什么、根因、修复、如何验证；贴脱敏后的失败→通过输出；列出已排除的假设；最后写未验证项与剩余风险。
- 跨会话无法完成时，按项目约定留最小 checkpoint：症状、期望来源、复现命令、已排除假设、下一步。

## 停止与交接

只要求调查时，停在根因，不改产品。修复只在授权范围内进行；缺陷、契约冲突和能力缺口交回调用方。诊断记录不替代独立验收（verify）和代码审查（review）。
