# Ship - 交付变更

## 强制约束

- 准备、推送、创建 PR、入队、合并和部署是不同动作；阶段名或 Skill 名不是授权。
- 就绪、授权和实际执行结果分开表达。
- `FAIL` / `NOT VERIFIED` 不能改写成 `PASS`；不绕过硬门禁。
- 没有真实动作或证据就明确说明。

## 产物

- **读**：EVIDENCE、项目门禁与分支保护、用户授权、当前候选与基线。
- **写**：就绪与授权判断、实际执行结果（短记录）；不伪造平台状态。
- 需要与其他 Skill 统一产物命名和字段时，调用 `core` Skill；未安装时以本节作为最小可用版本。

## 目标

按当前候选、有效证据、项目门禁和用户授权，完成所请求的交付。准备、合并、发布是能力分组，不因一句话自动升权。

## 判断顺序

1. 确定用户要求的结果、已授权动作与对象、目标分支 / 环境、候选和基线；读平台或仓库实际状态、未提交改动、项目规则、已有验收与审查。
2. 判断验收、审查、必需检查和审批是否覆盖当前候选与基线；核对实际受测对象和产物来源。绿色状态、被跳过的检查或模型意见，都不能自动当成业务验收。相关变化后，只有原依据仍然成立才能复用旧结果；不确定就补验或记录为缺口。
3. **Merge Readiness** 与 **Release Readiness** 分开：前者看阻塞缺陷、有效证据、必需 CI、审查状态、分支状态与可回退性；后者看部署配置、灰度、迁移、观测、发布后验证与恢复。合并会自动部署时两者一起评估，但结论仍分开。合并授权不自动覆盖生产环境操作及其副作用；访问不到就标未知。
4. 状态词汇统一：`Merge Readiness` / `Release Readiness`；`GO` / `HOLD` / `NO-GO`；实际结果用 已准备 / 已推送 / PR 已创建 / 已入队 / 已合并 / 已部署 分别说明。
5. 针对指定候选、目标和观察时点，把技术就绪、授权范围、阻塞与剩余风险分开报告。接受风险要有依据和明确的接受者。
6. 执行条件：用户要求并授权、必要门禁满足、相关副作用在授权范围内，三者同时成立才用现有工具执行。只问真正缺失的决定或权限，已授权的不要重复问。创建 PR 或推送不等于可以合并或部署；项目要求人工批准时遵守。
7. 动作前重读能拿到的候选、目标和关键门禁；平台支持把前置条件绑定到预期候选或版本时，优先使用这种能力；保证不了检查与执行之间条件不变，就说明这个限制。状态变化后重判受影响的证据。
8. 实际结果到平台或工具核对：入队不等于已合并，合并也不等于已部署；失败、未知或进行中都不能说成完成。

## 报告与停止

报告候选与目标、技术就绪、授权与副作用、实际执行结果、阻塞、证据和必要恢复安排。只要求判断时停在判断；要求交付且已授权时，直到得到所请求的结果，或遇到具体阻塞为止。没有真实动作或证据就明确说明。
