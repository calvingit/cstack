# CStack 产物槽位

本文件只定义**逻辑槽位**：每个槽位回答什么问题、最小字段是什么、谁写、谁读、何时需要。它不规定文件名、目录或模板——槽位可以是一段会话记录、一个 Markdown 文件、一个 issue，或 PR 描述里的一节。

## 6 个槽位

| 层 | 槽位 | 回答的问题 | 唯一写入者 | 主要消费者 |
| --- | --- | --- | --- | --- |
| 项目基座 | `PROFILE` | 这个项目长期怎么运作？ | setup | 所有 Skill |
| 需求契约 | `DECISIONS` | 哪些需求选择已经由用户确认？ | clarify | specify |
| 需求契约 | `SPEC` | 要做什么，怎么算完成？ | specify | design / slice / implement / verify / review |
| 交付计划 | `TECH` | 哪些共享或难逆的技术选择已定？ | design | slice / implement / verify / review |
| 交付计划 | `SLICES` | 怎么分步交付，谁阻塞谁？ | slice | implement / verify |
| 结果 | `EVIDENCE` | 实际做到什么程度？ | verify | review / ship |

## 最小字段

### PROFILE

稳定的项目事实，不存当前任务状态。

- 术语表 / 领域模型位置
- 验证入口（怎么启动、怎么操作、怎么观察）
- 需求权威来源（仓库内、外部系统或当前任务快照）
- 既有架构决策（ADR）位置
- 任务文档存放约定

### DECISIONS

只记用户确认过的需求选择。

- `C#`：稳定编号
- 问题：当时在决定什么
- 选择：用户确认的答案
- 理由：为什么这样选
- 可观察结果：怎么从外部看出这个选择生效
- 确认来源：谁在什么时候确认
- 未决项：尚未定的问题（保留，不用假设填平）

### SPEC

需求快照，只写需求与可观察验收，不写实现。

- Goal / Scope / Out of scope
- `R#`：需求；每条可追溯到确认来源（`C#` 或权威需求）
- `AC#`：验收条件；每条写明来源 `R#`、可观察面、可判定结果、必要的失败情形
- Acceptance Seam：在哪个公开面观察这些 AC（用户交互、外部契约响应、导出文件）
- 约束：业务、外部契约、兼容性等已确认约束
- 未决项：仍阻塞验收的问题

### TECH

仅在多个实现需要共享、或决策难以撤回时启用。

- `D#`：技术决定
- 依据：至少一条 `R#` / `AC#`，或一个可观察的代码事实（路径 / 符号）
- 备选：考虑过的真实方案
- 权衡：成本、风险、失败方式
- 恢复 / 迁移：不可逆部分怎么撤回
- Verification Seam：技术正确性在哪一层检查（与 SPEC 的 Acceptance Seam 分开）

### SLICES

仅在存在多个可分别交付、且有真实依赖的单元时启用。

- `S#`：切片编号
- 交付什么：端到端可演示或可验收的行为
- covers：覆盖的 `R#` / `AC#` / `D#`
- blocked-by：真正阻止本切片开始的其他 `S#`；没有就写“无”
- 本地 AC：`S#-AC#`，与 SPEC 的 `AC#` 分属不同命名空间
- 约束：继承自 SPEC 或 TECH 的相关约束

### EVIDENCE

有完成声明时才需要。

- 逐 `AC#` 的结论：`PASS` / `FAIL` / `NOT VERIFIED`
- 候选：HEAD 或提交范围，加上工作树是否有未提交 / 未跟踪改动
- 方法：实际运行的命令、测试、接口调用或界面操作
- 环境：会影响结论的版本、配置、依赖、数据或外部服务
- 执行者：实现者自检、独立验证者、CI 或外部系统
- 覆盖限制：没观察到的路径、被 mock 的依赖、未覆盖的环境
- 证据位置：日志、截图、报告或产物路径

## ID 约定

- `R#` / `AC#` / `C#`（需求确认）/ `D#`（技术决定）/ `S#`（切片）各自独立编号。
- `S#-AC#` 是切片本地验收条件，不复用 SPEC 的 `AC#`。
- 下游一律引用 ID，不复制内容；需要摘录时标明来源与版本。
- 判据是“这项事实是否会被下游引用”，不是“够不够正式”。

## 交接与变化

| 变化 | 只改 | 之后重判 |
| --- | --- | --- |
| 需求选择改变 | `DECISIONS` → `SPEC` | 受影响的 `TECH` / `SLICES` / `EVIDENCE` |
| 技术决定改变 | `TECH` | 受影响的 `SLICES` / `EVIDENCE` |
| 拆分或依赖改变 | `SLICES` | 受影响的执行与 `EVIDENCE` |
| 候选、测试、环境、基线改变 | — | 受影响的 `EVIDENCE`，必要时回 `SPEC` |

- 未受影响的有效结论不因流程重启而作废。
- `NOT VERIFIED` 记录的是证据不足，不是允许放弃验收；只有获授权的契约变更才能改变完成条件。

## 降级

槽位可以缺席，但缺席不授权编造：

- 没有 `DECISIONS` / `SPEC`，但请求已足够清楚：按会话契约执行，`EVIDENCE` 标注“来源：会话确认”。
- 没有 `TECH`：单一实现且无共享契约时直接做；跨模块共享设计时不能跳过。
- 没有 `SLICES`：单一交付范围直接实现；多单元互相阻塞时不能假装没有依赖。
- 没有 `EVIDENCE`：只能报告“未验证”，不能声明完成。
