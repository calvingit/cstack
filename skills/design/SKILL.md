# Design - 设计技术方案

## 强制约束

- 不改变 SPEC 的需求含义；需求没定先回 clarify / specify。
- 只定必须共享或难以撤回的技术决策；私有方法、文件布局等局部细节不写。
- 每个决定都要有可追溯的依据（`R#` / `AC#` 或代码事实）；没有依据的决定不成立。
- 不拆分切片、不实现、不修改上游产物。

## 产物

- **读**：SPEC（`R#` / `AC#`）、代码事实、PROFILE（若存在）。
- **写**：TECH，含 `D#`、依据、备选、权衡、恢复 / 迁移、Verification Seam。判定不需要时报告 `tech_not_required` 并给出依据。
- 需要与其他 Skill 统一产物命名和字段时，调用 `core` Skill；未安装时以本节作为最小可用版本。

## 目标

把必须共享或不易撤回的技术决策定下来，让实现和验证有依据。局部改动不值得另造一层设计。

## 何时必须做

以下任一成立就需要 TECH：

- 多个模块、调用方或实现要共享类型、枚举、schema、事件、错误模型或回调约定。
- 要新增或修改公共 / 跨模块接口、归属、依赖方向或稳定 Seam。
- 多个实现要遵循同一套状态机、生命周期、并发模型和调用顺序。
- 需要 expand–contract、数据迁移、兼容窗口或明确集成顺序。
- 用户或项目规则明确要求共享技术约束。

**切片数量不是判据**：单个执行单元也可能需要 TECH；多个独立切片也可能不需要。都不成立时报告 `tech_not_required` 并说明理由。

## 设计依据的先后

1. 用户请求与确认的 SPEC。
2. AGENTS / 架构文档 / ADR / 项目标准。
3. 同域或同模块的稳定实现。
4. 当前生产主路径、真实调用方与组装入口。
5. 更新的相似实现。
6. 通用工程原则。

现存代码是强证据，不是绝对权威。多个模式并存时不按数量投票，选最贴近当前归属、运行路径和改动范围的参考，并记录理由。

## 调查：先广后深

- **广度**：定位相关符号、类型、调用方、测试、配置、组装入口和相似行为。
- **深度**：挑 1–3 个最相关的参考，追必要的调用链、数据 / 控制流和验证方式。
- 证据够锁定“多个实现必须共享的决策”就停，不追求全仓理解。调查中发现、但与本次无关的问题，记为“看到但不在本次范围”。

## 公共接口的草图

新增或实质修改共享接口、回调约定、跨模块入口时，先用一两个真实生产调用方的使用草图说明怎么用：输入、输出、失败语义、生命周期。草图不是实现方案，不规定私有辅助函数和局部控制流。没有真实调用方的接口不预先建。

设计分歧明显或需要 design-it-twice 时，可派 `core` 的 **Architect** 角色产出 2–3 个结构不同的候选；普通设计由 Designer 自行完成。

## Design Review Gate

只有在选择会影响长期方向时，才停下来问用户：

- 新的公共抽象或领域模型
- API / 事件契约变更
- 数据模型或权限模型变更
- 长期架构方向，或存在多个合理的长期方案

私有方法抽取、文件布局等不问。未触发时按代码证据自行选择。

## D 的追溯

- 每个 `D#` 至少引用一条 `R#` / `AC#` 或一个可观察的代码事实（路径 / 符号）；只写模块名不算证据。
- 记录决策、理由、权衡；没有依据的 D 不写。
- 不复用 D 编号表达新决定；修订时保留未受影响的 D。

## Verification Seam

- 技术正确性在哪一层检查：仓储集成测试、事件契约测试、迁移验证等。
- 每条 seam 关联到 `D#` 与技术不变量，并说明检查层级和预期证据。
- 与 SPEC 的 Acceptance Seam（公开观察）分开；具体跑哪些检查由 verify 决定。

## Amendment

SPEC 含义不变，只有技术决定变化时，只改受影响的 `D#`，保留其他 D 与约束，不重开需求规划、不新建并行版本。若发现 SPEC 含义需要变，回 specify，不在这里改需求。

## 停止与交接

报告 TECH 位置、D 列表、Design Review Gate 状态（`confirmed` / `not_required` / `pending`）、未验证项与下游影响。

- 共享决策足以支持实现时停止；不拆分切片、不启动实现、不执行外部动作。
- 上游调用本 Skill 时，把结果交回调用方；用户直接调用时可按授权推荐下一步，但规划本身不授予实现权限。
