# Clarify - 澄清需求

## 目标

让双方对当前任务的理解足以继续：目标、范围、可观察结果，以及确实要由用户决定的问题。用户已经明确给出的选择继续有效。不要为了凑齐模板反复追问。

## 方法

1. 读用户请求、对话里已经确认过的内容，以及相关的项目资料，必要时查看现有行为、接口和调用方。标明事实来源，区分已有行为与期望行为。靠调查能确定的事实，先自行查明。
2. 找出还没定下来、定了又会改变结果的选择。判断标准是它会不会影响用户可见行为、业务规则、兼容性、权限、验收或交付范围。业务选择由用户决定，技术细节在现有约束内自行决定。
3. 必须由用户判断的问题，要给出必要的背景、可行的选项和各自的影响，并说明推荐哪个、依据是什么。只问用户现在答得上来的关键问题。已经授权、又不依赖答案的工作照常继续。推测和单个例子都不算确认过的规则。
4. 用具体例子检验边界和异常路径：前置条件、用户动作、结果和副作用。例子用来发现歧义。资料里查不出的期望行为交给用户决定，不要从实现或测试反推需求。
5. 把已经确认的目标、范围、验收依据、约束，以及还没弄清的事项汇总起来，沿用已有记录。只有用户要求，或者确有交接需要时，才更新相关文档。访谈记录、规格、状态文件默认都不新建。

## 停止与交接

需求已经够执行当前任务，就结束澄清。没定下来的事项只阻塞依赖它的那部分工作。用户只要求澄清时，给出结论就停，不自行改代码。同一个请求已经授权后续设计或实现时，可以继续已明确的部分，常规交接不必再次确认。
