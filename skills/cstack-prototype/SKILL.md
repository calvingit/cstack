# cstack-prototype · 制作原型

## 目标

用一次性原型替代反复讨论，让人对照实物，拍板一个说不清的行为、状态、界面或可行性问题。产出的是决策。原型代码留在自己的分支上，不进入主干。

相关代码由 Explorer 只读查清，原型由 Implementer 做出来。两者可以在同一上下文完成。做原型不因此获得正式实现、合并或发布的授权。

## 强制约束

- 先写判据再动手。判据放在原型顶部，打开就能看见，包含四件事：要回答的问题、候选选项、什么观察会确认判断、什么观察会推翻判断。写不出「什么观察会推翻判断」，就不做原型，转 `cstack-clarify`。
- 一次只回答一个问题。开工前把这次会话的上限写进判据：答完这一题就停。会话中途发现答不完，停手把问题拆开，只留下这次能回答的那一题。半截原型不能写成结论。
- 不伪造正在被测的那一维。测流程、状态或规则，操作必须真的驱动被测逻辑。测观感或交互，做到足以对这个问题下判断的完成度。测可行性，跑真实调用或真实约束。其余部分可以模拟，但要标明。模拟只说明原型里的结果。
- 原型代码放在独立分支 `cstack-prototype/<短名>` 上，不进主干，也不合入。未经授权不删除原型、不删除该分支，也不执行 `git reset --hard` 或 `git push --force`。「一次性」指不做后续维护，不指做完就删。
- 在主干或即将合入主干的工作区里，为原型改过的文件，结束后只恢复自己改过的那些。恢复不了就在报告里列出路径。这些改动的提交只留在原型分支上。
- 只用隔离数据和已获准的资源。不覆盖、不吞并不属于这次原型的已有工作。
- 界面、交互和体验的结论，必须有人实际看过并对照判据做出选择。当时没有人能判断，就停止并报告，不替人选定，也不把未确认的选择写入 `DECISIONS` 或 `TECH`。
- 原型能跑只说明工作状态，不等于验证状态。原型观察不能代替生产验收，不写 `EVIDENCE`。
- 原型代码不能当作 `cstack-second-pass` 的第一遍。第二遍的前提是第一遍已经能跑，而且行为依据来自已确认的 `AC#`、`DECISIONS` 或会话确认。原型没有这层依据。
- 答案已经清楚，就直接交 `cstack-implement`。局部减复杂度用 `cstack-simplify`。解释现有实现用 `cstack-how`。仓库以外的资料用 `cstack-research`。

## 产物

- **读**：要回答的问题、项目约束、这个问题碰到的代码。只读相关部分，不扫整个仓库。
- **写**：原型，加一份固定格式的报告（问题与判据、做了什么、证据、结论、状态）。报告不是正式产物。
- **落点**：用户确认的需求选择交 `cstack-clarify` 写入项目已有的 `DECISIONS`（`C#`）。共享或难以撤回的技术形状交 `cstack-design` 写入项目已有的 `TECH`（`D#`）。本 Skill 不改这两类产物的权威字段，不另建一套决策文档。项目里还没有对应位置时，沿用已有的决策或技术文档；没有这类文档，就把报告留给负责写入的 Skill。
- 需要与其他 Skill 统一产物命名、字段或共享判据时，读取 `cstack-core` 的 `ARTIFACTS.md`、`PRINCIPLES.md`、`CRITERIA.md` 对应小节；未安装时以本节作为最小可用版本。

## 选分支

先看判据真正会推翻的是哪一维，只做那一维。类型对不上时，按相关代码推断：页面或组件走界面，模块或状态规则走逻辑，外部调用、性能预算或「这条路走不走得通」走技术试验。推断写在原型顶部。

| 问题 | 读哪里 | 做成什么 |
| --- | --- | --- |
| 这个逻辑或状态模型对不对 | [LOGIC.md](LOGIC.md) | 能跑的最小操作台，加一份不依赖界面的纯逻辑模块 |
| 这里该长什么样、怎么交互 | [UI.md](UI.md) | 几个结构不同的变体，放在一起切换，优先嵌在真实页面 |
| 这条技术路线走得通吗 | [技术试验](#技术试验) | 分支上的最小脚本，结论只写走得通或走不通 |

[LOGIC.md](LOGIC.md) 和 [UI.md](UI.md) 不是单独的 Skill。技术试验不必打开它们。

窄问题是同一机制下的细节，做 2 到 3 个相近做法放在一起比。宽问题是机制本身还没选：先列出 3 到 5 条不同机制让人选一条，再往下做。

## 技术试验

只验证一个假设。代码放在 `cstack-prototype/<短名>` 分支，不放进正式源码目录，不抽公共层，不写测试。规模控制在一次会话里能读完并跑完。答不完就拆成更小的假设。

有性能或资源预算时，先写成可测量的数字，再跑。观察就是这次试验的检查：记下命令、计时和输出。结论只写「走得通」或「走不通」，并附上让结论翻盘的那条观察。命令没跑，就写未运行，不写走得通。失败就写走不通，并记下失败方式。

走得通只说明这个假设在这次条件下成立。它不说明生产实现已经验收通过，也不能代替界面或体验判断。

## 步骤

1. 写下判据：问题、候选、确认条件、推翻条件、这次做到多大规模。只读问题碰到的代码。用户只问要不要做原型，或拆分方式会出乎意料时，先用一句话说明再动手。已经点名要做原型、判据也写得出来，就直接做。
2. 选分支和存放位置。从当前基线拉出 `cstack-prototype/<短名>`，不在即将合入主干的分支上堆原型提交。
3. 做出来。一条命令或直接打开就能启动。默认不持久化。问题本身在问持久化时，这一维必须真做。每一步操作或每一次切换，都展示完整状态。
4. 在对应的面上取证。界面：每个变体都实际操作，并留下截图或录屏。逻辑：场景和会推翻判断的自由操作都跑完。技术试验：记下命令、计时和输出。
5. 界面和体验交给人对照判据下结论。技术试验按判据记下走得通或走不通。每答完一题，重算还剩哪些问题：有的已经顺带答了，有的变得没必要。没有人在场做出采纳、丢弃或转向，停在这一步并写报告。

## 分工

| Skill | 什么时候是它的事 |
| --- | --- |
| `cstack-research` | 查仓库以外的事实和资料。需要动手验证假设时，调研只给方法和判据，执行交给本 Skill |
| `cstack-clarify` | 写不出判据，或结论改变了用户可见行为、范围、验收。由它把已确认的选择写入 `DECISIONS` |
| `cstack-design` | 结论是共享或难以撤回的技术形状。由它写入 `TECH`。局部实现细节不单开设计 |
| `cstack-specify` | `DECISIONS` 里已有确认之后，整理需求与验收。本 Skill 不写 `SPEC` |
| `cstack-wayfinding` | 跨会话、方向还看不清的大块工作。本 Skill 是需要人在场的决策工单；关闭工单时在地图上链接原型位置 |
| `cstack-implement` | 采纳之后的正式实现。纯逻辑模块可以搬，但要补测试；操作台、变体和试验脚本重写 |
| `cstack-second-pass` | 第一遍已经能跑、行为依据已经确认之后，从变更前基线重写。原型不能充当那一遍 |
| `cstack-simplify` | 在现有代码上减复杂度。不拿原型代替局部简化 |
| `cstack-visual-explain` | 用图解释已经存在的东西。不做用来拍板的可操作原型 |
| `cstack-ui-review` | 审查真实界面。变体还没选定、正式界面还没有时，先不审查 |
| `cstack-diagnose` | 已有系统出了故障、原因还不清楚。不拿原型代替复现 |
| `cstack-performance` | 测量已有系统的性能。新机制能不能达到事先写明的预算，才走技术试验 |
| `cstack-verify` | 按已确认的验收条件核验正式候选。原型报告里的观察不能写成 `EVIDENCE` |
| `cstack-handoff` | 原型还没做完、要换会话。交接判据、当前证据和下一步，不把半成品说成结论 |
| `cstack-how` | 追踪并解释当前代码怎样运行 |

## 报告与停止

用下面的模板写一份短报告。空着的项写「无」「未运行」或「未决」，不省略。

```markdown
# 原型

## 问题与判据
- 问题：
- 候选：
- 什么观察会确认：
- 什么观察会推翻：

## 做了什么
- 分支：
- 轨道：逻辑 / 界面 / 技术试验
- 变体或场景：
- 启动方式：

## 证据
- 操作或命令：
- 输出、计时或截图：
- 没跑的部分：

## 结论
- 收尾：采纳 / 丢弃 / 转向 / 未决
- 胜者与理由：
- 被否决项：
- 仍开放的问题：

## 状态
- 工作状态：
- 验证状态：
- 原型位置：
```

工作状态只写原型做到哪一步、覆盖了哪些场景或变体。验证状态写「未运行」：原型观察不能代替生产验收。分支名、工作区是否有未提交改动、启动方式都要写上。

有人对照判据做了选择，收尾才是下面三者之一，由这个人决定：

- **采纳**：需求选择交 `cstack-clarify` 写入 `DECISIONS`；要整理成需求与验收时再交 `cstack-specify`。技术形状交 `cstack-design` 写入 `TECH`。正式实现交 `cstack-implement`。纯逻辑模块可以搬，但要补测试；操作台、变体和试验脚本重写。
- **丢弃**：结论已经够用。原型留在原分支，不再继续。
- **转向**：结论推翻了原来的想法。需求重新打开就回 `cstack-clarify`。要回答的是另一个问题，就另做一个原型。

技术试验可以按事先写好的数字判据，从命令、计时和输出写出「走得通」或「走不通」。判据里若已有用户授过权的那句「走得通就采纳」，收尾可以写采纳，并引用这句授权。没有这句授权，走得通也不等于采纳。

没有人在场做出上述选择，收尾写「未决」并停止。不合入、不删除、不发布。
