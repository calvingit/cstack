# Implement - 实现变更

## 目标

在用户授权的范围内做出能工作的候选变更，保留真实的检查结果，也保留还没验证的部分。

## 方法

1. 先读任务目标、已明确的验收条件、项目指令和相关代码，再查清直接调用方、现有测试和错误路径。检查仓库基线、已暂存和未暂存的改动，以及相关的未跟踪文件，把已有的工作保住。遇到关键冲突，而它的含义或授权判断不了时，只暂停受影响的部分。
2. 挑最小的完整实现，覆盖受影响的调用方和必要的错误处理。多步工作按可观察的行为一步步推进。不要扩大到无关的重构，也不要为假设中的未来扩展加新层或新依赖。
3. 实现之前先定下预期行为要靠什么独立依据来确认。按行为风险挑已有的检查，或新增必要的回归测试。有价值且可行时走测试先行。不要靠删除断言、跳过测试、放宽阈值或改变验收条件制造通过。
4. 问题原因不明时，先复现和定位，再按已授权的范围修复。诊断请求本身不自动授权修改。涉及权限、数据、迁移或外部副作用时，查清真实影响和恢复方式。
5. 跑与改动相称的开发检查，以及项目要求的门禁，记录实际跑的命令、结果和限制。检查失败要定位并处理。不能运行或证据不足时明确说明，不从自述、静态代码或绿色单测推断全部行为通过。
6. 说清候选的提交/基线和工作树里相关的改动。未提交和未跟踪的内容不能仅用 HEAD 代表。验证后又修改相关内容时，重新判断受影响的证据。

## 停止与交接

报告改了什么、候选是什么、跑了哪些开发检查，以及还有哪些没验证。在用户已授权的连续任务里，验收和审查可以继续做。做到什么深度由风险和项目规则决定。提交、推送、创建 PR、合并和部署，每一项都按已有的明确授权来。不要借 Skill 名称扩大权限。
