# Implement - 实现变更

## 底线（独立安装时自足）

- 在用户授权的范围内实现；下游角色只能收窄，不能扩权。
- 不改 SPEC、TECH、SLICES；需求、设计或范围冲突交回负责方。
- 不靠删除断言、跳过测试、放宽阈值或修改验收条件制造通过。
- 实现者自检不等于独立验收；自检记录不算 `EVIDENCE`。

## 产物

- **读**：SPEC（`R#` / `AC#`）、TECH（`D#`，若存在）、SLICES（若存在）、现有代码、基线与工作树。
- **写**：候选变更 + 自检记录（执行者标为实现者）。不写正式 `EVIDENCE`，不改上游槽位。
- 需要与其他 Skill 对齐槽位和字段时，调用 `cstack-core` Skill；未安装时以本节为最小自足版。

## 目标

在授权范围内做出能工作的候选变更，保留真实的检查结果，也保留还没验证的部分。

## 入口与硬停

- 先读目标、范围、AC、TECH / SLICES 与写入边界；检查基线、已暂存和未暂存的改动，以及相关的未跟踪文件，把已有工作保住。
- 硬停：存在活跃写入方或正在执行的切片、目标 / 范围 / 结果不清、缺共享设计、需求或设计冲突 → 先停受影响部分并交回。
- 只要求实现时，不要自行扩大成重构或清理。

## 实现顺序

1. 记录基线、初始候选和工作树状态。
2. 查清相关调用方、错误路径、现有测试和配置。
3. 实现前把每条 AC 对到一个足够的方法、前置条件和覆盖限制；缺方法就报缺口，不把“跑通命令”当验收。
4. 做最小的完整实现；多步按可观察行为推进；不为假设中的未来扩展加层或依赖。
5. 能测试先行时按 test-first 的失败→通过循环做；否则用仓库现有的最小反馈回路。测试预期来自契约，不复制实现算法；不为测试方便加生产接口。
6. 发现与本次无关的问题只记录，不顺手修。

## 自检与收尾

- 跑与改动相称的开发检查和项目门禁，记录实际命令、结果和限制。检查失败要定位并处理；不能运行或证据不足时明确说明。
- 收尾按影响的 blast radius 分级，默认 `simplify`（审查模式）→ `verify` → `review`。角色可以分开执行，也可以是不同上下文；**省略的角色记为“未运行”，不能记为“通过”**，`verify` 永不可省。
- 修复后重跑受影响的独立验证与审查。
- 只有每条适用 AC 有充分证据、独立收尾完成、没有未解决的高风险问题，才声明完成。

## 候选与报告

- 说明候选：HEAD 或提交范围，加上工作树是否有未提交 / 未跟踪改动；未提交内容不能只用 HEAD 代表。
- 报告：改了什么、候选是什么、实际跑了哪些命令和结果、simplify / verify / review 的结果、还有哪些未验证项和剩余风险。
- 验证后又修改相关内容时，重新判断受影响的证据。
- 提交、推送、创建 PR、合并、部署，每一项都按已有明确授权；Skill 名或任务名不扩大权限。
