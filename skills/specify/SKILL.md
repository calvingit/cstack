# Specify - 整理规格

## 底线（独立安装时自足）

- 只写已确认的需求；业务未决选择回到 clarify，不在这里替用户决定。
- SPEC 只写需求与可观察验收，不写实现、类/模块、文件改动、测试脚本或执行拆分。
- 每条 `R#` 至少有一条可判定的 `AC#`，预期来源必须写明。
- 例子只解释已确认规则，不新增业务规则；不建立第二份权威（如 `SPEC-v2`）。

## 产物

- **读**：DECISIONS、用户本轮确认的内容、PROFILE（若存在）、代码事实。
- **写**：SPEC，含 Goal、Scope/Out、`R#`、`AC#`、Acceptance Seam、约束、未决项。
- 需要与其他 Skill 对齐槽位和字段时，调用 `core` Skill；未安装时以本节为最小自足版。

## 入口与模式

- 来源顺序：用户本轮指定的来源 → PROFILE 的需求权威 → 仓库事实 → 本 Skill 默认。拿不到的外部内容要标明未核实，不能假装读过。
- **Create**：当前任务还没有 SPEC。
- **Amendment**：已有 SPEC 且需求新增、修改、删除或澄清。只改受影响的 `R#` / `AC#`，保留历史与未受影响部分，不新建副本。
- 需求本身还没定：先回 clarify，不要在 SPEC 里补业务决定。

## 写 SPEC

1. 收集已确认的上下文：确认项、需求来源、约束、业务术语、项目规则；指出冲突、过期快照和未确认假设。
2. 调查代码库：看现有公开行为、相关模块与调用方、类似行为的权威预期来源。只把代码当事实，不把它当新需求。
3. 确定 Acceptance Seam：需求在哪个公开面可被观察；优先用现有公开面，不为测试暴露内部。
4. 写 `R#` 与 `AC#`：每条 AC 写清来源、可观察结果、可判定条件和必要的失败情形。
5. 做一致性检查：问题、目标、范围、约束与验收不互相矛盾；每条 in-scope R 有 AC 覆盖；ID 唯一且稳定。
6. 写入并交接；不修改下游的 TECH、SLICES 或 EVIDENCE。

## Acceptance Seam

- 需求完成情况可被观察的位置：用户交互、外部契约响应、导出文件。
- 优先现有公开面；内部服务、仓储 mock、数据库表、测试层级和测试脚本属于 TECH 或验证，不写进 SPEC。
- 为每条 AC 标明覆盖它的 seam 与预期来源。需要新增公共契约才能验收时，回到 clarify。

## R 与 AC 的写法

- `R#` 描述必须满足的行为；`AC#` 描述可独立判定的结果。
- 每项 AC 至少能回答：前置条件、动作、预期结果；必要的失败或副作用。
- 避免“符合预期”“测试通过”“工作正常”这类无法独立判断的说法。
- 不写占位符，不编造字段、错误、公共契约或业务约束；缺的先调查，仍缺就回到 clarify。
- 简单明确的 AC 不需要场景表；例子只在能澄清真实分支或防止误读时使用。

## 两个交接判断

确认 SPEC 后，独立判断两件事，不要合并成一句：

1. **是否需要 TECH**：涉及多模块共享类型、接口、状态、迁移、公共契约或长期方向时，交给 design；否则报告 `tech_not_required` 并给出依据。ticket 数量不是判据。
2. **执行路线**：按交付边界与真实依赖，推荐直接实现或拆成 SLICES；风险高低本身不强制拆票。尊重用户已选的路线。

## 停止与报告

报告 SPEC 位置与确认状态、`R#` / `AC#` 数量与来源、未决项与阻塞、是否需要 TECH 及理由、推荐路线、当前授权范围。

- 只授权规划时，写完 SPEC（及必要判断）就停，不擅自实现或拆票。
- 不把 SPEC 当成实现许可；不修改代码、TECH、SLICES 或 EVIDENCE。
- 证据不足或来源冲突未解决时保留未决，不给出“看起来完成”的结论。
