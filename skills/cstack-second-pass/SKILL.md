# cstack-second-pass · 第二遍重写

## 目标

第一遍实现已经能跑。用这一遍学到的约束、死路和临时做法，从变更前的基线重写一个更简洁的实现。已确认的行为与范围保持不变。

第一遍能跑只说明工作状态，不表示已经验收通过。

## 强制约束

- 重写前先提交或打标签，保住第一遍，使它可以恢复。第一遍还不能恢复时，不开始重写。
- 在新分支上从变更前的基线重写，不在第一遍的实现上打补丁。
- 保持已确认的行为、接口和兼容性；不新增功能，不扩大范围。
- 更简洁指更少的概念、重复和抽象层，不是更少的行数。
- 工作状态与验证状态分开写；未运行不等于通过。
- `git reset --hard`、`git push --force`、删除第一遍所在分支，需先取得用户授权。

## 重写步骤

1. **写下「第一遍学到什么」**。短笔记，只记四件事：真实约束、走过的死路、哪些辅助只是临时的、哪些测试定义了行为。
2. **保住第一遍**。提交、打标签或留在独立分支上，记下可恢复的引用。笔记留在对话里，或跟第一遍一起提交，换到基线分支后仍然拿得到。
3. **从基线重写**。新分支的起点是变更前的基线。重写时只把这份笔记和第一遍的测试当作输入，不把第一遍的结构搬过来。去掉临时辅助、重复逻辑和没有必要的抽象层。
4. **两边跑同一组测试，再用 `git diff` 比较**。对照基线看每一版的变更面；对照两版实现比较新引入的概念数量、重复逻辑和抽象层数。记下命令和输出。
5. **推荐一个版本**。理由和风险写进报告。第二遍没有明显更简洁时，保留第一遍。

## 报告与停止

用下面的模板写一份短报告：

```markdown
# 第二遍重写

## 第一遍学到什么

## 两个版本
- 第一遍：
- 第二遍：

## 测试
- 第一遍：
- 第二遍：

## 比较
- 变更面：
- 新概念：
- 重复逻辑：
- 抽象层：

## 推荐
- 版本：
- 理由：
- 风险：
```

两个版本都写明分支、提交或标签。测试未运行就写未运行，不写成通过。第二遍没有明显更简洁时，推荐第一遍，并写明原因。

报告写完即停止。不合并、不删除分支、不交付。
