# Visual Explain - 图形化解释

围绕用户要理解的问题，把关键关系展示出来，让图形比纯文字更容易看懂。可用于解释概念、现有代码、方案或变更。图形只是解释工具，不能当作运行证据。

## 确定内容和依据

1. 先明确受众、要回答的问题、需要呈现的关系和交付位置。用户指定了格式就按格式来。用户明确要求图形时，应交出看得见的图形或图示；渲染不出来时，说明限制，并给出当前环境可用的替代方案。
2. 解释当前项目时，读取相关的源码、配置、调用路径和必要资料。解释变更或 PR 时，先确认用户指定的候选和基线，再看实际 diff 和必要的周边代码。涉及工作树时，把相关的未提交文件和未跟踪文件也算进来。访问不到，或范围不完整时，要把情况说明白，不要猜测实现。
3. 要把已观察到的事实、推断、拟议的方案和用作示意的数据分开。每个重要节点、连接、条件和数值，都要有来源；没有来源的，就明确标成示意。设计图和模拟出来的交互，都不能证明真实系统真的在运行。真实截图只能说明它在拍下那一刻可见的样子。

## 优先使用 Runtime 的可视化能力

1. 先看当前会话实际能用哪些 Skill 和工具，找出宿主原生的 `visualize` 或等价的可视化 Skill。它叫什么、有哪些能力，都以宿主注册的为准。不要假设每个 Runtime 都提供它，也不要把本 Skill 当成原生 `visualize`。
2. 用户需要**对话内**的图形或交互解释，而原生 `visualize` 又适合这个请求时，就优先按宿主给的 Skill 调用方式去用它。它规定的适用范围、可用工具、渲染和交付规则，都要先读清楚再照着做。只是提到名字，或者生成了一个相似的文件，都不算真的调用过。调用用不了或失败了，就说明限制，再从下面几种退路里选。
3. 原生能力不适用时，就按用户的目标和当前环境，挑一个能渲染出来的图示、表格或其他原生能力。流程、状态、依赖和数据流可以用 Mermaid 这类图示；要精确对比字段，可以用表格。用户要的是能复制的 PR Markdown 时，就选目标平台支持的结构图、表格或 `diff`，不要依赖嵌不进去的对话组件。
4. 用户明确要可下载的 HTML 时，按宿主的文件交付规则，做一个聚焦、能直接打开的单文件 HTML。需要交互探索、而宿主又没有可用的原生可视化时，也可以这样做。用户只要静态说明、也没指定文件形式时，不要为了展示效果去创建页面、安装依赖或额外加一层适配。

## 根据关系选择图形

- **顺序、分支或状态变化**：要展示触发点、关键路径和结果，不要把无关的步骤串成一条长链。
- **模块、数据和依赖关系**：标出主要的边界、方向和责任。范围复杂就拆成几张小图，不要把文字缩小硬塞进一张图。
- **方案或状态对比**：让差异、共同条件和取舍放在一起就能比出来。数值图要保留来源、单位和合适的尺度，不要编造指标。
- **变更说明 / PR**：用尽量少的视图，把变更前后、核心调用或数据结构展示清楚，并点出会影响审查的兼容性、迁移或验证限制。描述只依据实际 diff 和来源。需要能复制的 PR 文案时，补上简短动机和结构概览。
- **交互探索**：只有在切换条件、参数或步骤确实有助于理解时，才加控件。交互结果要基于明确的规则，把示意模型和真实系统分开。

按内容来选形式，不要套固定的页面模板。需要参考场景时，读取 [表达示例](references/examples.md)。

## 质量与交付

- 优先沿用用户和项目已有的视觉约定。没有明确设定时，用中性色加少量语义色，避免默认的绿色主题、蓝紫渐变、装饰性发光和重复的大卡片。排版与配色都要为信息层级服务。标签要清楚，对比度要够，控件要能用键盘操作，不要只靠颜色表达含义。
- 给出简短的结论和必要条件，不要在正文里把图里的内容再重复一遍。相关的源码、差异、文档或数据来源，要放在能查证的位置。信息缺失时，标明未知。
- 检查图里的方向、标签、分支和内容跟来源是否一致，也检查能看到的渲染效果、视口和实际交互。没法预览、执行或确认的部分，要明确写成未验证。生成成功，并不能证明所描述的软件已经通过验收。
- 遵守用户和宿主关于输出、文件保存和权限的规则。只要求解释或起草 PR 文案时，保持只读，不要创建、修改或发布 PR。用户另外明确授权时，可以在授权范围内继续。
