# Architecture Review - 审查现有架构

## 强制约束

- 只判断现有结构，不设计目标方案、不实施重构。
- 目录名、抽象层数量和个人偏好都不是缺陷证据。
- 发现要说明位置、触发或维护场景、影响、支撑事实和未查清部分。
- 默认只读；范围过大时挑高影响路径，并报告未覆盖部分。

## 产物

- **读**：架构约束、关键入口、ADR、代码与配置、真实调用链。
- **写**：架构审查报告（范围、当前结构、按影响分类的发现、反证、限制）。不写正式产物；需要形成共享设计的技术决定交回 `design`。
- 需要与其他 Skill 统一产物命名和字段时，调用 `core` Skill；未安装时以本节作为最小可用版本。

## 目标

判断指定范围内的现有结构是否满足项目约束，找出职责、依赖或生命周期上确实有实际影响的问题。先把当前事实和代价说清楚，再谈方向。

## 审查维度

- **职责与归属**：一处变化是否要同步改多处；一个模块是否因多个不相关原因而改动。
- **依赖方向与边界**：跨层 / 跨模块依赖是否绕开契约；是否有循环依赖。
- **接口深度**：是否浅模块、透传多、内部细节泄漏到调用方。
- **状态与生命周期**：谁拥有状态；并发、取消、清理是否清楚。
- **重复与死代码**：是否多套并行实现、过期兼容路径、无人使用的抽象。
- **可验证性**：关键行为是否有可观察的 seam；与 `codebase-design` 配合判断。

不预设某种架构风格；用项目约束和行为证据判断。

## 流程

1. 定审查范围、质量目标与基线；读架构约束、关键入口和已有决策。文档只是线索，要和当前代码、配置核对。
2. 从生产入口、代表性调用方、模块边界、数据与控制流、依赖注入和状态生命周期，追实际责任。测试和配置能提供证据，但目录名或抽象层数量本身说明不了问题。
3. 针对最强的疑点找实际影响：一处变更同步改多处、错误语义在边界丢失、资源无法安全关闭、持久数据兼容受损。再找能推翻它的现有约束、保护和调用路径。
4. 每项发现写位置、具体触发或维护场景、影响、支撑事实与未知；把直接观察和推断分开。
5. 按影响和证据强度分成必须处理 / 值得考虑 / 可接受，给出方向与最小可验证的后续工作。没有足以改变决策的问题就报告没有发现。

## 停止与交接

输出范围、当前结构、发现、反证和限制。架构审查默认只读，不代替具体变更的代码审查，也不自行设计或实施重构。用户另行要求方案或修复时，按已有授权继续，并把设计交给 `design`。
