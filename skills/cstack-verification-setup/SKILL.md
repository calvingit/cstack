# Verification Setup - 建立项目验证能力

## 底线（独立安装时自足）

- 先发现项目已有的验证方法；够用就不新建。
- “起来了”指应用可用，不是端口有响应。
- 只写能实际运行、操作、观察的方法；没试运行的标为草稿。
- 不修产品、不放宽断言来让方法变绿；不静默安装框架。

## 产物

- **读**：项目指令、依赖、脚本、CI、测试、PROFILE 的验证入口。
- **写**：项目验证方法（可复用入口、Launch / Doctor / Drive / Observe / Isolate / Cleanup、Feature Map、限制）。放在项目已有位置或本地验证 Skill；PROFILE 只放链接与摘要。
- 不写正式任务槽位，也不判定某个候选是否通过——那是 verify 的事。
- 需要与其他 Skill 对齐槽位和字段时，调用 `cstack-core` Skill；未安装时以本节为最小自足版。

## 目标

让后续执行者知道怎样安全启动、操作并观察项目的相关行为。项目里已有测试、脚本、CI 和文档时，优先复用；不要默认生成新 Skill，也不强制安装框架。

## 先盘点

1. 读项目指令、Git 状态、文档、manifest、scripts、CI、测试配置和相关测试。
2. 识别界面：UI / API / CLI / library / device；怎么构建和启动、怎么驱动、能观察什么、怎么隔离和清理。查版本、认证、种子数据、端口和共享资源。
3. 每个方法记录来源、命令、前置条件、实际能证明什么、限制；不要根据工具名推断覆盖范围。
4. 区分行为、视觉一致性和交互质量；不要用测试名或 mock 冒充真实系统。

## Harness 契约

建立或更新方法时，至少写清这几段，并用真实内容填满：

- **Launch**：确切启动命令、就绪判据、关闭方式。
- **Doctor**：只读检查“这个实例值不值得驱动”——进程、版本、端口归属、认证。
- **Drive**：真实选择器与命令；优先稳定句柄（ARIA、data 属性、路由），不用坐标和 tab 顺序。
- **Observe**：抓什么证据、放哪里、证据标准；走真实用户路径，不用内部 setter 或测试专用接口。
- **Isolate / Cleanup**：能否并行两个实例；只关自己启动的，不按进程名杀；清理不删除证据。
- **Helpers**：附带脚本必须可执行，调用方式写在方法里。
- **Feature Map**：功能 → 验证入口 → 证据类型 → 限制。

## 就绪判据

- 从空数据目录启动，跑完迁移和种子数据，再用一个真实读请求确认可用。
- 端口通不等于应用可用；按端口判断会过早开始操作。
- 每个新增或改过的方法实际跑一遍最小但代表性的路径：启动、操作、观察、留证、清理。跑不通就标为草稿或受阻。

## 停止与交接

报告可复用方法、前置条件、观察范围、试运行结果、清理情况和还缺的部分。已有位置够用时不另造 Profile 或能力索引。方法能跑只说明能观察到东西，不代表哪个任务候选已经通过验收；不修改产品代码或测试断言来掩盖失败；不擅自提交或推送。
