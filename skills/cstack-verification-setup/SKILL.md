# Verification Setup - 建立项目验证能力

## 目标

让后续执行者知道怎样安全启动、操作并观察项目的相关行为。项目里已经有测试、脚本、CI 和文档时，优先复用；不要默认生成新的 Skill，也不要强制安装框架。

## 方法

1. 先确定这次请求是只做调查、建立新方法，还是修复失效的方法。然后读项目指令、依赖、现有的运行命令、测试、CI 和相关入口，分清哪些能力只是声称有、哪些是真正跑过的。只做调查时保持只读。
2. 针对目标界面逐项查清：怎么启动、什么条件算就绪；从哪个入口操作；需要哪些身份、种子数据和依赖；怎么观察结果和副作用；版本与构建身份是什么；怎么做隔离、资源归谁、怎么清理。一个项目可能同时有 UI、API、CLI、设备等多个入口，不必一次全查。
3. 把现有方法和需要观察的行为对上，指出哪里走的是真实路径、哪里是 mock 或模拟边界，还缺哪些项。不要因为工具名字里有某个词，就声称它覆盖了真实系统；也不要把当前实现的行为当成验收预期。
4. 得到授权去做建设时，先复用已有方法，只补必要的脚本、项目说明或测试能力。新增依赖、接入外部系统、对共享资源做写操作，都要受用户和项目的授权约束。不能为了让方法跑起来，就悄悄改掉产品行为或放宽断言。
5. 对新增或改过的方法，实际跑一遍最小但能代表典型用法的路径：启动、操作、观察、留下证据，再清理自己创建的资源。记下命令、环境、实际结果和没覆盖到的范围。无法试运行时，把它标为草稿或受阻。

## 停止与交接

报告可复用的方法、前置条件、观察范围、实际试运行结果、清理情况和还缺的部分。已有位置够用时，不要另造新的 Profile 或能力索引。项目的方法能跑，只说明能观察到东西；这不代表哪个任务候选已经通过验收。
