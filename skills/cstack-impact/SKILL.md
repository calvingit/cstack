# Impact - 变更影响分析

## 目标

查清一项已有或拟议中的变更实际影响到什么，找出它的安全取决于哪些关键事实，以及仍需继续观察的风险。结果供方案、实现、验证或审查参考，不自动替代这些判断。

## 方法

1. 先确定这次变更想做什么，候选或拟议的范围有多大，基线在哪里，已知有哪些约束。已经有变更时，去看实际的 diff 和工作树。只有方案时，标明它尚未实现，计划中的行为不能当成现状来写。
2. 从受影响的入口往下追，找出必要的调用方、数据流和下游消费者，公共接口、序列化格式、持久数据、异步任务和外部系统都算在内。搜索引用只是起点。动态调用、配置和跨语言契约可能有盲区，查不到的地方要明确说明。
3. 找出少数几个关键不变量，判断影响要靠它们，比如谁能访问、写入是否幂等、旧数据能不能读出来、失败后能不能恢复。对每一项都说明实际证据是什么，这些证据能支撑什么结论。确有必要并已获授权时，运行针对性的检查；不能为了证明安全去操作真实业务数据。
4. 按触发条件、影响对象和实际后果，列出有证据的风险。已经查明不受影响的部分和判断不了的地方，也要一并记下来。区分直接观察、从代码推断和待证实的假设；可能性清单上的条目还没发生，不能当成已经出现的缺陷。
5. 指出哪些验收、构建、配置或审查证据可能因为这次变更失效，以及最小可行的补充检查。能证明不受影响的证据可以继续用。判断不了的部分，要么继续观察，要么保留为未知。

## 停止与交接

报告基线与范围、受影响的路径、关键不变量的证据、已排除的事项、剩余风险和检查建议。只做分析时，默认不改代码，也不执行交付。证据不足时，不要宣布这次变更安全。
