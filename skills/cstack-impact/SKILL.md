# cstack-impact · 变更影响半径

## 目标

在设计、实现、验证或审查之前，弄清这项变更会在别处碰到什么，并尽量证明决定其是否安全的关键事实。列调用方不是活——关键安全事实才是。不做逐条验收、不做缺陷审查清单、不做方案对抗，也不批准交付。

## 强制约束

- 未证明的事实标「未证明」，不得写成已安全；已排除与未证明分栏。
- 未实现的方案可分析，须标明「未实现」，不得写成现状。
- 默认只读；不为证明安全操作真实业务数据。改代码或跑会改状态的检查需授权。
- 工作状态与验证状态分开写；未运行 ≠ 通过。

## 证明层级

对每条「凭它安全」的事实，尽量往下推，并写明停在哪一层：

1. **说了算** — 单独无价值。
2. **指到行** — 真实 `file:line`，或所调库源码与钉死版本。
3. **推演到走不通** — 逐步走失败路径，证明到不了坏结果。
4. **跑真实代码** — 脚本或测试导入应用实际依赖的同一库/同一函数，错了就失败；通常停在这一层。
5. **运行中复现** — 在真实运行的应用里复现或证伪。

只列出调用方、搜索无结果、或只写报告，都不到第 4 层。

## 方法

1. **读变更**：符号与行为上实际变了什么（含 diff 未写明的）。仅有方案时标明未实现。
2. **找 1–2 条关键安全事实**：多数风险取决于一两句话（例如「这次调用只清理已失效缓存」）。先找这条，不堆可能性清单。
3. **查符号搜不到的地方**：库源码与版本/补丁、时序与卸载、返回 JSON、DB 列、线格式、跨语言同字节、feature flag、多跳下游。
4. **写风险与已排除**：每条写触发、对象、可能与代价、`file:line`、怎么查；查过无事的另列。不编造调用方或 API。
5. **按证明层级证明那 1–2 条事实**：尽量跑真实代码，贴命令与输出；证不了就标「未证明」并写明卡在哪一层。

## 停止与交接

写出一份短报告后停下：

- **改了什么**（方案则标未实现）
- **凭它安全的事实**：陈述、证明层级、证明；未证则写「未证明」
- **风险** / **已排除** / **未证明与未知**
- **合并前最便宜的检查**（含哪些验收/构建/审查证据可能因此失效）

证据不足时，不宣布这次变更安全；默认不改产品、不执行交付。本报告非正式产物，不替代规格、技术决定或验收证据。
