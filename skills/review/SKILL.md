# Review - 审查变更

## 硬约束

- 只审指定的提交、分支、工作树或路径；读不到范围或 diff 为空是限制，不算审查通过。
- 发现要有可达场景、具体位置和实质后果；先查能推翻它的保护条件。
- 不改产品、需求或 Git 状态，只报告。
- 审查不替代逐 AC 验收，也不等于交付许可。

## 产物

- **读**：diff、SPEC（`R#` / `AC#`）、TECH（`D#`，若存在）、EVIDENCE（若已有）、项目规则。
- **写**：审查报告（结论、范围、按影响排序的发现、后续项、需求缺口、未验证范围、证据）。不修改正式槽位。

## 目标

本 Skill 执行 **Reviewer** 角色：找出这次改动可能引入的问题，判断哪些真能发生、也确实有影响，让修复有据可查。请求只做审查时，默认只读。

## 确定范围

- 用用户指定的 commit / branch / worktree / path 固定基线，并区分出既有改动。
- 分支比较用 merge base；单提交看该 commit 的 patch，不用三点比较 HEAD。
- 工作树审查包含暂存、未暂存和相关未跟踪文件。
- 读需求与项目规则；没有需求来源时，只报可证明的缺陷，并说明“需求完整性未评估”。

## 审查什么

- **意图与行为**：是否满足确认需求，含失败路径；有没有未经授权的新行为或公共契约变更。
- **正确性与回归**：可达输入、状态转换、错误传播、并发、资源生命周期；追踪 diff 之外可能受影响的交互。
- **安全与成本**：权限绕过、数据丢失、敏感信息、真实负载下的性能或资源问题；说明触发条件与影响。
- **设计与复杂度**：是否贴合现有边界与约定；只在维护成本具体可见时，报多余的兼容路径、猜测性抽象或仅为测试增加的间接层。
- **证据**：测试是否断言预期可观察行为、覆盖风险路径；命令通过不证明需求正确或测试有意义；区分实际检查过的证据与声明。

不重复 formatter / linter / type-checker 的输出；没有具体失败就不要要求更多测试、抽象、兼容或防御代码。

## 决定什么算数

- 报告前查相关保护、调用方和测试，看能否推翻这个发现。
- 严重度：`P0` 影响面广且后果严重；`P1` 严重，需尽快修复；`P2` 局部可修复的缺陷；`P3` 可选改进。严重度与“是否阻塞本次变更”是两个决定。
- 本次引入或加重的问题必须修；无关的旧问题和可选改进列后续，不阻塞本次。
- 合并同一根因的重复症状；按影响排序，不按审查类别排序。
- 需求矛盾交需求负责人；缺访问或缺证据写限制，不编造缺陷，也不判通过。

## 两轴（可选）

- **Standards**：是否符合本仓有据可查的规范。
- **Spec**：是否忠实实现来源需求。
- 分开报告，不合并排序，避免一轴掩盖另一轴。规范来源缺失时只审可证明的缺陷。

## 报告

给出结论、范围、按影响排序的发现、后续项、需求缺口、未验证范围和证据；输出可读 Markdown，不返回 JSON。没有发现时，说明哪些部分没有覆盖到，不要声称已经证明代码没有缺陷。

## 停止与交接

只读。修复需要用户在同一次任务中明确授权；修完复查受影响的改动和仍开放的问题。审查有合理预算；预算用尽而关键问题未解，保留为未解决项，不自动视为通过。
