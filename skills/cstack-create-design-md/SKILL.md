# cstack-create-design-md · 建立与更新界面设计文档

## 目标

写出一份机器和人都读得懂的 `DESIGN.md`：YAML 里是规范值，正文解释为什么、怎么用。后续做界面、做视觉审查时有同一份依据，而不是每次重新猜。

本 Skill 只管视觉系统（颜色、字体、间距、圆角、组件形态与禁令）。产品气质和受众写在 Overview，不另建产品事实文件。业务规则和工程约定不写进这里。技术方案仍归 `cstack-tech-design`。

## 强制约束

- 只在用户手动触发时运行；不在「顺便写个设计文档」时自动跳出来。
- 格式按 `DESIGN.md` 规范：token 只放 `colors` / `typography` / `rounded` / `spacing` / `components` 五组；正文 8 节标题与顺序固定（见「格式」）。不另起顶层 token 组。阴影、动效、过渡、深色主题和取舍理由写进已有正文节。
- 组件属性只用规范允许的键。阴影、动效、过渡不进组件 YAML。
- 每个写入的值都要能追溯到来源。一次性的字面值、工具类名、只出现一次的数字不算规范值，不进 YAML。
- 「不要做」只写来源里明确禁止、或至少两个页面共用组件里反复违反会出问题的禁令；没有依据就不写。
- 已有设计文档时不静默覆盖：先展示差异与拟写内容，用户确认后再写。更新时对比写入前的副本，看有没有退步。
- 写完要校验。项目指令或 PROFILE 写了校验命令就跑那条；没写就跑官方 CLI。命令跑了但失败，不交付。命令没有跑起来，就做人工核对并报告未验证；未运行不等于通过。
- 不改产品代码、不改测试、不把设计值硬塞进实现。配置本身不授予提交或推送权限。
- `AGENTS.md`（或等效指令文件）与工程档案的写入权归 `cstack-create-project-profile`。本 Skill 只交回待并入的片段，不直接改那些文件。
- 与 `cstack-tech-design`、`cstack-ui-review`、`cstack-prototype` 分清：本 Skill 写规范文档；技术方案写共享技术决定；界面审查读规范找看得见的问题；原型用来试一个说不清的方向，试完的结论可以回流，原型代码本身不是规范。

## 产物

- **读**：现有设计文档（若有）、PROFILE 的「界面设计系统位置」、项目指令、全局样式与主题配置、组件库、设计相关文档；种子模式还读用户对气质与受众的回答。项目若写了校验命令，一并读出来。
- **写**：`DESIGN.md`（首次建立或增量更新同一份）。位置按顺序选：PROFILE 的「界面设计系统位置」或项目指令里已链接的路径 → 仓库根目录已有的 `DESIGN.md` → 都没有才新建仓库根目录 `DESIGN.md`。
- **交回**：需要把位置记进工程档案时，只交回待并入片段，由用户手动触发 `cstack-create-project-profile` 写入。本 Skill 不写 `AGENTS.md`，也不写 PROFILE。
- 需要与其他 Skill 统一产物命名时，读取 `cstack-core` 的 `ARTIFACTS.md`、`PRINCIPLES.md`、`CRITERIA.md`；未安装时以本节为准。`DESIGN.md` 不是六类正式产物，按项目基座的旁路文档处理。

建议交回的片段（路径按实际替换）：

```markdown
- 界面设计系统位置：`DESIGN.md`；做界面、改主题或做视觉审查前先读。
```

## 格式

正文 8 节，有则按此顺序。缺的节在 frontmatter 的 `omitted` 里标明原因，不改标题，不加第九节：

1. Overview
2. Colors
3. Typography
4. Layout
5. Elevation & Depth
6. Shapes
7. Components
8. Do's and Don'ts

YAML token（frontmatter 或节内 `yaml` 代码块，同一顶层键全文件只出现一次）：

- `version`（当前为 `alpha`）、`name`（必填）、`description`（可选）、`omitted`（可选）
- `colors`：扁平语义名 → CSS 颜色
- `typography`：层级名 → `fontFamily` / `fontSize` / `fontWeight` / `lineHeight` / `letterSpacing` / `fontFeature` / `fontVariation`
- `rounded`、`spacing`：刻度名 → 带单位的尺寸；只有规范允许无单位数时才写无单位数
- `components`：组件名 → 属性。属性只用 `backgroundColor`、`textColor`、`typography`、`rounded`、`padding`、`size`、`height`、`width`。值尽量引用已有 token（`{colors.primary}`）。悬停、按下、聚焦、禁用、错误态写成另一条相关组件（如 `button-primary-hover`），不往属性里加规范没有的键。

正文写法：描述在前，精确值放括号里。颜色、字体按角色说明「用在哪」，不堆无角色的色板。组件写清关键状态和变体。

放不进上述键的内容，写进已有正文节，不新开顶层 YAML 组，也不另建一份并行文档：

- 产品给谁用、界面要留下什么感觉：Overview。
- 深色主题：Colors。引用已有颜色，说明何时切换。
- 阴影和层次：Elevation & Depth。
- 动效和过渡：写进它所属的那一节，多半是 Components。
- 为什么这样定、放弃了什么：写进对应节。种子模式可以在相关节末加一小段决定记录；这是可选的，不写也不算没做完，不单开必填的一节。

## 证据门槛

候选值先记成一行依据，再决定进不进 YAML：

```text
角色 → 值 → 来源 → 作用范围 → 复现次数 → 确信度
```

- **来源**：文件路径与符号、主题配置键、用户确认的回答、设计稿或截图里的测量。截图不能单独充当精确值依据。
- **复现**：至少在两处共享用法，或被具名 token / 主题变量定义过，才进 YAML。
- **确信度**：`confirmed`（有共享定义或用户确认）/ `inferred`（多处字面值一致但无具名 token）/ `missing` / `conflicting`。
- `inferred` 可以进正文说明，进 YAML 前要标出来并在报告里列出；冲突未解决不写入。
- 种子模式下尚未落地的值写成 `[实现时再定]`，不编造精确色值或字号。

## 选择模式

| 项目状态 | 模式 | 做什么 |
| --- | --- | --- |
| 已有界面或主题代码 | 扫描 | 从代码与配置抽取复用值，再补只能问人的气质与禁令 |
| 几乎没有界面，要从零定视觉方向 | 种子 | 短访谈 → 草案 → 确认后写种子版 `DESIGN.md` |
| 只要审当前页面好不好看 | 停 | 改走 `cstack-ui-review` |
| 只要定共享接口、数据模型或迁移 | 停 | 改走 `cstack-tech-design` |

用户点名模式就按点名的做。两种都说得通时，先报告判断依据，问一次再继续。线上站点抓取、外部设计稿的变量拉取本版不做；用户只要这两项时说明缺口，能从仓库代码补的部分仍可做扫描。

## 扫描模式

1. **定位来源**（按优先级，有就读，没有就跳过）：CSS / 设计变量 → Tailwind 或等价主题配置 → CSS-in-JS / 主题对象 → token 文件 → 组件库主题 → 全局样式。不根据框架名臆造刻度。
2. **收集候选**：按「证据门槛」逐条记录；只出现一次的值进省略清单，不进 YAML。
3. **只问人补不了的部分**：每轮最多 3 个问题，例如整体气质一句话、颜色的描述性名字、层级是靠阴影还是靠色面。能从代码读到的不问。气质和受众的答案写进 Overview。
4. **起草**：按「格式」写出完整草案；冲突项单独列出，不擅自拍板。
5. **进入写入与校验**。

## 种子模式

1. **短访谈**（能合并就合并，总数控制住）：
   - 产品给谁用、界面应该让人记住什么感觉。这两点写进 Overview，不写成另一份产品文档。
   - 更偏稳妥还是更偏辨识度；有没有必须避开的视觉雷区。
   - 已有品牌色、字体，或「不要像某种既有气质」的约束。
2. **出草案，不直接落盘**：用文字说明气质、角色色、字体层级与组件方向；没定的值标 `[实现时再定]`。需要时给「稳妥 / 大胆」两个方向对比，等用户选一个或指出混合方式。决定记录可选，不作为这一步的完成条件。
3. **确认后再写**种子版 `DESIGN.md`。实现落地后应再跑一次扫描模式，用真实 token 替换待定项。
4. **进入写入与校验**。种子版若有意留空若干节，在 `omitted` 或报告里写明原因。

## 写入与校验

1. 展示：模式、依据摘要、拟写全文或与旧文件的差异、拟交回的档案片段、冲突与省略项。
2. 用户确认写入策略：新建 / 刷新（保留已确认决定，只更新有证据变化的部分）/ 覆盖 / 取消。默认可选「刷新」；「覆盖」必须明示。
3. 写入前保留旧文件副本（更新时）。写入后按下面的顺序校验，只跑适用的那一档：
   - 项目指令或 PROFILE 已经写明校验命令：运行那条，不再额外跑官方 CLI。
   - 没有项目命令：运行 `npx --yes @google/design.md lint <路径>`。更新已有文件时，再运行 `npx --yes @google/design.md diff <写入前副本> <写入后文件>`。项目使用 Tailwind，或项目要求导出时，再运行 `npx --yes @google/design.md export`，格式按项目约定（Tailwind v4 用 `--format css-tailwind`，Tailwind v3 用 `--format json-tailwind`），抽查导出里有没有预期的颜色和字体变量。
4. 命令跑起来之后：`lint` 有 error，或 `diff` 退出码非 0（错误或警告变多），或导出抽查对不上，先改文档再交。改不了就报告失败项，不把失败写成完成。warning（含对比度）写进报告；退出码只说明有没有 error，不能用来把 warning 说成没问题。
5. 该跑的命令没有实际跑起来（没有网络、命令不存在、环境起不来）：按规范人工核对节顺序、必填 `name`、引用是否断了、主色和文字的对比关系，并报告未验证。未运行不等于通过。人工核对只说明看过哪些项，不能写成 lint 通过。
6. 重读落盘文件，检查差异。需要挂到工程档案时，只准备片段，提示用户手动触发 `cstack-create-project-profile`。

## 报告与停止

报告里写清：

- 模式（扫描 / 种子）与设计文档路径
- 主要来源与省略项（含一次性值、冲突未写入项）
- 相对旧文件的变更摘要；若跑了 `diff`，有没有退步
- 校验结果：实际运行的命令与结论，或未运行及原因。未运行要写成未验证，不写成通过
- 交回工程档案的片段（若有）与待用户确认的项
- 建议的下一步：有界面后补扫描、交给 `cstack-ui-review`，或无需再做

写完报告即停止：不提交、不推送，除非另获授权；不修改产品代码；不代替界面审查或技术方案。
