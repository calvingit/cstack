# Clarify - 澄清需求

## 底线（独立安装时自足）

- 只处理会改变用户可见行为、范围、验收、兼容或权限的未决选择；私有实现细节自己定。
- 能查的事实自己查，不把事实问题当决策问题抛给用户。
- 决策归用户；不替用户选，也不把单个例子或推测写成规则。
- 确认项写入 DECISIONS；未决项保留，不用假设填平。

## 产物

- **读**：用户请求、会话中已确认的内容、PROFILE（若存在，用于项目术语与需求权威）。
- **写**：DECISIONS，每项含 `C#`、问题、选择、理由、可观察结果、确认来源、未决项。
- 需要与其他 Skill 对齐槽位和字段时，调用 `core` Skill；未安装时以本节为最小自足版。

## 目标

让双方对当前任务的理解足以继续：目标、范围、可观察结果，以及确实要由用户决定的问题。用户已经明确给出的选择继续有效。不要为了凑齐模板反复追问。

## 决策树

把讨论画成一棵**决策树**：每个决定都会分叉出依赖它的决定。树必须留在已确认的目标与范围内；范围本身是第一个要定的枝。

## 前沿与轮次

- **前沿（frontier）** 是所有“前置条件已经确定、现在就能问、不用猜还没听到的答案”的未决选择。
- 一轮问完整个前沿，等用户回答。不要逐个挤牙膏，也不要一次问到依赖未答项的分支。
- 用户每答一轮，树被重塑：已定的决定会解锁它下游的问题。重算前沿，再问下一轮。
- 依赖某个未答问题的问题属于后面的轮次，不属于本轮。
- 只有新证据或需求变化才重开受影响的枝，不整棵树重来。

## 事实调查

- 能看代码、文档、工具或现有行为查到的，先自己查，不把事实问题当决策问题问用户。
- Runtime 支持子代理时，按 [事实调查子代理定义](references/fact-finder.md) 派发只读调查（对应 `core` 的 Explorer 角色）；一个前沿里可以并行多条，各自报告结论、证据、置信度和未解决项。暂不支持时，按同一职责自己调查，保持同样的输出结构。
- 正在进行的调查只阻塞它下游的问题，其余前沿照常问；不要等所有事实回来才开始整轮提问。
- 子代理只查事实，不做需求决策；涉及业务选择时回传“需要用户决定”。
- 不编造拿不到的来源内容，也不把未决选择静默假设成答案。

## 决策分类

| 选择 | 谁定 | 记录去向 |
| --- | --- | --- |
| 用户可见行为、范围、验收、兼容、权限，以及外部契约字段、协议限制、后端定义状态 | 用户 | DECISIONS → SPEC 输入 |
| 跨模块架构边界、公共契约变更、共享模型、长期技术方向 | 记为技术关注点 | 交给后续 design 审查，不在访谈里选实现 |
| 私有方法、文件布局、局部重构、内部辅助 | Agent | 自己定，不问 |

一个具体场景不能替未确认的业务选择做决定。比如“软删除还是永久删除”会改变行为，必须在澄清阶段定；已经确认行为的例子属于 specify。

## 提问格式

一轮对应一个前沿。优先调用 Runtime 的 `visualize`（或等价的可视化 / 交互能力）把整轮问题渲染成**一个可批量提交的交互界面**：每题给出标题、必要背景、选项和推荐，用户可以在同一页勾选或填写，一次提交回答整轮。图形只是载体，不改变“决策归用户、推荐要有理由、接受自由回答和替代方案”。

若没有可用的可视化能力，或问题不适合图形化，退回文本格式：编号（跨轮次唯一）、写清背景与关键后果、给出推荐和理由，并在轮末给一次回复快捷方式。两种形式都要保证键盘可用、文本可复制，不因图形丢信息。

```markdown
### Q1. <要决定的事>

<一两句背景与关键后果>

<问题>

- **A.** <选项>
- **B.** <选项>

> **推荐：** <选项>——<理由>

---

**回复：** `1A, 2: <回答或替代方案>`
```

## 会话记录

每轮结束后，把确认项写入 DECISIONS，连同理由、可观察结果和未决项。沿用项目已有位置；没有明确要求或交接需要时，不新建文件、不新建状态系统。术语或长期决定可以交给领域建模处理，澄清本身不负责实现。

## 完成判据

- 需求层面的决定已经定下，前沿为空，没有静默假设。
- 实现细节和未决设计可以留给后续，不阻塞澄清结束。
- 向用户复述已定的结论与记录位置，确认双方理解一致后再交接。

## 停止与交接

需求够执行当前任务就停。未定事项只阻塞依赖它的部分，其余已授权工作照常继续。只要求澄清时，给出结论就停，不改代码。已经授权后续工作时，常规交接不必再次确认。
