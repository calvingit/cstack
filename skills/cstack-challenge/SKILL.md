# cstack-challenge · 对抗式审查

## 强制约束

- 对已成形的方案做有边界的对抗审查，不重新发散或重设计。
- 只报影响明确、可验证的问题；不为体现审查价值而制造异议。
- 默认只读；修改方案或实现需要授权。

## 产物

- **读**：当前结论、目标、约束、已接受前提、相关代码与证据。
- **写**：对抗审查报告（必须处理 / 建议考虑 / 可接受风险，附证据）。不是正式产物。
- 需要与其他 Skill 统一产物命名和字段时，调用 `cstack-core` Skill；未安装时以本节作为最小可用版本。

## 目标

找出会实质影响决策的薄弱点，不重新设计整套方案。

## 流程

1. 明确当前结论、目标、约束和已接受前提，不重新发散讨论。
2. 检查关键假设是否有证据，是否忽略了已有职责、现有机制或架构约束。
3. 重点查职责重叠、重复维护同一状态、运行时依赖、额外复杂度和迁移成本，并判断是否有更简单且满足目标的方案。
4. 提出问题前，先查现有机制和证据是否已经消除该风险。
5. 如果没有发现足以改变方案的问题，就保留当前方案。

## 独立升级

默认一次审查、一名 Reviewer。只有方案影响大、一次审查后仍有相互独立且证据不足的关键判断，或用户明确要求独立对抗审查时，才用 2–3 名独立 Reviewer：同一目标、约束、已确认事实和提案，互不看别人结论。结论一致只提高置信度，不替代证据；分歧按代码、需求、测试和可观察事实解决，不按票数裁定。

## 边界

不替代通用代码审查或技术调研；不把低概率、低影响的风险升级为阻塞项。默认只报告问题，不修改方案或实现。
