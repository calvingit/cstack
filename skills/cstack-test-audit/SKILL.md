# Test Audit - 审计测试

## 目标

判断指定的测试实际保护了哪些行为、可能遗漏什么，以及维护成本有没有依据。普通验收里核对相关断言，不需要先运行完整审计。

## 方法

1. 先确定范围，再读已经确认的行为、真实的调用路径，以及测试、断言、夹具、mock、快照和执行配置。需求依据不清楚时，就标为未知。不要凭测试内容推断业务是否正确。
2. 对每个重要疑点都要追问：预期是从哪里来的？测试实际跑的是哪条路径？返回值和必要的副作用都观察到了吗？哪些外部边界换成了替身？有没有跳过的检查、空断言，或者只对实现细节敏感的检查？
3. 用具体的回归案例说明测试能查出什么、查不出什么。名称相似、测试数量多少、覆盖率高低，本身都不是删除的依据。要提出合并或删除，得先说清这么做之后还能留下哪些独有的保护，反馈速度又如何。
4. 只对存疑的地方跑必要的检查。安全并且拿到授权时，才可以在隔离的副本里用负向控制或小范围变异验证敏感度。没有真正跑过的变异只能算假设，不能当作已观察到的结果报告。
5. 给出保留、改写、合并或移除的建议，并附上证据。只有请求里包含修复或清理时，才动手改测试。不得为了让测试变绿就放宽正确的期望，也不得顺带重写产品。

## 停止与交接

报告测试范围、能证实的发现及其位置、已有的保护或缺口、实际跑过的检查，以及有哪些限制。没发现问题，不等于所有业务验收都通过了。任务验收和变更审查，仍由各自的判断负责。
