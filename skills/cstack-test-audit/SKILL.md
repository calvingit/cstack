# Test Audit - 审计测试

## 底线（独立安装时自足）

- 只在有具体疑点时审计，不默认做全面测试审计。
- 审计测试有效性与维护价值，不把“覆盖率低”当缺陷。
- 默认只读；改测试需要明确范围与授权。
- 不替代 review 对本次改动的测试发现，也不替代 verify 的逐 AC 验收。

## 产物

- **读**：目标测试、被测代码、SPEC（`R#` / `AC#`）、项目验证方法。
- **写**：审计报告（测试是否断言可观察行为、是否可能虚假通过、维护成本、建议）。不修改正式槽位。
- 需要与其他 Skill 对齐槽位和字段时，调用 `cstack-core` Skill；未安装时以本节为最小自足版。

## 目标

判断指定测试实际保护了哪些行为、可能遗漏什么，以及维护成本有没有依据。普通验收里核对相关断言，不需要先运行完整审计。

## 审计什么

- 预期从哪里来、测试实际跑的是哪条路径、返回值和必要副作用有没有被观察。
- 是否可能在行为坏掉时仍通过：空断言、过度 mock、只测 shape、复制实现算法、快照掩盖真实变化。
- 是否只对实现细节敏感，而不是断言可观察行为；有没有跳过的检查或重复保护同一行为。
- 是否覆盖关键失败路径与风险分支；风险高的行为有没有足够保护。
- 维护成本：脆弱选择器、重复 fixture、测试专用生产接口、与实现强耦合。
- 每个结论给证据（文件、用例、断言），不凭测试数量或覆盖率下结论。

## 验证敏感度

只对存疑处跑必要检查。安全且有授权时，可在隔离副本里用负向控制或小范围变异验证敏感度；没有真正跑过的变异只能算假设，不能当作已观察到的结果。不得为了让测试变绿就放宽正确期望，也不得顺带重写产品。

## 停止与报告

按风险排序报告：有效保护、疑似虚假通过、维护成本问题，以及保留 / 改写 / 合并 / 移除的建议和证据。提出合并或删除时，先说清这样之后还留下哪些独有保护、反馈速度如何。修复或清理需要请求中明确授权；只读时只报告。没发现问题，不等于所有业务验收都通过了。
