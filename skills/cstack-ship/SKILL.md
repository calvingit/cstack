# Ship - 交付变更

## 目标

按当前候选、有效证据、项目门禁和用户授权，完成所请求的交付工作。准备、推送、创建 PR、入队、合并和部署是不同的动作，不要把一个阶段名或 Skill 名当作授权。

## 方法

1. 确定用户要求的结果、已经授权的动作和对象、目标分支/环境，以及候选和基线。再读仓库或平台的实际状态、未提交的改动、变更范围、项目规则，以及已有的验收和审查。保护他人的工作，只处理当前授权范围内的事。
2. 判断验收、审查、必需检查和审批有没有覆盖当前候选和相关基线。核对实际受测的对象和产物来源。状态显示绿色、跳过的检查，或者只是模型给出的意见，这些都不能自动当成业务验收。代码、测试、配置、环境、基线或要求有了相关变化之后，有依据才复用旧结果；不确定就补验，或者保留缺口。
3. 合并条件和运行条件要分开检查。运行条件只在需要发布时才涉及，包括部署配置、数据迁移、观测、验证和恢复。还要看合并会不会自动触发发布，以及触发之后有什么影响。合并的授权不能自动延伸到还没获准的生产副作用上。无法访问，或者查不清门禁，就说明这是未知。
4. 针对指定的候选、目标和观察时点，把技术就绪、授权范围、阻塞与剩余风险分开报告。接受风险必须有依据，也要有明确的接受者。FAIL 或 NOT VERIFIED 都不能改写成 PASS，项目里硬性的保护也不能绕过。
5. 用户要求并授权了某个动作、必要的门禁已经满足、相关副作用也在授权范围内，这三条同时成立，才用现有工具去执行。只请求真正缺失的决定或权限，已经授权过的不重复询问。创建 PR 或者推送，本身并不意味着可以合并或者可以部署。项目要求人工批准时，遵守这项要求。
6. 动作之前，重新读一遍能拿到的候选、目标和关键门禁。平台支持针对预期候选/版本的前置条件时，优先用它。不能保证条件在检查与执行之间不变，就说明这个限制。必要的安全前置条件满足不了，就停下来报告。状态变了之后，重新判断受影响的证据。
7. 实际结果要到平台或工具上核对：已准备、已推送、PR 已创建、已入队、已合并和已部署，这几种状态要分别报告。入队了还没合并，合并了也还没部署。失败、未知或者还在进行中的，都不能说成完成。

## 结果与停止

报告候选和目标、技术就绪、授权与副作用、实际执行结果、阻塞、证据，以及必要的恢复安排。只要求判断时，就停在判断这一步。要求交付，并且已经有相应授权时，继续做到请求的结果，或者做到具体的阻塞为止。没有真实动作或证据，就明确说明。
