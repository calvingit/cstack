# 交付变更

## 目标

根据当前候选、有效证据、项目门禁和用户授权完成所请求的交付工作。准备、推送、创建 PR、入队、合并与部署是不同动作；不要把一个阶段名或 Skill 名当作授权。

## 方法

1. 确定用户要求的结果、已授权动作与对象、目标分支/环境、候选和基线。读取实际仓库或平台状态、未提交改动、变更范围、项目规则及已有验收和审查。保护他人工作；只处理当前授权范围。
2. 判断验收、审查、必需检查和审批是否覆盖当前候选与相关基线。核对实际受测对象和产物来源，不把状态绿色、跳过的检查或模型意见自动当成业务验收。若代码、测试、配置、环境、基线或要求发生相关变化，有依据才复用旧结果；不确定时补验或保留缺口。
3. 分别检查合并条件和需要发布时的运行条件：部署配置、数据迁移、观测、验证和恢复。检查合并是否自动触发发布及其影响；合并许可不能自动扩展为未获准的生产副作用。缺少访问或不能查明门禁时说明未知。
4. 给指定候选、目标及观察时点分别报告技术就绪、授权范围、阻塞与剩余风险。风险接受须有依据和接受者；不把 FAIL 或 NOT VERIFIED 改写为 PASS，也不绕过项目硬性保护。
5. 用户要求并授权某动作、必要门禁满足且相关副作用在授权内时，使用现有工具执行；只请求真正缺失的决定或权限，不重复询问已获授权。创建 PR 或推送不自动意味着可合并或部署。项目要求人工批准时遵守。
6. 动作前重新读取可取得的候选、目标和关键门禁，优先使用平台支持的预期候选/版本前置条件。不能保证条件在检查与执行之间不变时说明限制；若必要的安全前置条件无法满足，则停下并报告。状态变化后重新判断受影响证据。
7. 从平台或工具核对实际结果：已准备、已推送、PR 已创建、排队、已合并和已部署分别报告。入队不等于合并，合并不等于部署；失败、未知或尚在进行不能称为完成。

## 结果与停止

报告候选与目标、技术就绪、授权与副作用、实际执行结果、阻塞、证据及必要恢复安排。只要求判断时停止在判断；要求交付且已有相应授权时继续到请求的结果或具体阻塞。没有真实动作或证据时明确说明。
