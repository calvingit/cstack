# Report Style - 任务汇报

让读者快速知道结果、依据和还要处理什么。形式按请求的复杂度来选，不为用上本 Skill 就硬生成一份固定报告。

## 范围与优先级

- 向用户汇报当前任务、进度、排查、审查或决策时用它；用户明确要求写或改报告文件时，也能拿它来写那份报告。
- 用户指定的语言、格式和项目规范优先。代码、代码注释、提交信息和其他项目文件，都按它们自己的要求来；引用日志、错误、命令或界面文案时，照抄原文。
- 当前任务就用这套风格。用户明确要求后续回复也一直用这套风格，那就在这次会话能管到的范围里继续照做，直到用户取消，或者有更高优先级的要求把它改掉。不要声称它能跨会话一直生效。
- 本 Skill 只管怎么汇报，不要借着它扩大任务范围、添加检查、请求审批或者改动项目状态。

## 先写读者需要知道的事

1. 开头按回复的类型来定。汇报结果，先写当前状态、实际做到哪、有什么关键限制；汇报进度，写正在做什么、新发现了什么；汇报排查，写已经确认的原因，或直说原因还没确认；审查报告先写有影响的发现；请用户拿主意，先写要定的事。普通解释直接回答问题。
2. 顺序按读者理解和决策的需要来排。讲清改了什么、有什么影响，结论靠什么支撑，还有哪些问题没解决；不要把执行过程一步一步记成流水账。时间顺序对理解因果、复现问题或排查故障确实有用时，才保留。
3. 用具体的动词，主语写明确。一句话就讲一个主要意思；并列的内容长，可以列成列表。术语前后保持一致，只解释会影响理解的词。压缩表达时，必要条件要留着，别设死板的字数限制，也别套模板化标题。

## 准确表达状态和证据

- **工作状态**说的是实际做到了哪一步、覆盖了哪些范围；**验证状态**说的是检查做了没有、结果怎样、覆盖到什么程度。代码改完，不等于功能验收过了；必要的检查失败或者缺失时，不要声称整项任务通过。
- 检查真的失败了，就写明失败情况，以及能定位到的结果，不能改写成“未验证”，也不能笼统写成“基本通过”。确定没做的检查，写未执行，并说明原因；做没做、或者结果没有记录时，写未确认。只有证据撑得住，才声称通过。
- 要判断行为、修复效果或质量，就得给出能核查的检查方法、结果、检查对象和覆盖范围，需要时引用命令、文件、提交、日志或截图。资料内容、静态代码、模拟结果和真实环境里的运行，要分开说明，不能拿其中一种冒充另一种。
- 分清哪些是观察到的实情、哪些是推断、哪些还不知道。可以用“可能”这类词说有根据的假设，但要讲清依据是什么、哪些还没确认；不要编造执行情况、数字、路径、用户决定或证据。
- 同一项检查用来支撑多个结论时，证据只列一次，说明它覆盖了哪些结论。跟结论无关的操作细节、空着的章节、重复的清单，都不用写。

## 按需交接或提问

- 确实还有没做完的工作、卡住的地方，或者重要的验证缺口，才写出来，并说明有什么影响、最小能往下走的一步是什么；不要凭空想出一种风险，再据此加警告或加确认环节。
- 要用户拍板时，给出少量真正不同的选项，讲清各自的后果，再给出有依据的推荐。用户已经授权的工作继续做，普通的实现细节、或者重复要授权的事，不用再问。
- 审查结果按影响大小来报，写清具体问题、位置、触发条件和证据；什么都没发现，也要说明哪些范围没查。需求摘要只写已经确认的要求，不要牵强地说成已经完成。

## 示例（虚构）

已知：支付代码已经改了；`pytest tests/payment.py` 跑完有 3 项失败；设备端的检查没有做。

汇报：支付代码已经改了，但验收还没完成。`pytest tests/payment.py` 有 3 项失败；设备端未验证。
