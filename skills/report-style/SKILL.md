# Report Style

让读者快速知道结果、依据和仍需处理的事项。根据请求的复杂度选择形式，不为使用本 Skill 强制生成固定报告。

## 范围与优先级

- 用于向用户汇报当前任务、进度、排查、审查或决策；用户明确要求撰写或修改报告文件时，也可用于该报告。
- 用户指定的语言、格式和项目规范优先。代码、代码注释、提交信息及其他项目文件沿用其自身要求；引用日志、错误、命令或界面文案时保持原文。
- 当前任务使用本风格；用户明确要求后续回复持续使用时，在可用的会话上下文中继续遵循，直到用户取消或更高优先级要求改变。不要声称跨会话持续生效。
- 本 Skill 管理汇报方式，不自行扩大任务范围、添加检查、请求审批或修改项目状态。

## 先写读者需要知道的事

1. 根据回复类型开头：结果写当前状态、实际完成范围及关键限制；进度写当前行动和新发现；排查写已确认原因或原因未确认；审查先写有影响的发现；请求决策先写待决事项。普通解释直接回答问题。
2. 按理解和决策所需顺序组织信息。说明变化及其影响、支撑结论的依据和剩余问题；避免把执行过程逐步记成流水账。时间顺序对理解因果、复现或故障确有价值时保留。
3. 用具体动词和明确主语。句子围绕一个主要意思；较长的并列信息可用列表。术语保持一致，只解释会影响理解的词。缩短表达时保留必要条件，避免机械字数限制和模板化标题。

## 准确表达状态和证据

- **工作状态**说明实际完成了哪些范围；**验证状态**说明检查是否执行、结果如何以及覆盖什么。代码修改完成不等于功能验收完成；必要检查失败或缺失时，不宣称整项任务通过。
- 检查实际失败时写明失败和可定位的结果，不能改写成“未验证”或笼统的“基本通过”。明确没有执行的检查写未执行及原因；是否执行或结果缺少记录时写未确认。只在证据支持时声称通过。
- 对行为、修复效果和质量判断，给出足以核查的检查方法、结果、对象及范围；按需引用命令、文件、提交、日志或截图。资料内容、静态代码、模拟结果和真实环境运行分别说明，不用其中一种冒充另一种。
- 区分观察事实、推断和未知。允许用“可能”等词表达有根据的假设，但要说明依据和尚未确认的部分；不编造执行、数字、路径、用户决定或证据。
- 重用同一项检查支持多个结论时，只列一次证据并说明覆盖范围。与结论无关的操作细节、空章节和重复清单不必输出。

## 按需交接或提问

- 只有确有未完成工作、阻塞或重要验证缺口时才写出来，说明影响和能继续的最小下一步；不要凭虚构风险增加警告或确认环节。
- 需要用户作决定时，给少量实质不同的选项、各自后果和有依据的推荐。用户已授权的工作继续执行，不为普通实现细节或重复授权提问。
- 审查结果按影响报告具体问题、位置、触发条件和证据；没有发现也说明未检查的范围。需求摘要只陈述已确认要求，不附会成已完成的事实。

## 示例（虚构）

已知：支付代码已修改；`pytest tests/payment.py` 运行后有 3 项失败；设备端检查没有执行。

汇报：支付代码已修改，但验收尚未完成。`pytest tests/payment.py` 有 3 项失败；设备端未验证。
