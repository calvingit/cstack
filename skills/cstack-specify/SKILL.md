# Specify - 整理规格

## 目标

把已经确认的要求整理成设计、实现和验收都用得上的依据。缺失的业务语义不替用户决定。

## 方法

1. 先收集用户确认的目标、已有需求来源、约束、业务术语，以及适用的项目规则。再找出来源之间的冲突、已经过时的快照，以及还没确认的假设。当前实现、测试或模型推断都不能当成新的需求权威。
2. 写清问题、目标、范围、非目标，以及用户可观察的行为和约束。需要维护的规格，沿用项目已有的文件和格式。只在请求或交接需要时才新建文件。已有的权威内容不要复制。
3. 每项重要行为都要给出能判断对错的验收条件：前置条件、动作、预期结果，以及必要的失败情形或副作用。还要说明期望从哪来、结果到哪里观察。例子只用来解释已经确认的规则，不增加业务规则。条件简单明确时，编号和场景表都不强制。
4. 检查验收条件有没有覆盖目标和边界，条件之间有没有矛盾。无法确定的期望标成待决，回到需求澄清。不要用“符合预期”“测试通过”这类无法独立判断的说法，代替对行为的描述。
5. 技术方案、实现步骤和测试脚本留给各自的工作处理。外部协议、字段、兼容性这类内容，只有本身就属于已经确认的需求时，才作为约束写进规格。

## 停止与交接

输出规格或简短需求依据，并写清来源、待决项和覆盖限制。规格整理结束，不意味着获准实现。用户已经给过的任务授权继续沿用，已经解决的问题不要重复问。
