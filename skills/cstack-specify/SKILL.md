# 整理规格

## 目标

将已确认要求变成可供设计、实现和验收共同使用的依据，不替用户决定缺失的业务语义。

## 方法

1. 收集用户确认的目标、已有需求来源、约束、业务术语和适用的项目规则。识别来源冲突、过时快照和未确认假设；不把当前实现、测试或模型推断作为新的需求权威。
2. 写清问题、目标、范围、非目标、用户可观察行为和约束。对需要维护的规格沿用项目已有文件与格式；只在请求或交接需要时创建文件，不复制已有权威内容。
3. 对每项重要行为给出可判断的验收条件：前置条件、动作、预期结果及必要的失败或副作用。说明期望来源与观察位置；例子只解释已确认规则，不增加业务规则。简单明确的条件不强制编号或场景表。
4. 检查验收是否覆盖目标和边界，条件之间是否矛盾。不能确定的期望写为待决并回到需求澄清；不要用“符合预期”“测试通过”等无法独立判断的表述代替行为。
5. 将技术方案、实现步骤和测试脚本留给各自的工作；只有外部协议、字段、兼容性等本身属于已确认需求时才作为约束写入。

## 停止与交接

输出规格或简短需求依据、来源、待决项和覆盖限制。规格整理结束不意味着获准实现；沿用用户已给的任务授权，避免重复询问已解决的问题。
