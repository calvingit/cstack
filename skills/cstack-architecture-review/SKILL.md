# Architecture Review - 审查现有架构

## 目标

判断指定范围内的现有结构是否满足项目约束，找出职责、依赖或生命周期上确实有实际影响的问题。先把当前的事实和代价说清楚，再谈方向。

## 方法

1. 先定审查范围、用户关心的质量目标和基线，再读项目的架构约束、关键入口和已有决策。文档只是线索，需要和当前的代码、配置核对。范围过大时，挑出高影响路径，并报告没有覆盖的部分。
2. 追踪实际责任时，从生产入口、代表性调用方、模块边界、数据与控制流、依赖注入和状态生命周期一路看下去。测试和配置能提供证据，但目录名称或抽象层的数量本身说明不了架构有问题。
3. 针对最强的疑点，检查它实际会造成什么影响，例如一处变更要同步改多处、错误语义在边界丢失、资源无法安全关闭，或持久数据的兼容性受损。再去找能推翻这个疑点的现有约束、保护和调用路径。不要把个人偏好包装成项目标准。
4. 每项发现都要说明位置、具体触发或维护场景、影响、支撑事实，以及还没查清的部分。能直接观察的事实和推断要分开。只有相关且适用时才引用官方技术指导，不强制某种架构风格。
5. 按影响和证据强度，把事项分成必须处理、值得考虑和可接受三类。给出方向，以及最小可验证的后续工作。没有足以改变决策的问题时，直接报告没有发现。

## 停止与交接

输出范围、当前结构、发现、反证和限制。架构审查默认只读，不代替具体变更的代码审查，也不自行设计或实施重构。用户另行要求方案或修复时，按已有授权继续。
