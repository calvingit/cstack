# 审查现有架构

## 目标

判断指定范围的现有结构是否满足项目约束，识别有实际影响的职责、依赖或生命周期问题。先解释当前事实和代价，再讨论方向。

## 方法

1. 确定审查范围、用户关心的质量目标和基线。读取项目的架构约束、关键入口和已有决策；文档是线索，需要与当前代码和配置核对。范围过大时选定高影响路径并报告未覆盖部分。
2. 顺着生产入口、代表性调用方、模块边界、数据与控制流、依赖注入和状态生命周期追踪实际责任。测试和配置能提供证据，但目录名称或抽象层数量本身不能证明架构问题。
3. 针对最强疑点检查其真实影响，例如变更需要同步多处、错误语义在边界丢失、资源无法安全关闭或持久数据兼容性受损。查找能推翻该疑点的现有约束、保护和调用路径；不把个人偏好包装成项目标准。
4. 给每项发现说明位置、具体触发或维护场景、影响、支撑事实及仍未知的部分。区分可直接观察的事实和推断；只有相关且适用时引用官方技术指导，不强制某种架构风格。
5. 按影响和证据强度区分必须处理、值得考虑与可接受事项。给出方向和最小可验证的后续工作；若没有足以改变决策的问题，直接报告没有发现。

## 停止与交接

输出范围、当前结构、发现、反证和限制。架构审查默认只读，不代替具体变更的代码审查，也不自行设计或实施重构；用户另行要求方案或修复时，按已有授权继续。
