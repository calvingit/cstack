# 图形化解释

围绕用户要理解的问题展示关键关系，让图形比纯文字更容易理解。可用于解释概念、现有代码、方案或变更；图形是解释工具，不能充当运行证据。

## 确定内容和依据

1. 明确受众、问题、需要呈现的关系及交付位置。遵守用户指定的格式；用户明确要求图形时，应交付可见的图形或图示，无法渲染时说明限制并提供当前环境可用的替代。
2. 解释当前项目时，读取相关源码、配置、调用路径和必要资料。解释变更或 PR 时，确认用户指定的候选与基线，检查实际 diff 和必要的周边代码；涉及工作树时包含相关未提交及未跟踪文件。访问不可用或范围不完整时明确说明，不猜测实现。
3. 区分已观察事实、推断、拟议方案和示意数据。每个重要节点、连接、条件和数值都要有来源，或明确标为示意。设计图和模拟交互不能证明真实系统运行；真实截图只能支持其对应时点的可见状态。

## 优先使用 Runtime 的可视化能力

1. 查看当前会话实际可用的 Skill 和工具，寻找宿主原生的 `visualize` 或等价可视化 Skill；以宿主注册的真实名称和能力为准，不假设所有 Runtime 都提供它，也不要把本 Skill 当作原生 `visualize`。
2. 用户需要**对话内**的图形或交互解释，且原生 `visualize` 适用于该请求时，优先通过宿主提供的 Skill 调用方式使用它；读取并遵守它的范围、工具、渲染和交付规则。只提到名称或生成相似文件，不等于已调用。调用不可用或失败时说明限制，选择下列退路。
3. 原生能力不适用时，按用户目标和当前环境选择可渲染的图示、表格或其他原生能力；流程、状态、依赖与数据流可用 Mermaid 等图示，精确字段对比可用表格。用户要求可复制的 PR Markdown 时，选目标平台支持的结构图、表格或 `diff`，不要依赖无法嵌入的对话组件。
4. 用户明确要求可下载 HTML 时，按宿主文件交付规则创建聚焦、可直接打开的单文件 HTML。需要交互探索而宿主没有可用原生可视化时，也可采用此方式。用户只要静态说明且未指定文件形式时，不因展示效果创建页面、安装依赖或新增适配层。

## 根据关系选择图形

- **顺序、分支或状态变化**：展示触发、关键路径和结果；避免把无关步骤串成一条长链。
- **模块、数据和依赖关系**：标明主要边界、方向和责任；复杂范围拆成几张小图，不靠缩小文字塞进一张图。
- **方案或状态对比**：让差异、共同条件及取舍可直接比较。数值图保留来源、单位与适当尺度，不编造指标。
- **变更说明 / PR**：用最少的视图展示变更前后、核心调用或数据结构，并点出会影响审查的兼容性、迁移或验证限制。只根据实际 diff 和来源描述；需要可复制的 PR 文案时，结合简短动机与结构概览。
- **交互探索**：仅在切换条件、参数或步骤能帮助理解时增加控件；交互结果基于明确规则，区分示意模型与真实系统。

按内容选择形式，不套固定页面模板。需要参考场景时读取 [表达示例](references/examples.md)。

## 质量与交付

- 优先沿用用户和项目的视觉约定；没有明确设定时使用中性色和少量语义色，避免默认绿色主题、蓝紫渐变、装饰性发光和重复大卡片。排版与色彩服务信息层级；用清晰标签、足够对比度及键盘可操作的控件，不只靠颜色表达含义。
- 给出简短结论和必要条件，不在正文重复图中全部内容。将相关源码、差异、文档或数据来源放在可核查的位置；信息缺失时标明未知。
- 检查图中的方向、标签、分支和内容是否与来源一致；检查能够查看的渲染、视口和实际交互。无法预览、执行或确认的部分明确写未验证；生成成功不证明所描述的软件已通过验收。
- 遵守用户和宿主的输出、文件保存与权限规则。只要求解释或草拟 PR 文案时保持只读，不创建、修改或发布 PR；用户另有明确授权时可在其范围内继续。
