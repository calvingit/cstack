# cstack-chinese-writing-style · 中文技术写作自然化

## 何时使用

- 中文技术文本读起来生硬拗口，带有明显的英文直译痕迹。
- 机器翻译的技术资料需要译后润色。
- API 文档、架构设计文档、用户手册、错误提示、PR 描述或提交信息需要改写。
- 文本反复出现“进行 XX 操作”“将被执行”“在 XX 方面”“对于 XX 来说”这类翻译腔句式。
- 句子短而碎，句间缺少承接，读起来像电报。
- 中文本身写得通顺，只需判断是否值得改：按审校模式处理。

## 核心原则

1. **准确优先**：不改变技术事实、前置条件、参数范围、例外场景和因果逻辑。
2. **先逻辑后句子**：先拆出前提、条件、动作、结果和例外，再按中文的叙述习惯重组信息。改的是信息结构，不是同义词替换。
3. **自然不等于口语化**：保持严谨、简洁、可检索，避免口语化或文学化表达。
4. **连贯优先于简短**：句子可以短，但不要堆叠互不衔接的短句。同一话题的相邻句子用逗号、分号、复句或指代自然接上，让人读起来是一段话，而不是一串口令。
5. **概念一致，词形适配**：同一概念全篇只用一种词形，具体译法按语境选择，不逐词对应。
6. **一致性让位于准确性**：统一用语是为了便于阅读，不是为了整齐。统一会改变技术事实时停在准确上，并在正文里说明为什么不统一。

## 工作流

### 1. 判断文本类型，按读者的任务组织信息

先确定文本属于哪一类，再按读者的核心目标排序，不要照搬原文语序。

- 操作文档、用户手册：读者要照着执行，按条件、动作、结果的顺序写。
- API 文档、开发者文档：读者要查参数和返回值，先写功能说明，再列参数、返回值与示例。
- 设计文档、技术方案：读者要理解逻辑与权衡，按层级展开，重点前置。
- 排错文档、错误信息：读者要定位并解决问题，按现象、原因、解决方法的顺序写。
- PR 描述、提交信息：读者要快速理解变更，核心信息前置，其余从简。

段落和句子各有各的分寸：一个段落只讲一个主题，长段落主动拆分；一个句子围绕一个主要动作，相关的条件、动作和结果用复句承接，合并与衔接的具体手法见“短句堆叠与句间衔接”。

### 2. 提取逻辑骨架

拆解每个长句或段落的核心要素：前提背景、限制条件、执行动作、产生结果、例外场景、原因与影响。先脱离原文，用中文母语逻辑复述一遍技术内容，再回查信息是否完整。

### 3. 分层自检

按六层顺序检查，改完一层再进下一层。各层对应的改写手法见下文“改写规则”。

1. **句法层**——被动句、条件句、介词结构、名词化结构、长定语、形式主语、范畴词。校验时问：被动句是否已转成主动句或受事主语句；条件句是否残留“后，且……才允许”一类句式；“对于……来说”“在……方面”这类介词框架是否还撑着句子。
2. **名词层**——补全中心词，消除语义悬空；英文名词在中文里没有对等词时换词。校验时问：删掉“该/此/其”“前者/后者”之后，句子还能不能独立读懂；某个名词是否只是把英文词形搬了过来。
3. **动词层**——删掉冗余的泛动词，让直接动词充当谓语。校验时问：是否还有“进行、开展、实现”与抽象动作名词的堆砌。
4. **语篇层**——一段一个主题，句子围绕主要动作展开，句间靠语义、指代和自然承接推进，既不靠连词堆砌，也不靠句号把一句话切碎。校验时问：连续短句是否读成了电报；拆句之后相邻句子是否仍有明确的话题和指代关系；连词是否机械照搬英文。
5. **术语层**——按核心原则 5 把同一概念收敛到一种词形。校验时问：同一对象是否换用了两种词形。
6. **格式层**——代码、命令、参数名、API 名称、错误码、协议名和标准号保留原文。校验时问：是否有标识符被翻译。

六层走完再通读全文，检查改写有没有引入同类问题，例如换掉“后者”之后，前半句仍在要求读者反推；同时确认技术事实、参数、条件和范围完整保留。

### 4. 输出

默认输出三部分：**改写版**（优化后的完整文本）、**关键改动**（逐条列出原文问题与对应改法）、**术语与风险**（术语的语境变体、易歧义点）。用户明确只要结果时，只输出改写版。

改到触发条件、行为约束或对外元数据（description、摘要、目录条目）时，要说明改了哪一处、是否与其他文件用词对齐、哪些结论来自检索而非实测。检索没有发现某类问题，不等于该类问题不存在，两者分开写。

## 审校模式

用户给的是中文原文，且只要求评估或润色时，不按翻译流程重做，按下面五步走。

1. 先判断文本类型与篇幅：短文逐句过；规范、Skill、README 一类长文先通读，再把问题标成“必须改”“可改可不改”“不必改”三档。
2. 把问题分成两类：**硬问题**包括语义偏差、概念不统一、指代悬空、搭配不通和约束被弱化；**软问题**包括可读性、节奏、短句堆叠和句间断裂。软问题不当作错误上报。
3. 结论先行：先说是否需要改、改动量级有多大，再逐条给依据。用户没问的文件不擅自改动，范围外的问题单独列出。
4. 检查正文与元数据（description、标题、摘要、目录条目）的用词是否一致；不一致时以正文语义为准，并向批次口径对齐。
5. 批量文档（一批 Skill、一组错误文案、一套错误码）中，单个文件向全批次风格靠拢，不自行改变人称、语气或术语。

## 统一之前先验证

术语统一和写法统一都建立在“两处说的是同一件事”这个前提上，前提不成立时，统一本身就是改错。替换前逐项确认：替换后的事实、数值、取值范围和命令行为是否仍然成立。拿不准就先实测，不要凭形式相像下判断。

形式相近而语义不同的写法最容易在这一步改错，例如 `git diff A..B` 与 `git diff A...B`、`--force` 与 `--force-with-lease`、`-f` 与 `-F`：两个写法各自成立，统一到任一方向都会改变实际行为。确认两种写法都要保留时，在正文里写明区别与适用场景，不要让读者当成笔误。三组的具体差别见 [examples.md](references/examples.md)。

## 改写规则

### 条件句与被动语态

英文的条件句常写成 *After A, and if B, C is allowed*，被动语态也用得比中文密。条件句按中文语序重排，只有满足全部条件才谈得上执行动作：

- 只有满足 A 且 B，才能执行 C。
- 完成 A 并满足 B 后，方可执行 C。
- 执行 C 前需同时满足两个条件：A、B。

避免“……后，且……才允许”“当……并且如果……则……”这类叠加句式。

被动句尽量转成主动句或受事主语句。“配置文件在系统启动时被自动加载”改成“系统启动时自动加载配置文件”；“所有请求都会被网关模块进行校验”改成“网关模块校验所有请求”，或保留受事主语写成“所有请求均由网关模块校验”。

### 名词化结构

英文常用 *perform validation*、*make an optimization* 这种“动词加动作名词”的组合，中文优先让动词直接作谓语：“对集群进行扩容操作”改成“扩容集群”，“实现数据的实时同步”改成“实时同步数据”。

“进行校验”“提供支持”这类搭配不必一律禁止，但不要无意义地堆叠。判断按结构走，不要只检索固定搭配：凡是“抽象动作名词加泛动词”都可能冗余，去掉泛动词能还原成直接动词的就改写。“已授权的工作继续进行”改成“已授权的工作照常继续”，“问题得到解决后再推进后续工作”改成“问题解决后继续推进”。只查“进行校验”“进行确认”会漏掉“工作继续进行”“流程得到执行”这类同源变体。

### 长定语与并列清单

英文的后置修饰成分多，直译会形成“XX 的 XX 的 XX”这样的长串定语，应当拆成短句、并列成分或复句：“一个用于在超时后自动重试请求的配置项”改成“该配置项用于超时后自动重试请求”。

并列清单不要塞进“的”字定语，尤其以“等”收尾的清单：读者读到“等”会以为句子结束，中心词因此失去着落。“处理会影响兼容性、权限、验收等的配置”应改成“处理可能影响兼容性、权限或验收的配置项”。清单较长时用冒号引出，再用分句说明影响范围：

> 找出会改变结果的未决选择：可能影响用户可见行为、业务规则、兼容性、权限、验收或交付范围。

拆分之后要回看句间衔接。如果连续出现几个互不相连的短句，就合成复句，或者补出主语和指代关系。更多译前译后对照见 [examples.md](references/examples.md)。

### 短句堆叠与句间衔接

短句本身不是问题，连续堆叠才是；清单和步骤可以逐条写，这一节说的是成段叙述。判断标准不是句子长短，而是相邻句子之间有没有语义承接。

- 同一话题的条件、动作和结果能合成复句就合成，不要一句一个句号。
- 连续几句都省略主语、都只有十来个字，或每句都用“该/本/此”开头，通常就是堆叠。
- 该用逗号、分号、冒号的地方正常使用，不要为了显得简洁把一句完整的话切成几段。
- 合并之后仍要围绕一个主要动作，不要把多个动作硬塞进一个长句。

同一段接口说明的两种写法，差别在于句间是否承接：

> 堆叠：这个接口需要登录。默认返回 30 条记录。支持分页。分页参数优先。没有数据时返回空列表。
>
> 连贯：该接口要求登录后调用，默认返回 30 条记录并支持分页；用户传入分页参数时，以该参数为准。没有数据时返回空列表。

改完朗读一遍。停顿明显多于正常说话的节奏，或每句都要重新建立主语，说明句号太密，应当回头合并。

### 补全中心词与换词

英文可以依托上下文省略中心词，中文往往需要补全：“当前候选”写成“当前候选变更”或“当前合并候选”，“该配置”写成“该配置项”或“该配置规则”，“此实现”写成“此实现方案”或“此实现逻辑”。

补中心词不等于逐处补主语。行为约束和规范条款多用无人称句，主语缺失往往不构成歧义，“技术细节在现有约束内自行判断”不必改；只有需要明确责任人才补，写成“业务选择由用户决定，技术细节在现有约束内自行决定”。同一批文档统一用无人称写法时，个别段落突然出现“由 X 执行”，反而造成归属不一致。

补全中心词解决的是词不完整，另有一类情况是中文里根本没有这个名词。英文技术写作习惯把动词压成名词，findings、takeaways、insights、action items 都属于这一类，对应的中文往往只有动词形式，直接当名词用会语义悬空。判断办法是把词单独拎出来读，读者若还要追问“什么的？”，说明它站不住：findings 译为问题、评审意见或结论；takeaways 译为要点或结论；insights 译为判断或结论；action items 译为待办事项或后续工作。

两种情况可以保留原词：一是该名词在中文里已经立住，像“附带发现”“研究发现”这类动宾结构作名词本来就是自然的中文；二是该词已被当作固定术语反复引用，例如章节名、字段名或 API 约定，改动成本大于收益时保留，但全篇要统一到底。

### 指代与连接词

避免“该/此/其”连续密集出现，适当重复名词比模糊指代更清晰，“该服务”“此参数”这样的写法让读者不必回翻上文。连词也不必机械对应 and/or/if/when/while，靠语序和自然承接体现逻辑即可，不必句句都加“并且、因此、然而”。

## 口语词替换表

“避免口语化”需要可判断的依据。规范、Skill、README 这类会被反复引用的文本，下列写法读起来随意，换成对应的书面说法：

| 口语写法 | 书面说法 |
| --- | --- |
| 出错、出问题 | 失败、异常 |
| 走过场 | 必须实际执行 |
| 挑一遍毛病 | 自查一遍 |
| 两个概念别搞混 | 两者不可混用 |
| 靠它落地 | 要靠它落实 |
| 卡在工具上 | 因工具不可用而中断 |
| 最容易出事的规则 | 最易出错的规则 |

口语化不等于不自然。判断标准是这份文本会被反复引用、当作规范执行，还是只作一次性说明：前者按上表收紧，后者可以放松。依赖具体上下文的单例改写见 [examples.md](references/examples.md)。

## 术语规则

1. 概念一致按核心原则 5、原则 6 执行。“期望/预期”“适当/相应”这类混用会让读者当成两个对象；本义是“意见不合”的词（分歧、争议、冲突）不要用来指“尚未决定”，后者写成“未决选择”或“未确认项”。
2. 通用技术词按国内技术圈的习惯适配：solution 译为方案，不必次次写成“解决方案”；feature 译为功能，不必全部写成“特性”；deploy 译为部署或上线，不必写成“进行部署操作”；gate 译为门禁或准入检查；candidate 按语境译为候选变更、合并候选或发布候选。
3. 代码标识符、命令、参数名、API 名称、错误码、协议名和标准号一律保留原文。
4. 首次出现的陌生术语可以保留英文括号标注，后文统一使用中文译法。
5. AI 生成的中文偏好给概念起隐喻性的名字，并反复使用同一批词，例如“槽位”（slot 直译，离开硬件、对话系统这些既有语境就显得生硬）、“底线”“红线”（靠比喻表达“不可违反”）、“硬约束”。遇到这类词先问一句：用中文已有的词根能不能直接说清？能就换掉并全篇统一，“硬约束”可以写成“强制约束”；确需保留的抽象名词，首次出现时用一句话定义，不要让读者靠隐喻自行领会。判断标准是词根是否自然，不是禁用一切抽象名词。

## 禁止

以下三条属于高代价失误，出现即判定不合格。

- 不得为语言流畅删减关键技术信息。
- 不得把“没有发现某类问题”表述成“不存在该类问题”；检索范围和实测范围分开说明。
- 不得把风格偏好当成语言错误，也不得为求顺口弱化规范、约束或验收条款的强度。
