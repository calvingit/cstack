# cstack-simplify · 简化代码

## 目标

减少当前代码里仍在维护、却已无必要的概念、状态、路径或重复，同时保持已确认的行为与兼容性。

简化有两种范围。局部范围是某段代码本身。功能范围是某个功能加进来的改动集：这类改动常常贴着原有结构另加一层，把功能并回已有设计同样是简化，只是范围以那处功能为界。

## 角色

本 Skill 执行 **Simplifier** 角色。`cstack-core` 的 `ROLES.md` 把 Simplifier 定义为只读判断，那是审查模式的契约；用户在审查模式之外明确要求并授权简化时，改动部分按授权执行，角色边界不因此扩大。收尾可以跳过本 Skill；未运行记为跳过，不视为失败，也不能代替 `cstack-verify` 或 `cstack-review`。

## 强制约束

- 保持已确认的行为、兼容性和相关工作不变；减少行数本身不是目标。
- 单凭相似代码、短文件或风格偏好，不足以证明可以删除。
- 搜索没结果不能证明没人用；动态调用、外部使用或历史数据核对不了时，先保留并说明。
- 只读或按授权修改，不扩大范围。
- 简化后概念、分支和抽象层只应更少或持平，不应更多。改完比改前更复杂，就不是简化。
- 尽量不动原有逻辑。原有代码能承担这个功能时，把功能并进去，不要顺手重排结构。
- 默认只改代码结构，不改可观察行为。确实要改行为，先回到 `cstack-specify` 或用户确认，再按新契约执行；不在本 Skill 里自行决定。

## 两个模式

本 Skill 有两条路径，进入时先分清走哪条；用户点明模式时按点明的走。

| 模式 | 何时进入 | 能改代码吗 | 产出 |
| --- | --- | --- | --- |
| **审查模式** | 收尾时判断候选里有没有可移除的复杂度；由 `cstack-implement`、`cstack-orchestrate` 或上层审查派发 | 不能，只读 | 简化候选清单或 `no_change` |
| **修改模式** | 用户明确要求简化指定代码，并授权改动 | 可以，限授权范围 | 实际改动 + 检查记录 |

判不准时按审查模式做：给出候选和理由，让有权方决定要不要改。审查模式不产出改动，所以它可以由只读实例承担，也可以和 Verifier、Reviewer 并行。

被自动选中时只走审查模式：只给候选，不动代码。修改模式要用户明确要求并授权改动，没拿到授权就没有写入权限。

功能范围的简化只用于功能。缺陷修复保持最小改动，交给 `cstack-diagnose` 与 `cstack-implement`。

## 产物

- **读**：目标与基线、实际调用方、边界、配置、序列化格式、持久数据、测试。功能范围另读功能 diff、这段代码的历史和现有运行数据。
- **写**：审查模式写简化候选清单或 `no_change`；修改模式写实际改动与检查记录，功能范围另写建议的提交信息。两者都不是正式产物。
- 需要与其他 Skill 统一产物命名、字段或共享判据时，读取 `cstack-core` 的 `ARTIFACTS.md`、`PRINCIPLES.md`、`CRITERIA.md` 对应小节；未安装时以本节作为最小可用版本。

## 简化候选类型

- 已不承担责任的包装或透传。
- 重复的状态、重复的保护。
- 过期的兼容路径或死代码。
- 只为测试方便而加进生产代码的复杂度。

本 Skill 是可移除复杂度的唯一归属：`cstack-review`、`cstack-test-audit`、`cstack-codebase-design` 或 `cstack-challenge` 发现后转入这里判断价值、授权和改动；其他 Skill 不重复给简化方案。`cstack-second-pass` 从变更前基线重写时自带一次减复杂度，重写后残留的可删复杂度仍回到这里判断。

## 候选判断

说明三点：它现在承担什么责任；删掉或合并后这份责任怎么保住；预期减少哪些维护成本。判断不了就先保留，并说明哪里不清楚。

## 审查模式

只看不改，结论是候选清单，不是改动。

- 范围是**本次候选的改动集**及与之直接相关的路径，不顺手审无关代码；候选与基线都写清楚。
- 每条候选按「候选判断」的三点说明，并标注位置（文件与行，或符号名）。
- 只报**本次引入或加重**的复杂度。既有代码里本来就在的多余结构记为后续项，不算本次问题。
- 核对不了的（动态调用、外部使用、历史数据）记为保留并说明缺口，不写成候选。
- 没有安全且有价值的候选就输出 `no_change`；这本身就是有效结果，不为了有产出而凑候选。
- 不写 `EVIDENCE`，不改产品代码、测试或需求。产出交回调用方，由它决定进修复队列还是记为后续项。

## 修改模式

获得授权后，做范围内最小的完整改动；公共行为不能变，用户确认过的兼容要求要满足。运行相称的检查，再查有没有残留引用，并核对实际 diff。

范围是一段代码时，按「候选判断」逐项处理，以删除和合并为主。

范围是一个功能的改动集时，多做下面三步，因为这类复杂度不在某一处，而在「功能怎么接进原有结构」上：

1. **读出功能都加了什么**。`git diff <base>...HEAD`，`<base>` 是这个 PR/MR 的目标分支（例如 GitHub PR 用 `gh pr view --json baseRefName -q .baseRefName` 取）或用户指定的提交范围。分支比较用 merge base，工作树包含暂存、未暂存和相关未跟踪文件，与 `cstack-review` 同一口径。列出每一块新增或改动的分支、开关、常量、文件、测试。
2. **弄清原设计**。对每个被触碰的地方，比调用点再往下看一两层；读类型、调用方和历史（`git log -p`），直到能说清这段代码为什么是现在这样。查设计原因用 `cstack-why`。有运行数据（日志、错误追踪、分析、数据库记录）时先核对哪些路径和情况真的发生；只读，不提交。
3. **并回原设计**。问：原有代码里，哪一处本来就该承担这个功能？把功能接到那里：泛化那个类型或联合、加进已有的分派点、复用共享的校验与下载路径，然后删掉为它另加的那一层。原有逻辑能原样不动就不动；不得不改时，改到刚好容得下这个功能为止。

判断标准是改完之后的净效果：概念、分支、抽象层比功能刚加进来时更少，或至少持平。要达成这个结果只能靠新造一层时，说明并错了地方，回头重新判断归属。

功能范围常见的可删结构，都是「少动原有代码」的产物：

- 把已有的值重新推导一次的别名，例如 `getContentType()` 已经返回名词时，又写 `const noun = isVideo ? 'video' : 'image'`。
- 在已经按 kind 分派的地方散落 `if (newKind)` 分支。
- 为一个变体复制一个已有的文件或组件。
- 与类型已经表达过的信息重复的新 `options`、开关或布尔值。
- 在共享的校验或下载路径旁边再写一条。
- 只为证明「其他部分没变」的测试。
- 同一件事已经有一套实现时再建第二套，例如在已有的费用统计、计数器、日志、重试封装或配置读取器旁边再写一个。把它并进已有实现，不够用就扩展那个，再删掉重复的。

这几条都是按「候选判断」处理：说明它现在承担什么责任、并回哪里后这份责任怎样保住、预期减少哪些维护成本。识别到但判断不了价值的，留在候选清单里，不直接删。

## 边界

- 不新造抽象层，只调整已有的。
- 保留真正不同的行为：`<video>` 与 `<img>` 是不同行为，重复的状态机不是。
- 功能范围改完后，行为要和功能做完时一致；确实要改行为，先回到需求侧确认，再按行为变更处理。
- 功能范围的改动与功能本身的提交分开，按仓库的提交约定写建议的提交信息：行为未变用 `refactor`，行为变了用 `feat`。提交、推送和建 PR 属于交付动作，由 `cstack-ship` 判断与执行，本 Skill 不自行执行。

## 报告与停止

- 报告确认了哪些简化或候选、哪些保留及为什么、实际检查了什么、还有哪些限制；审查模式另报候选的所属位置，修改模式另报实际 diff 与检查结果。
- 功能范围另报：范围与基线、复杂度并回了哪里、删掉了哪些为功能另加的结构、删掉的测试保护的行为现在由谁断言、残留检查结果、行为是否改变、建议的提交信息。
- 没有安全且有价值的候选，本身就是有效结果。
- 新发现的需求变化、架构改造或无关清理，都不要自行扩大范围。
