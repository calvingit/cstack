# cstack-second-pass · 第二遍重写

## 目标

第一遍实现已经能运行，接下来不是继续修补，而是带着这一遍学到的约束、死路和临时做法，从变更前基线重写一个更简洁的版本，同时保持已确认的行为与范围不变。

第一遍能运行只说明工作状态，不等于已经验收通过。

## 强制约束

- 行为依据来自已确认的 `AC#`、`DECISIONS` 或会话确认；只在第一遍的代码和测试里成立时，先运行 `cstack-verify` 建立基线，不开始重写。
- 重写前先提交、打标签或留在独立分支上，让第一遍随时可以恢复；恢复不了就不开始重写。
- 在新分支上从变更前基线重写，不在第一遍的实现上打补丁。
- 保持已确认的行为、接口和兼容性；不新增功能，不扩大范围。
- 更简洁指更少的概念、重复和抽象层，不是更少的行数。
- 工作状态和验证状态分开写；未运行不等于通过。
- `git reset --hard`、`git push --force`、删除第一遍所在分支，需先取得用户授权。

## 角色

重写由 **Implementer** 执行，减复杂度由 **Simplifier** 判断，两者可以在同一上下文完成，报告标明执行者。重写本身自带一次减复杂度；写完后残留的可删复杂度仍交回 `cstack-simplify`。

## 产物

- **读**：行为依据（`AC#` / `DECISIONS` / 会话确认）、变更前基线、第一遍的测试。
- **写**：两个候选和比较报告，写明候选标识与执行者。不写 `EVIDENCE`，不改上游产物。
- 需要与其他 Skill 统一产物命名、字段或判据时，读取 `cstack-core` 的 `ARTIFACTS.md`、`PRINCIPLES.md`、`CRITERIA.md` 对应小节；未安装时以本节作为最小可用版本。

## 重写步骤

1. **写下「第一遍学到什么」**。篇幅不用长，只记四件事：真实约束、走过的死路、临时辅助、定义行为的测试。
2. **保住第一遍**。记下可恢复的引用（分支、提交或标签）。笔记留在对话里，或跟第一遍一起提交，换到基线分支后仍然拿得到。
3. **从变更前基线重写**。新分支从变更前基线起步，输入只有那份笔记、行为依据和测试，第一遍的结构不搬过来；临时辅助、重复逻辑和多余的抽象层一并去掉。
4. **两边运行同一组测试，再用 `git diff` 比较**。对照基线看两个版本各自的变更面，再按下面「比较口径」逐项比较，命令和输出都记下来。
5. **推荐一个版本**。理由和风险写进报告；第二遍没有明显更简洁时，保留第一遍。

## 比较口径

- 概念指需要单独维护的东西：类型、状态、路径、配置项；抽象层单独数，局部变量和测试辅助函数不计数。
- 每个数字附对应清单（文件或 `file:line`），不报总数；两个版本用同一口径数。
- 数不出差异或口径统一不了时写「不可比」并说明原因，不拿印象补结论。

## 报告与停止

用下面的模板写一份短报告：

```markdown

## 行为依据
- 来源：
- 覆盖的行为：

## 第一遍学到什么

## 两个版本
- 第一遍：
- 第二遍：

## 测试
- 第一遍：
- 第二遍：

## 比较
- 变更面：
- 新概念：
- 重复逻辑：
- 抽象层：
- 不可比项：

## 推荐
- 版本：
- 理由：
- 风险：

## 验证状态
- 测试：
- 验收与审查：
```

两个版本都要写明分支、提交或标签，以及工作树是否有未提交改动；测试没运行就写未运行，不写成通过。第二遍没有明显更简洁时，推荐第一遍并写明原因。

推荐不等于验收通过：第二遍是新候选，第一遍的验收结论不能平移，交付前重新运行 `cstack-verify` 和 `cstack-review`。

报告写完即停止：不合并、不删除分支、不交付。
