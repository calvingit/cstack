# cstack-second-pass · 第二遍重写

## 目标

第一遍实现已经能运行，但实现过程可能留下临时结构、错误假设或探索性折中。第二遍从**同一个变更前基线**重新实现，利用第一遍发现的事实，形成一个独立候选，再判断它是否比第一遍更值得保留。

本 Skill 评估的是两个实现候选，不负责证明需求已经验收通过。第一遍能运行、两遍测试结果相同、第二遍代码更短，都不能单独证明第二遍更好。

## 进入条件

开始前确认：

- 第一遍已经形成可识别的候选，能够运行目标功能或执行相关检查。
- 已确认的行为依据可取得：`SPEC` 的 `R#` / `AC#`、`DECISIONS`，或用户在当前会话确认的行为与接口约束。
- 能确定第一遍之前的基线提交，以及第一遍候选的可恢复状态。

缺少行为依据时，先交回 `cstack-clarify` / `cstack-specify` 或用户确认；不能从第一遍代码、测试或说明中反推需求。基线或第一遍状态无法可靠恢复时，不开始重写。

## 强制约束

- **候选 A 必须可恢复**：记录基线提交、第一遍候选提交或快照、分支、工作树状态。快照必须覆盖暂存、未暂存和未跟踪文件；只有分支指针不能保护未提交改动。
- **候选 B 必须从同一个基线开始**：使用独立分支，优先使用独立 worktree；不得在候选 A 上打补丁、复制其结构或 cherry-pick 其实现。
- **优先隔离上下文**：第二遍 Implementer 优先使用新的 Agent 实例或会话。模型可以相同，关键是实现者在设计和编码阶段没有看到候选 A 的代码、diff 或设计过程。无法隔离时可以降级执行，但必须标明上下文污染，不能称为净室（clean-room）重写。
- **交接知识，不交接方案**：第一遍只提供经核实的约束、观察到的边界、失败尝试和未决问题；不提供第一遍的架构结论、代码片段或“照此实现”的指令。
- **契约优先**：已确认的行为和兼容性是判断依据。候选 A 只是比较对象，不是正确性标准；第一遍测试也不是天然可信的行为契约。
- **行为变化必须有授权**：不增加功能、不扩大范围、不擅自改变接口、持久化格式或兼容性。发现行为契约冲突时停止并交回有权决定的人。
- **比较必须可复核**：两个候选使用同一组适用的检查，并记录候选标识、环境、命令和结果。条件不可比时明确写出，不用印象补齐。
- **不以代码行数或评分决定优劣**：复杂度、可理解性和维护成本要落实到具体结构与代码路径；不生成没有依据的综合分数。
- `git reset --hard`、`git push --force`、删除候选 A 或 B 的分支，以及清理其 worktree，均需用户明确授权。

## 角色

- **Implementer**：从基线实现候选 B，负责自检，不写 `EVIDENCE`。
- **Simplifier**：只读比较候选 A 与 B，判断复杂度和维护成本的差异。可以由同一上下文承担；当候选影响面大、风险高或比较结论有争议时，优先派独立实例。
- 隔离第二遍 Implementer 与第一遍实现者的上下文，比更换模型更重要。Runtime 不支持独立实例时，按角色顺序在同一上下文执行并标明限制；若任务要求严格隔离，则暂停并请求可用的独立上下文。第二遍从基线重写本身即是一次整体简化；候选 B 中残留的可移除复杂度仍交给 `cstack-simplify` 判断。

## 产物

- **读**：已确认的行为依据、变更前基线、候选 A 的可恢复引用、项目约定、基线测试，以及第一遍的 Learning Handoff（由第二遍 Implementer 读取）。
- **写**：Learning Handoff（由了解候选 A 的上下文整理）、必要时的简短 Design Sketch、候选 A/B 标识和比较报告。记录可留在会话或任务工作区，不建立新的权威需求或技术决策。
- **不写**：`EVIDENCE`，不修改 `SPEC` / `DECISIONS` / `TECH`，不把比较结论写成验收结论。
- 比较方法与判据见 [references/comparison.md](references/comparison.md)。只在需要选择测试方法或判断候选差异时读取。

## 执行步骤

### 1. 固定候选 A 与基线

记录：

- `BASE`：第一遍开始前的准确提交 SHA。使用实际分支关系或 merge base 确定，不猜测为 `HEAD~1`。
- `A`：第一遍候选的提交 SHA、分支或可恢复快照。
- 工作树：暂存、未暂存和未跟踪文件是否存在，以及它们如何被保存。
- 环境：运行候选 A 所需的关键版本、配置、数据和服务。

确认 A 可恢复后，再创建从 `BASE` 开始的候选 B 分支和独立工作区。若 A 的状态包含未提交改动，先保存并验证恢复方式；不能安全保存就停止。

### 2. 确认行为契约与比较范围

整理本次重写必须保持的行为、接口、兼容性和明确排除项，并引用 `R#` / `AC#` / `C#` 或会话确认来源。

区分：

- **已确认行为**：必须保持，或按已批准的变更调整。
- **观察到的行为**：第一遍或现有系统中实际观察到，但尚未确认是否属于行为契约。
- **未知项**：无法判断是否允许变化；可能影响范围时先交回确认。

没有明确的行为依据时，不开始净室重写。候选 A 或其测试不能填补行为契约缺口。

### 3. 提取第一遍经验

由了解候选 A 的上下文整理一份简短的 Learning Handoff。只写可帮助第二遍避开已知死路的事实：

- **约束**：仓库、平台、外部 API、数据或兼容性限制，附来源。
- **边界情况**：实际发现的输入、状态、时序或失败路径，附测试或观察依据。
- **失败尝试**：尝试了什么、观察到什么失败、证据在哪里。
- **临时措施**：为排查或快速实现加入的辅助、开关或绕行路径，说明当时原因。
- **未知项**：尚未验证的假设，以及它影响什么判断。

每条标为 `Fact`、`Inference` 或 `Unknown`。不复制第一遍代码、架构图、设计结论或完整推理过程；无法证明的内容不能包装成事实。

### 4. 在独立上下文重建设计

第二遍 Implementer 读取：

- 已确认的行为契约；
- `BASE` 上的代码和项目约定；
- Learning Handoff；
- 基线已有测试，以及独立于候选 A 的验证入口。

在开始编码前，先简要回答：

1. 核心数据、领域概念和状态是什么？
2. 哪些现有模块应承担主要职责？
3. 主数据流、控制流和关键边界在哪里？
4. 哪些约束决定了实现方式？
5. 相比直接照搬常见模式，最简单且完整的实现是什么？

对较复杂的改动写一份简短 Design Sketch，说明职责、关键路径和主要取舍；简单改动可以跳过并说明原因。不要在这里重做 PRD / HLD，也不要为了展示设计而增加抽象。

### 5. 从 BASE 实现候选 B

- 在独立分支或 worktree 中从准确的 `BASE` 开始。
- 只依据行为契约、项目事实和 Learning Handoff 实现。
- 不读取候选 A 的源代码、diff 或设计说明；候选 B 完成前不解除这条信息隔离。
- 优先复用基线已有的类型、模块、边界和项目惯例。
- 保持相同的外部行为与范围；不为追求“更简洁”而牺牲错误处理、资源生命周期、安全性或可读性。
- 记录实现者自检和未解决问题，不写验收通过结论。

### 6. 比较两个候选

候选 B 完成后，才允许比较者读取 A 和 B。先确认两个候选都指向准确的 `BASE`，再按 [比较指南](references/comparison.md) 选择适用的方法：

1. 对 A、B 运行同一组适用测试和检查，使用可比环境。
2. 对确定性且适合黑盒比较的行为，使用相同输入进行 Differential Testing；有价值时再使用 Property-based Testing。
3. 对照行为契约分类行为差异，不把 A 当作 oracle。
4. 比较概念、结构、可理解性、修改局部性、错误处理和项目适配；只比较本次改动相关且有证据的维度。
5. 对较大改动，可用一个来自真实需求或已知变化方向的 Maintenance Probe，观察两个候选实现同一变化时需要触及的模块和规则；不实现这个假设需求。

如果测试条件、数据或环境无法对齐，标记 `不可比` 并说明原因。不要为获得“第二遍胜出”的结论而补造测试、指标或候选优势。

### 7. 作出推荐并停止

只有在以下条件同时成立时，才推荐 B：

- 没有未经批准的行为、接口或兼容性差异；
- 适用的共同测试和检查没有显示 B 的回归；
- B 在至少一个重要维护维度上有具体、可复核的优势；
- 没有引入同等或更大的复杂度、风险或运行成本。

否则保留 A，或给出“证据不足，暂不推荐”的结论。A 和 B 都不满足行为契约时，报告问题并交回实现或需求环节，不把两者中相对较好的一方包装成合格候选。

报告完成即停止：不合并、不删除分支、不交付。用户选定候选后，按当前候选重新运行 `cstack-verify` 和 `cstack-review`；本 Skill 的比较、差异测试和实现者自检均不能替代它们。
