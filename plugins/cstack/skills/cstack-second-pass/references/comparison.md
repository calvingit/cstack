# 第二遍重写：比较指南

本文件供 `cstack-second-pass` 在选择测试方法、解释行为差异和比较候选时按需读取。它提供方法选择，不要求每个任务都执行所有技术。

## 1. 先建立可比条件

A、B 的比较至少记录：

- 基线提交和候选提交；
- 运行时 / 平台 / 构建模式；
- 关键配置、fixture 和数据集；
- 测试工具与版本；
- 实际执行的命令和结果。

依赖版本由各候选自己的锁文件决定；若依赖差异会影响行为或性能，单独记录，不要声称环境完全相同。性能数据只有在负载、设备、构建模式、数据规模和测量方法一致时才可比较。条件不一致就重测或标记 `不可比`。

## 2. 选择共同测试集

优先顺序：

1. **基线已有测试**：确认没有被候选改写成只适配某一种实现。
2. **契约测试**：从已确认的 `AC#`、接口约束和失败条件中选取，断言可观察行为。
3. **第一遍新增测试**：只作为边界情况线索。检查它是否对应已确认行为、是否断言外部结果、是否复制实现算法；不满足条件的测试不能作为行为 oracle。
4. **项目已有专项检查**：例如类型检查、静态检查、平台构建或集成测试，按本次变更的影响范围选择。

A、B 使用同一组适用测试。若测试只能在某个候选内运行，说明限制；不要静默比较不同测试集。测试断言应保护行为，不应锁定内部类型、私有调用顺序或某一实现算法。

共同测试未通过时，分别记录 A 和 B 的结果。候选 A 的既有失败不能自动算作 B 的回归；候选 B 通过 A 也失败的测试，也不能自动算作行为契约通过，仍需对照确认的行为依据。

## 3. Differential Testing

当两个实现可以在隔离环境中接收相同输入，并观察相同外部结果时，考虑 Differential Testing。

适用场景包括：

- 纯函数、计算、格式化、解析和序列化；
- 确定性的状态转换；
- 可使用 fixture 或 sandbox 隔离的 API / 业务流程。

比较公开输出、错误类别、持久化结果或其他行为契约的可观察面。先定义规范化规则，排除时间戳、随机 ID、无关字段顺序等非语义差异。

每个差异按以下类型分类：

| 类型 | 处理 |
| --- | --- |
| 已确认且已批准的行为变化 | 记录批准来源和影响 |
| 与已确认行为契约冲突 | 对冲突候选记为不满足该行为 |
| A、B 不同，但行为契约没有说明 | 标为未知，交回确认 |
| 仅内部表示不同，外部行为相同 | 不视为行为回归 |

**A 不是 oracle。** Differential Testing 只负责发现不同，不负责裁定哪个结果正确。两个实现输出相同也不能证明没有共同缺陷。

对有副作用的流程，只在可重置的 fixture、fake 或 sandbox 中运行。不得为 Differential Testing 重放生产写操作、触发真实退款 / 发信 / 删除，或污染共享数据。

没有合适的隔离方式时，跳过 Differential Testing 并说明原因，不为它引入常驻依赖或复杂测试框架。

## 4. Property-based Testing

只有在输入空间较大、规则可以清楚表达、生成成本合理时才使用。优先复用项目已有工具，不为单次比较引入新的测试依赖。

先写独立于实现的性质，例如：

- 编码后再解码应保持约定语义；
- 合法状态转换后始终满足不变量；
- 对有效输入，结果满足业务约束；
- 对相同输入，确定性操作得到相同结果。

性质必须来自行为契约、领域规则或可证明的不变量。不要从 A 或 B 的实现逻辑反向生成性质。随机种子、生成范围、失败样本和工具版本应可复现。

Property-based Testing 不适合时直接跳过，不把“没有使用”记为缺陷。

## 5. 比较维护成本

按本次改动选择有意义的维度，不必逐项评分。

| 维度 | 观察点 |
| --- | --- |
| 概念复杂度 | 新增了哪些类型、状态、配置、规则或需要独立记忆的概念？ |
| 结构复杂度 | 职责、依赖、分支和抽象层如何组织？关键路径是否需要跨越不必要的层？ |
| 可理解性 | 能否沿入口追踪主流程？关键不变量在哪里表达和保护？错误路径是否容易定位？ |
| 修改局部性 | 修改一个已知行为需要触及哪些模块、类型和调用方？ |
| 正确性边界 | 错误传播、并发、资源生命周期和副作用是否清楚？ |
| 项目适配 | 是否复用仓库已有约定、平台能力和基础设施？ |
| 运行成本 | 仅在相关时比较性能、资源、依赖或运维负担。 |

数量只能作为线索，不能单独作为结论。若统计概念、分支或抽象层，两个候选必须使用同一口径，并附具体清单或位置；无法统一口径就写 `不可比`。不把代码行数当作质量指标。

### Maintenance Probe（可选）

只有当需求、领域规则或项目路线中存在真实且合理的后续变化时才使用。给 A、B 同一个变化场景，只读追踪需要修改的入口、模块、数据结构和测试，比较影响范围与风险。不要为了制造差异而虚构一个需求，也不要实际实现这个 probe。

## 6. 推荐规则

- 行为契约是强制约束，不与复杂度收益抵消。
- 没有可复核的维护收益，不推荐仅仅“看起来更优雅”的候选。
- 一个维度改善但另一个重要维度明显恶化时，写清权衡；不强行求和。
- 无法排除行为差异、测试条件不可比或关键风险未查清时，结论应为“证据不足”。
- A、B 都不满足行为契约时，指出失败并交回实现 / 需求环节；不要只选相对较好者。
