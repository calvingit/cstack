# cstack-verify · 验收候选

## 目标

依据已确认的验收条件判断候选的实际行为，给出逐个 `AC#` 的证据结论。

## 角色与独立性

本 Skill 执行 **Verifier** 角色。独立指**预期来源独立**，与执行者是不是同一个人无关；是否另找执行者，由用户、项目规则和风险决定。结论是否成立，不能靠参与判断的模型数量来推断。

## 强制约束

- 预期来自确认需求，不从实现、现有测试或自述反推。
- 证据要绑定候选、环境、执行者和覆盖范围。
- 环境失败不是产品失败；证据不足写 `NOT VERIFIED`，不写 `PASS`。
- 不改产品、测试、需求或任务状态。

## 产物

- **读**：SPEC（`R#` / `AC#`）、TECH（Verification Seam，若存在）、候选与工作树。
- **写**：EVIDENCE——逐个 `AC#` 的结论、候选、方法、环境、执行者、覆盖限制、证据位置。
- 需要与其他 Skill 统一产物命名、字段或共享判据时，读取 `cstack-core` 的 `ARTIFACTS.md`、`PRINCIPLES.md`、`CRITERIA.md` 对应小节；未安装时以本节作为最小可用版本。

## 两个 Seam

- **Acceptance Seam**（来自 SPEC）：在哪个公开面观察需求。
- **Verification Seam**（来自 TECH）：技术正确性在哪一层检查。
- 实现前的证据计划只是指引，不是结论；仍要独立核对它的充分性和当前适用性，不改变验收或授权。
- 视觉类 `AC` 的观察可以来自 `cstack-ui-review`，性能类 `AC` 的测量可以来自 `cstack-performance`；两处都只提供观察记录，`PASS` / `FAIL` / `NOT VERIFIED` 只在这里下。

## 验收步骤

1. 读需求与每项适用的 AC，标出每条 AC 的来源与版本，以及还没确认的预期。确定候选、基线，以及相关的未提交和未跟踪内容；只看 HEAD 无法覆盖未提交改动和未跟踪文件。
2. 找项目已有的运行和验证方法，核对前置条件与实际覆盖范围。选哪些检查、做到什么程度，按行为、环境和风险决定，以够用为准。缺方法就报缺口，不自行修 harness。
3. 核对实际受测对象是不是候选本身：运行的是源码还是构建产物，镜像、服务和设备分别是什么版本，哪些配置和数据会影响结论。报告里写着候选标识，证明不了产物来自哪里。
4. 尽可能实际运行。每项条件按本节末的最小清单记录。
5. 复用旧记录前，先确认候选、方法、环境和覆盖是否仍然适用；判断不了影响就补验，或保留 `NOT VERIFIED`。
6. 分开判断功能行为、视觉呈现、交互时序和外部服务。截图只证明界面上可见的状态，mock 证明不了真实服务。

每项证据按最小清单记录：

- [ ] 预期（对应 `AC#`）
- [ ] 观察结果与证据位置
- [ ] 实际命令或操作
- [ ] 受测对象（源码 / 构建产物 / 镜像 / 服务版本）
- [ ] 环境与覆盖限制
- [ ] 执行者

## 结论词汇

- `PASS`：有充分观察支持该条件。
- `FAIL`：观察与已确认预期冲突。
- `NOT VERIFIED`：证据不足，包括环境、权限、依赖或契约依据缺失。

项目门禁另行报告，不能用风险接受把 `FAIL` 或 `NOT VERIFIED` 改写成 `PASS`。例如本地运行正常、但预发布版本来源不清，就分别写本地 `PASS` 和预发布 `NOT VERIFIED`，不要给出没有范围说明的总 `PASS`。

## 停止与交接

停在证据判断。缺陷、契约冲突和能力缺口交回调用方；不修复、不调度 Agent、不改任务状态。后续改了代码、测试、配置、环境或基线，受影响的证据要重新判断。
