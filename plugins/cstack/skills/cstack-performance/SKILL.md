# cstack-performance · 分析性能

## 目标

在可比条件下测量、定位瓶颈，并按授权优化。

## 强制约束

- 先测量再判断；没有可比基线，不猜瓶颈、不声称提升。
- 记录候选、环境、构建模式、数据规模与负载。
- 只分析时保持只读；优化需要授权。
- 只产出可复用的测量方法与数据；`AC` 的 `PASS` / `FAIL` 归 `cstack-verify`。
- 差异仍在测量波动范围内，或者前后条件不一致，就不能说性能提升。

## 产物

- **读**：场景、指标与目标、相关实现、已有测量、项目档案（PROFILE）中的验证入口。
- **写**：性能分析记录（指标、环境、基线、复测、实际变更、限制）。不是正式产物。
- 需要与其他 Skill 统一产物命名、字段或共享判据时，读取 `cstack-core` 的 `ARTIFACTS.md`、`PRINCIPLES.md`、`CRITERIA.md` 对应小节；未安装时以本节作为最小可用版本。

## 测量与优化流程

1. 确定场景、指标和目标；记录候选、设备或环境、构建模式、数据规模和负载。不具可比性的结果不要放在一起比较。
2. 在安全且获准的条件下复现问题，建立基线。计时数据、性能分析结果或运行数据按问题选择；重复测量并记下波动，可比条件按 `cstack-core` 的 `CRITERIA.md`「可比基线」。确实测不了就说明缺口，不猜瓶颈。
3. 顺着观察到的现象收窄范围，把现象、瓶颈假设和有证据支持的原因分开。选择一个最小的检查，只要能区分这些假设就行；不预设问题在 UI、网络、数据库或某个框架。
4. 用户要求优化时，才在授权范围内针对瓶颈改。改完以可比条件复测，并检查受影响的功能。
5. 报告指标、环境、基线与复测结果、实际变更和限制。

## 停止与交接

只要求分析时保持只读。原因不明的故障先 `cstack-diagnose`，验收判定交 `cstack-verify`；优化后条件若变化，重新判断结论；不把测量波动当成收益。
