# cstack-implement · 实现变更

## 目标

在授权范围内做出能工作的候选变更，保留实际检查结果，也保留还没验证的部分。

## 强制约束

- 在用户授权的范围内实现；下游角色只能收窄，不能扩权。
- 不改 SPEC、TECH、SLICES；需求、设计或范围冲突交回负责方。
- 不靠删除断言、跳过测试、放宽阈值或修改验收条件制造通过。
- 实现者自检不等于独立验收；自检记录不算 `EVIDENCE`。

## 产物

- **读**：SPEC（`R#` / `AC#`）、TECH（`D#`，若存在）、SLICES（若存在）、现有代码、基线与工作树。
- **写**：候选变更 + 自检记录（执行者标为实现者）。不写正式 `EVIDENCE`，不改上游产物。
- 需要与其他 Skill 统一产物命名、字段或共享判据时，读取 `cstack-core` 的 `ARTIFACTS.md`、`PRINCIPLES.md`、`CRITERIA.md` 对应小节；未安装时以本节作为最小可用版本。

## 入口与硬停

- 先读目标、范围、AC、TECH / SLICES 与写入边界；检查基线、已暂存和未暂存的改动，以及相关的未跟踪文件，把已有工作保住。
- 硬停：存在活跃写入方或正在执行的切片、目标 / 范围 / 结果不清、缺共享设计、需求或设计冲突 → 先停受影响部分并交回。
- 只要求实现时，不要自行扩大成重构或清理。
- SLICES 里有两个以上无阻塞切片、Runtime 支持独立实例且写入可隔离时，可以改走 `cstack-orchestrate` 并行实现；本 Skill 不自动切换，需用户明确要求。

## 实现顺序

1. 记录基线、初始候选和工作树状态。
2. 查清相关调用方、错误路径、现有测试和配置。
3. 实现前，为每条 AC 确定充分且可行的验证方法、前置条件和覆盖范围，并写明限制；缺方法就报缺口，不把「命令能正常执行」当验收。
4. 做最小的完整实现；多步按可观察行为推进；不为假设中的未来扩展而增加层次或依赖。
5. 能测试先行时按 `cstack-test-first` 的失败→通过循环做；否则用仓库现有的最小反馈回路。测试预期来自契约，不复制实现算法；不为测试方便而加生产接口。
6. 发现与本次无关的问题只记录，不顺手修。

## 自检与收尾

- 执行与改动相称的开发检查和项目门禁，记录实际命令、结果和限制。检查失败要定位并处理；不能运行或证据不足时明确说明。
- 收尾必须实际运行 `cstack-verify`（Verifier）和 `cstack-review`（Reviewer）。`cstack-simplify`（Simplifier）可以跳过。角色可以在同一上下文执行；安装 `cstack-core` 时按其 `ROLES.md` 派发角色，未安装时在同一上下文按角色顺序执行并标明执行者。
- Verifier 或 Reviewer 记为「未运行」不等于通过，不能据此声明完成。Simplifier 未运行记为跳过，不视为失败，也不能代替验收或审查。
- 不按改动大小或影响范围省掉验收和审查。修复后重新执行受影响的验收与审查。
- 只有每条适用验收条件都有充分证据、`cstack-verify` 和 `cstack-review` 都已实际运行，并且没有未解决的高风险问题，才能声明完成。

## 候选与报告

- 说明候选：HEAD 或提交范围，加上工作树是否有未提交 / 未跟踪改动；未提交内容不能只报 HEAD。
- 报告用下面的最小模板：

  ```markdown
  - 改了什么：
  - 候选：HEAD / 提交范围；工作树是否有未提交或未跟踪改动
  - 实际检查：命令、结果、限制
  - cstack-verify / cstack-review：结果，或未运行
  - cstack-simplify：运行过或跳过
  - 未验证项与剩余风险：
  ```

- 验收或审查未运行要明确写成未运行，不能写成通过。
- 验证后又修改相关内容时，重新判断受影响的证据。
- 提交、推送、创建 PR、合并、部署属于交付动作，交给 `cstack-ship` 判断与执行，各自按明确授权；Skill 名或任务名不扩大权限。
