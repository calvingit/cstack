# cstack-impact · 变更影响半径

## 目标

在设计、实现、验证或审查之前，先弄清这项变更会影响哪些其他地方，并尽量证明决定其是否安全的关键事实。列出调用方只是起点，关键安全事实才是重点。本 Skill 只分析影响半径，不替代验收、审查或交付判断。

## 强制约束

- 未证明的事实标「未证明」，不得写成已安全；已排除与未证明分栏。
- 未实现的方案可分析，须标明「未实现」，不得写成现状。
- 默认只读；不为证明安全操作真实业务数据。改代码或运行会改变状态的检查，需先取得授权。
- 工作状态与验证状态分开写；未运行不等于通过。

## 证明层级

对每条关键安全事实，尽量往下推，并写明停在哪一层。五级定义见 `cstack-core` 的 `CRITERIA.md`「证明层级」，这里是判断要点：

1. **口头断言 / 搜索无结果** — 不成立。
2. **定位到具体行** — 真实 `file:line`，或所依赖库的源码与固定版本；只是线索。
3. **推演到失败路径不可达** — 可以成立，写明推演前提。
4. **运行真实代码** — 调用应用实际依赖的同一库、同一函数；通常停在这一层。
5. **在运行环境复现** — 安全结论依赖真实运行时序、外部系统或部署环境时必须到达。

审查时判断一个问题能否推翻，用同一套层级。

## 常见陷阱

- 只按符号搜索，漏掉动态调用、配置驱动路径、反射或跨语言边界。
- 只查当前工作树，不看实际依赖库的版本、补丁与构建产物。
- 只看返回类型，不看 JSON 序列化、数据库列、线格式和字节级兼容。
- 只运行测试，不确认测试加载的是不是应用实际依赖的同一库、同一构建产物。
- 把「没搜到调用方」当成「没有调用方」；搜索无结果只是盲区提示，不是安全证据。

## 分析步骤

1. **读变更**：符号与行为上实际变了什么（含 diff 未写明的）。仅有方案时标明未实现。
2. **找 1–2 条关键安全事实**：多数风险可由一两条关键事实判断（例如「这次调用只清理已失效缓存」）。先找这条，不堆可能性清单。
3. **查盲区**：按「常见陷阱」逐项核对，不停留在符号搜索。
4. **写风险与已排除**：每条写触发条件、影响对象、可能性与代价、`file:line`、怎么查；查过无事的另列。不编造调用方或 API。
5. **按证明层级验证**：尽量运行真实代码，贴命令与输出；证不了就标「未证明」并写明卡在哪一层。

## 报告与停止

用下面的模板写一份短报告：

```markdown
# 变更影响半径

## 范围与基线

## 改了什么
（方案则标未实现）

## 关键安全事实
- 事实：
- 证明层级：
- 证明：

## 风险

## 已排除

## 未证明与未知

## 合并前成本最低的检查
```

每条风险写触发条件、影响对象、可能性与代价、`file:line`；已排除项单列，未证明项写清卡在哪一层。

报告写完即停止。

证据不足时，不宣布这次变更安全；默认不改产品、不执行交付。本报告非正式产物，不替代规格、技术决定或验收证据。
