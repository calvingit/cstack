# cstack-statechart · 梳理状态转换

## 目标

从需求、领域模型和实现中恢复一个实体、流程或协议的状态行为，形成有证据依据、可审查的状态模型，并用状态图解释关键路径。

核心产物是状态模型。图是模型的视图；TLA+ 是按需采用的形式化验证方式。本 Skill 不负责实现状态机，也不要求项目采用特定状态管理库。

## 何时使用

- 需要设计或审查实体、任务、会话、订单、连接、资源等生命周期。
- 状态分散在多个字段、条件判断、事件处理、异步回调或持久化逻辑中，需要识别隐式状态机。
- 需要理解重试、超时、取消、恢复、重复事件或并发操作如何影响状态。
- 需要把状态转换整理成图，供设计、实现或代码审查使用。

如果只是追踪某个函数的执行路径，使用 cstack-how；如果重点是业务概念、关系和规则，使用 cstack-domain-model；如果已有关系只需要一般性的图形解释，使用 cstack-visual-explain；如果行为方向仍不确定且需要可运行原型拍板，使用 cstack-prototype。

## 强制约束

- 先限定分析对象和代码范围。只调查相关实体、事件入口、状态读写点和必要调用链，不以全仓扫描代替判断。
- 分开记录需求约束与当前实现。需求、ADR、接口契约说明系统应该如何工作；代码和运行记录说明当前实际如何工作。两者冲突时并列报告，不静默选边。
- 重要状态和转换必须有依据。记录文件路径、符号或可用的行号；没有证据的内容标为推断、假设或未知，不补造事件和路径。
- 区分 State 与 Context。只有当某个差异会改变实体允许的后续行为或对外可观察的生命周期时，才建成独立状态；普通数据、计数器和参数留在 Context，并在需要时作为 Guard 条件。
- 区分 Event、Guard 和 Effect。事件触发转换，Guard 决定转换是否允许，Effect 描述转换伴随的操作；不要把操作步骤误画成状态。
- 识别真实的原子性边界。不得把多个数据库写入、远程调用或异步步骤默认视为一个原子动作；无法确认事务、锁、CAS 或消息确认语义时，明确标为未知。
- 多个独立状态维度分别建模。不要把任务状态、Worker 生命周期、验证状态和资源所有权的所有组合展开成笛卡尔积；需要时用多张关联图表达交互。
- 不因画图或建模而修改业务代码、重构状态管理或改变需求。后续修改由相应 Skill 和用户授权决定。
- 状态图、静态分析和模型检查结果都不能冒充实际运行证据。

## 证据分类

对模型中的重要信息使用以下分类：

| 分类 | 含义 |
| --- | --- |
| Contract | 来自已确认需求、ADR、接口契约或明确业务规则 |
| Observed | 直接从当前代码、配置、测试或运行记录观察到 |
| Inferred | 根据多个状态读写点、调用路径或条件推断 |
| Assumption | 为继续分析暂时采用，但尚无证据确认 |
| Unknown | 当前范围内无法确定 |

Contract 描述预期行为，不代表实现已经遵守；Observed 描述当前实现，不代表它符合需求。Inferred 和 Assumption 不得写成已确认事实。

## 工作流程

### 1. 确定边界

明确被分析的实体、流程或协议，以及要回答的问题。优先读取：

- 相关类型、枚举、字段和数据库结构。
- 创建、更新、删除或状态持久化入口。
- 读取状态并据此分支的代码。
- 事件、消息、回调、定时任务和 API 入口。
- 重试、超时、取消、恢复和清理逻辑。
- 相关需求、领域规则、测试和架构决定。

追踪状态的写入者和读取者。只读到一个字段定义，不足以确定它的完整生命周期。

### 2. 发现状态与转换

显式状态通常来自 enum、状态常量或状态机配置。

隐式状态可能分散在：

- 多个 Boolean 或可空字段的组合。
- 时间戳、计数器和错误信息。
- 条件分支与状态写入。
- 数据库记录、缓存和消息元数据。
- 异步回调、超时任务和恢复逻辑。
- Worker、锁、租约或资源所有权。

从事件入口追踪到状态变化，再追踪后续读取和副作用。记录正常路径，也检查失败、重复、迟到和取消事件。

### 3. 建立状态模型

至少区分以下元素：

| 元素 | 要回答的问题 |
| --- | --- |
| State | 当前处于什么行为阶段？ |
| Context | 哪些数据影响 Guard 或 Effect？ |
| Event | 什么输入或外部事件触发变化？ |
| Guard | 满足什么条件才允许转换？ |
| Effect | 转换时执行什么操作？ |
| Atomicity | 哪一部分由事务、锁、CAS 或单一状态更新保证不可分割？ |
| Invariant | 哪些条件必须始终成立？ |

不要为了统一而强行把所有系统压成单一 status 字段。多个状态维度可以独立存在，并通过事件、所有权或同步关系相互影响。

### 4. 整理转换表

默认使用以下字段；简单场景可以省略无意义的列，但不能省略证据依据。

| From | Event | Guard | To | Effect | Atomicity | Basis / Evidence |
| --- | --- | --- | --- | --- | --- | --- |
| 起始状态 | 触发事件 | 允许条件 | 目标状态 | 伴随操作 | 原子性边界 | 分类及源码位置 |

每条转换都要能回答：

- 谁或什么触发它？
- 在什么条件下允许发生？
- 状态在哪里被更新或持久化？
- 是否有副作用，以及副作用是否与状态更新处于同一原子边界？
- 重复、并发或迟到事件到达时会怎样？

没有足够证据确定的转换，放入待确认项，不要为了填满表格而猜测。

### 5. 检查模型缺口

按场景相关性检查：

- 初始状态和终止状态是否有依据。
- 是否存在无法到达的状态或没有处理的事件。
- 是否存在非法状态组合、绕过必要阶段或意外回退。
- 重试次数、超时、取消和恢复是否有明确边界。
- 重复事件、重复提交和迟到回调是否可能覆盖新状态。
- 多个执行者是否可能同时获得同一资源或任务。
- 检查与写入之间是否存在竞态。
- 需求约束与实际实现是否一致。

只有在分析范围足够完整时，才报告状态不可达、转换不存在或事件未处理。否则应写明“在已检查范围内未发现”，并列出未覆盖入口。

### 6. 生成状态图

发现有意义的状态机后，默认提供 Mermaid 状态图。Mermaid 是可审查、可版本管理的文本图示；如果用户需要对话内交互探索，优先按宿主实际提供的原生 visualize 能力呈现，或交由 cstack-visual-explain 处理展示。不要假设每个 Runtime 都提供原生可视化，也不要让展示层改写模型语义。优先使用 stateDiagram-v2：

- Overview 展示主要状态、关键事件、正常路径和重要异常路径。
- 复杂模型再拆出 Detailed 图，展示 Guard、重试、超时或多个状态维度之间的关系。
- 转换标签优先写触发事件；影响判断的 Guard 放在标签中。
- 只有有依据时才标记初始和终止状态。
- 不把 Context 的每个取值画成独立节点。
- 不把未知转换画成事实；未知和假设放在图旁说明。
- 图过于拥挤时拆图，不通过隐藏关键异常路径来简化。

示意结构：

~~~mermaid
stateDiagram-v2
    [*] --> Pending
    Pending --> Running: Claim
    Running --> Completed: Success
    Running --> Retrying: Failure / retry allowed
    Retrying --> Running: RetryReady
    Running --> Failed: retry exhausted
    Completed --> [*]
    Failed --> [*]
~~~

示意图只说明表达方式，不代表当前项目的实际行为。实际图必须依据本次读取到的模型生成。

### 7. 按需进行形式化验证

TLA+ / TLC 不是默认步骤。只有在以下情况值得进一步考虑：

- 多个执行者的并发交错会影响正确性。
- 重试、超时、事件乱序或恢复路径难以通过普通路径推理。
- 涉及锁、租约、资源所有权或分布式一致性。
- 可以明确写出要检查的 Safety 或 Liveness 性质。
- 模型边界和有限检查规模合理，结果可能影响设计或验证决策。

用户明确要求形式化验证时，按请求执行。其他情况下，先说明潜在价值和成本；不要仅为了生成图而创建 TLA+ 模型。

执行时：

- 从已确认的状态模型派生 TLA+ 规范，并显式列出抽象、假设、常量、状态空间边界和公平性条件。
- 优先使用项目或环境中已有的 TLC；不自动安装 Java、TLA+ 工具或外部服务。
- 分开检查 Safety 与 Liveness。Liveness 必须说明所依赖的公平性假设。
- 记录实际执行的命令、配置和结果。未运行、超时或状态空间受限都不能报告为检查通过。
- TLC 反例必须先映射到模型转换，再定位实际代码。模型反例不自动等于实现缺陷；需要实际代码复现或其他独立证据。

结果使用以下状态：

| 状态 | 含义 |
| --- | --- |
| MODEL_PASS | 指定模型、边界和性质的检查完成且通过 |
| MODEL_FAIL | 找到违反性质的反例 |
| MODEL_INCOMPLETE | 超时、状态空间限制或工具错误导致检查不完整 |
| MODEL_NOT_RUN | 未执行模型检查 |
| CODE_REPRODUCED | 已在实际实现中复现对应行为，单独记录，不由 MODEL_PASS 推导 |

### 8. 输出与停止

按任务复杂度输出，通常包括：

1. 分析对象和覆盖范围。
2. 状态及 Context 摘要。
3. Mermaid 状态图。
4. 关键状态转换表及证据。
5. 不变量、异常路径、并发边界和未决问题。
6. 如执行形式化验证，附模型范围、假设、TLC 结果和实际代码复现情况。

简单模型可以合并状态摘要和转换表；复杂模型拆分多张图。不要为了套模板制造无意义章节。

默认在当前任务中展示结果。只有用户要求持久化，或项目已有状态模型文档约定时，才写入文件；沿用项目位置，不创建第二份权威模型。

如果没有有意义的状态转换关系，报告 NO_STATE_MACHINE，并说明原因及更合适的分析方式。

达到回答当前问题所需的模型范围后停止。报告尚未调查的入口、外部系统和未知行为，不以全仓扫描追求完整感。

## 职责边界

| Skill | 职责 |
| --- | --- |
| cstack-domain-model | 业务概念、关系、术语和业务规则；本 Skill 将相关生命周期转化为可审查的状态转换 |
| cstack-how | 追踪具体代码路径；本 Skill 需要恢复实体或协议的状态行为 |
| cstack-visual-explain | 通用图形解释和交互呈现；本 Skill 负责状态模型语义及可审查的状态图 |
| cstack-prototype | 用可运行原型解决尚未确定的行为选择；本 Skill 不替人拍板 |
| cstack-tech-design | 决定跨模块共享的接口、生命周期和并发约束；本 Skill 提供状态模型依据 |
| cstack-verify | 验证实际候选是否满足已确认的验收条件 |
| cstack-review | 审查代码变更是否引入状态转换回归 |

本 Skill 不拥有领域术语、需求决策、实现修改或正式验收结论。上游调用时，将状态模型、图示、证据和未决问题交回调用方。
