# cstack-clarify · 澄清需求

## 目标

澄清只定需求层面的选择，产出后续环节共用的 DECISIONS。用户已经给出的选择继续有效，不要为凑齐模板反复追问；该不该继续问，只看前沿是否为空。实现归 `cstack-implement`，由用户手动调用，不随澄清结束自动开始。

## 强制约束

- 只处理会改变用户可见行为、范围、验收、兼容或权限的未决选择；私有实现细节自己定。
- 能查的事实自己查，不把事实问题当决策问题抛给用户。
- 决策归用户；不替用户选，也不把单个例子或推测写成规则。
- 回答一轮只解锁下一轮前沿，不是开始实现的授权。
- 澄清阶段不改代码。
- 确认项写入 DECISIONS；未决项保留，不用假设填平。

## 产物

- **读**：用户请求、会话中已确认的内容、PROFILE（若存在，用于项目术语与需求权威）。
- **写**：DECISIONS，每项含 `C#`、问题、选择、理由、可观察结果、确认来源、未决项。它是澄清的职责产物，不属于「额外状态系统」。
- 需要与其他 Skill 统一产物命名、字段或共享判据时，读取 `cstack-core` 的 `ARTIFACTS.md`、`PRINCIPLES.md`、`CRITERIA.md` 对应小节；未安装时以本节作为最小可用版本。

## 决策树

把讨论画成一棵**决策树**：每个决定都会分叉出依赖它的决定。树必须留在已确认的目标与范围内；范围本身是第一个要定的枝。

## 前沿与轮次

- **前沿（frontier）** 指当前就能提问的未决选择：前置条件已经确定，不必猜测尚未得到的回答。
- 一轮问完整个前沿再等回答，不逐个追问，也不一次问到依赖未答问题的选择；这类选择属于后面的轮次。
- 用户每答一轮，已定的决定会解锁下游的选择：重算前沿，再问下一轮。只有新证据或需求变化才重开受影响的枝，不整棵树重来。

提问是**循环**，不是一次性动作：

```text
重算前沿 ──> 问一整轮 ──> 等用户回答 ──> 记录确认项
   ↑                                        │
   └────────── 前沿非空：回到下一轮 ─────────┘
               前沿为空：转入收尾
```

- **前沿非空就不得收尾，也不得开始实现。** 唯一出口是用户以新指令明确要求停止澄清（见「完成与停止」的「停止澄清的出口」）。
- 答完一轮新解锁的连带选择（依赖升级、旧账处理）同样是前沿的问题，都要问。

## 决策分类

| 选择 | 谁定 | 记录去向 |
| --- | --- | --- |
| 用户可见行为、范围、验收、兼容、权限，以及是否改变外部契约 | 用户 | DECISIONS → SPEC 输入 |
| 契约如何定义与实现、跨模块架构边界、共享模型、长期技术方向 | 记为技术关注点 | 交给 `cstack-tech-design` 审查，不在澄清阶段选择实现方式 |
| 私有方法、文件布局、局部重构、内部辅助（不改依赖版本） | Agent | 自己定，不问 |

依赖升级（版本及其兼容影响）和顺手处理旧账属于范围与兼容选择，归用户，不算私有实现细节。

一个具体场景不能替未确认的业务选择做决定。比如“软删除还是永久删除”会改变行为，必须在澄清阶段定；已经确认行为的例子属于 `cstack-specify`。

## 事实调查

- Runtime 支持子代理时，按 [事实调查子代理定义](references/fact-finder.md) 派发只读调查（对应 `cstack-core` 的 Explorer 角色）；一个前沿里可以并行多条，各自报告结论、证据、类型（观察 / 推断 / 未知）、影响和未解决项。
- 暂不支持子代理时，按同一职责自行调查，保持同样的输出结构。
- 调查尚未结束时，只把依赖它的问题留到后面，其余前沿照常提问；不要等所有调查结束再开始整轮提问。
- 子代理只查事实，不做需求决策；涉及业务选择时回传“需要用户决定”。
- 不编造拿不到的来源内容，也不把未决选择悄悄当成答案。
- 附带发现里属于范围、兼容或依赖的选择，按「前沿与轮次」进入下一轮，不自行消化。

## 提问格式

一轮对应一个前沿。优先调用 Runtime 的 `visualize`（或等价的可视化 / 交互能力），把整轮问题渲染成**一个能一次提交的交互界面**：每题给出标题、必要背景、选项和推荐，用户可以在同一页勾选或填写，一次提交整轮回答。图形只是载体，不改变“决策归用户、推荐要有理由、接受自由回答和替代方案”。

若没有可用的可视化能力，或问题不适合图形化，退回文本格式：编号（跨轮次唯一）、写清背景与关键后果、给出推荐和理由，并在轮末给一条简短的回复格式。两种形式都要保证支持键盘操作、文本可复制，不因图形丢信息。

```markdown
### Q1. <要决定的事>

<一两句背景与关键后果>

<问题>

- **A.** <选项>
- **B.** <选项>

> **推荐：** <选项>——<理由>

---

**回复：** `1A, 2: <回答或替代方案>`
```

## 会话记录

- 每轮结束后，按「产物」的字段把确认项连同理由、可观察结果和未决项写入 DECISIONS。
- 落点默认沿用项目已有位置；没有时先记在会话里，收尾时与用户确认，已有位置也不例外。确认沿用、按用户指定迁移，或用户明确拒绝落盘；拒绝落盘时在收尾总结中明示「未落盘」，这是用户的选择，不是跳过落盘的理由。
- 除 DECISIONS 和用户确认的落点外不新建文件，也不新建别的状态系统；术语或长期决定可以交给领域建模处理。

## 完成与停止

**进入收尾的默认条件：前沿为空，没有未经确认的假设。** 唯一例外是用户以新指令明确要求停止澄清，见本节「停止澄清的出口」。

收尾按顺序执行：

1. **总结全部决策**：逐条复述 `C#` 的问题、选择、理由、可观察结果和未决项，并说明前沿为空的依据；用户要求停止澄清时，改为说明哪些枝仍未问及原因。
2. **问落点与补充**：落点是收尾的固定动作，不因前沿为空而省略——问用户 DECISIONS 写到哪里、是否还要补充或修改。
3. **判断是否结束**：用户明确回答无需补充时，澄清到此为止；有属于需求层面待决选择的补充时，它进入下一轮，问完重算前沿再回到第 1 步。落点调整在第 2 步内处理，不进下一轮。两种情况都只推进澄清，不进入实现。

- 实现细节和未决设计留给后续，不阻塞澄清结束；它们不算未决项。
- 「未决项」只接纳三种分支，并写明各自的原因：已经问过且用户明确暂不作答；依赖尚未到手的外部信息；用户要求停止澄清时仍未问到的连带选择。答完一轮新解锁的连带选择不能登记为未决项来替代提问。
- 未决项只阻塞依赖它的部分；哪些部分现在能做归用户决定，不在澄清阶段推定。
- 需要重述目标与边界时用 `cstack-restate-goal`，交给他人接手时用 `cstack-handoff`；两者都不替代收尾三步，也不在澄清阶段另写交接摘要。
- 用户声称「已授权后续工作」时，这句话只免去重复确认已答的 `C#`，不跳过剩余前沿，也不等于可以开始实现；只有用户要求停止澄清本身（例如「别问了，直接做」），才按本节「停止澄清的出口」处理。
- 反例：把一轮回答当成开始实现的信号，替用户决定新解锁的连带选择，或用「不新建文件」跳过 DECISIONS 落盘。
- **停止澄清的出口**：用户明确要求停止澄清时（无论是否同时要求开始实现），那是新的指令与新的授权，不是对上一轮回答的解释：澄清让位。让位前先把仍未问的连带选择逐条登记为未决项并写明原因，再做收尾三步；同一指令还要求开始实现时，收尾后转入 `cstack-implement`，视为用户的手动调用。无论哪种，都不在澄清里顺手改代码。
