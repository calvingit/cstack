# cstack-domain-model · 梳理领域模型

## 目标

把业务概念、关系、状态和规则理清，记录到项目能长期维护的位置，让后续设计、实现和审查使用同一套词。

## 强制约束

- 持续维护项目的领域模型：术语、关系、状态、不变量和长期决定。
- 术语说“是什么”，不是代码做什么；一个概念用一个规范词。
- 不假定固定路径；优先项目已有的术语表、领域模型和 ADR 布局，不为了套模板而重命名或迁移。
- 不改代码，不替用户决定业务。

## 产物

- **读**：现有术语表 / 领域模型 / ADR / 架构文档、相关代码、确认需求（DECISIONS / SPEC）。
- **写**：术语条目与 ADR，放在项目权威位置；没有约定时先问用户，或复用当前会话记录、项目已有位置。不建立第二份领域权威。
- 需要与其他 Skill 统一产物命名、字段或共享判据时，读取 `cstack-core` 的 `ARTIFACTS.md`、`PRINCIPLES.md`、`CRITERIA.md` 对应小节；未安装时以本节作为最小可用版本。

## 权威来源

1. 用户命名的术语、架构或决策文档。
2. AGENTS / README / CONTRIBUTING / 架构文档声明的位置。
3. 已有的 glossary / CONTEXT / DOMAIN / TERMS / 领域模型 / ADR 布局。
4. 当前代码、公共契约、调用链和测试证明的事实。

位置重要但尚未确定时，先问一次；项目既有格式优先。

## 何时更新术语

- 用户或 SPEC 的词与现有术语冲突。
- 一个词在不同会话、代码或文档里有多个含义。
- 新概念将进入代码名、接口名、任务文档或长期规格。
- `cstack-clarify` / `cstack-specify` / `cstack-review` / `cstack-architecture-review` 需要稳定的词来描述模块、seam 或需求。

术语表不写实现细节：文件路径、类名、API 路径、字段映射、缓存策略、发布步骤。通用工程词（timeout、retry、错误类型、factory）通常不是领域语言，先问“这是本业务独有，还是通用工程概念”。

## 术语格式

```markdown
**Visitor**：当前会话中接受服务的对话参与方。
_Avoid_: Customer, Buyer, User
```

优先项目已有格式；几个词指同一概念时，选一个规范词，其余记为 avoid 或兼容别名。

## 领域模型与 ADR

- 已有领域模型权威（关系、生命周期、状态、不变量）时，任务中确认有长期变化就按原格式更新；与代码冲突时列出证据，不私下选边。
- 没有这种权威时，不新建单独的领域模型文件：术语写进术语表，通过 ADR 门禁的决定写成 ADR，其余作为问题报告。
- **ADR 门禁** 三条同时满足才写：① 难以逆转；② 缺少背景说明会让后续读者感到意外；③ 是真实权衡的结果。
- ADR 内容写背景、决定、理由（1–3 段）；状态、选项、后果只在有长期价值时加。任务内的选择留在任务记录或 SPEC，接口协议留在契约文档，编码规则留在项目规范。
- ADR 与 `TECH` 的分工见 `cstack-core` 的 `ARTIFACTS.md`：任务内决定写 `D#`，跨任务仍成立时提升为 ADR，`TECH` 保留 `D#` 与一行摘要，不复制内容。

## 会话中的做法

1. 读当前领域文档、相关代码、任务文档和历史决定。
2. 用户用词与现有术语冲突时立刻指出，给有依据的候选解释。
3. 用具体场景压边界：角色、状态、生命周期、权限、失败路径、跨模块交互。
4. 术语定下就记录，不等会话结束；位置不明就不猜。
5. 代码、文档和用户不一致时，列出冲突与证据，不静默选边。

## 与 cstack-clarify 组合

本 Skill 不拥有决策树、前沿或轮次。它把领域问题交给 `cstack-clarify` 的同一前沿；用户确认后由 `cstack-clarify` 写入 DECISIONS，本 Skill 只记录术语和 ADR，不再要求第二次确认。复用项目已有的 glossary / ADR 位置。

## 验证与停止

- 只执行目标仓库已有的轻量检查（Markdown / lint / link check 或 `git diff --check`），不发明特定技术栈的检查。
- 只做建模时，不自动改代码；后续实现按已有授权继续。
