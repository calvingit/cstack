# cstack-orchestrate · 并行切片实现

## 目标

在授权范围内把互不阻塞的切片并行实现，再合并成一份可验收的候选，并在固定轮次内完成验收、审查和简化的收口循环。并行只服务于实现；验收、审查和简化仍是独立实例的判断。

## 强制约束

- 主会话以 **Orchestrator** 身份运行：只派发、转发、等待和收尾，不改代码、不做技术判断、不验收、不审查、不裁定分歧。
- 编辑权只来自 Implementer 角色实例；主会话没有编辑权，一次也不许“顺手改一下”。
- Verifier、Reviewer、Simplifier 都是独立实例，结论不能由主会话或 Implementer 代写；Implementer 自检不构成 `EVIDENCE`。
- **只有 Verifier 和 Reviewer 定义收口判据**；Simplifier 的发现进入修复队列，但不参与“是否完成”的判定，也不得无限追。
- 候选是**提交链**，不是浮动工作树；切片提交是实现机制，属于写入范围，不等于交付授权——不推送、不建 PR、不合并。并行只改变实现顺序，不改变完成判据：`N` 个切片各自通过**不能**推出候选通过。

冻结边界、只增不改与轮次上限（T1 ≤2 轮，T2 ≤3 轮）见下文对应小节；到达上限仍未收敛就停止推进并交回，不进入下一轮，不自行放宽判据。

## 产物

- **读**：SLICES（`S#`、blocked-by、covers、`S#-AC#`、约束）、SPEC（`R#` / `AC#`）、TECH（`D#`，若存在）、现有代码、基线与工作树。
- **写**：候选变更（由各 Implementer 在其 worktree 内产生）、SLICES 的**追加**（修正切片，只追加不修改既有条目）、编排记录（派发批次、隔离载体、提交链、修正切片、收口轮次、失败与降级原因）。主会话不写 `EVIDENCE`；候选级 `EVIDENCE` 由 T2 的 Verifier 写。不改 SPEC / TECH 和 SLICES 的既有条目。
- 需要与其他 Skill 统一产物命名、字段或共享判据时，读取 `cstack-core` 的 `ARTIFACTS.md`、`PRINCIPLES.md`、`CRITERIA.md` 对应小节；未安装时以本节作为最小可用版本。

## 入口与硬停

- 手动触发。本 Skill 只在用户明确要求并行实现多个切片时进入，`cstack-implement` 不自动升级到本 Skill。
- 先读 SLICES 与写入边界，检查基线、已暂存和未暂存的改动，以及相关的未跟踪文件，把已有工作保住。
- **硬停**：存在活跃写入方、目标 / 范围 / 结果不清、缺共享设计、需求或设计冲突、Runtime 不支持独立实例 → 先停受影响部分并交回。
- 不满足并行条件时退回 `cstack-implement` 串行执行，并说明退回原因；不假装派发过。

## 并行判定

全部满足才并行派发，否则退回串行：

1. SLICES 存在，且至少两个切片的 `blocked-by` 为“无”或已满足。
2. 这些切片之间没有未定的共享契约；`cstack-slice` 的「共享契约落在第一个使用它的端到端切片上」已落实，且该切片已完成或排在更早批次。
3. Runtime 能派独立实例，且隔离载体可用（见下节）。做不到就退回串行，不伪造并行。
4. 存在明确的写入授权范围，覆盖所有被派切片。

**并行上限 4**。上限不为省资源而设：合并成本与冲突概率随并行度超线性上升。超出上限时按 SLICES 顺序分批，不为了跑满而放宽判据。

## 隔离载体

载体是 **git worktree + 切片提交**：每个 Implementer 一个独立 worktree，基于**当前批次基线提交**创建。不提供文件所有权分区、加锁串行化等其他隔离方式。

- 创建 worktree 是实现机制，不是交付动作：不推送、不建 PR、不合并。它属于写入范围的一部分，未获写入授权时不得创建。
- **基线随批次推进**：同一批次的切片基于同一基线并行；切片通过 T1 后提交，后续批次以这个新提交为基线。
- 每个 Implementer 只在自己的 worktree 内改动；越界写入视为失败，不并入候选。
- worktree 保留到收口循环结束才清理：修复轮次仍要回到原 worktree 和原 Implementer 实例。提前清理等于丢掉实现者的上下文。
- 合并都是写操作，由 Implementer 实例执行，主会话只指定顺序和基线；主会话自己不动 git 索引。
- **集成方式固定为 `git merge --no-ff`**：切片提交的 SHA 保持不变，冻结时记录的门禁结论才对得上。rebase、squash 或 cherry-pick 都会产生新提交，等于把已冻结的切片换成没验过的代码。
- 收尾清理只删本次创建的 worktree；不清理他人或来历不明的 worktree，清理结果与实际残留一并报告。

## 冻结与追加

**冻结边界**是“通过 T1 并提交”。边界两侧的规则不同：

| | 未提交 | 已提交并冻结 |
| --- | --- | --- |
| 可以改吗 | 可以，这是 T1 循环内的正常修复 | 不可以，只能追加新切片承载修正 |
| 基线 | 本批次基线 | 后续批次的基线 |
| 结论 | 逐轮重判 | 保持有效：提交按 `--no-ff` 集成、SHA 没变，证据就仍然成立 |

- SLICES 中**尚未实现**的切片可以调整顺序或改切法；已实现的切片不可回改，也不靠重排把它们“改掉”。
- 需要修正已冻结切片的实现时，**追加一个修正切片**：它同样是正式的 `S#`，进入 SLICES，标注 `fixes: S#`，说明它改的是哪条行为、为什么原实现不成立。修正切片同样要过 T1。
- **追加是 SLICES 唯一被允许的写入**：既有 `S#` 条目的编号、covers、`S#-AC#`、约束一律不改；追加时编号接续，不复用已冻结的编号。SLICES 作为交付契约向前增长，不回写历史。
- 追加修正切片后候选变了，T2 对新候选重判；已冻结切片先前的 T1 记录仍然有效，前提是它的提交按 `git merge --no-ff` 集成、SHA 没变。重放或重写过的切片不算，要重新过 T1（见「失败与降级」）。

## Router 状态

主会话只持有指针，不持有结论内容。状态表按切片一行，字段固定：

| `S#` | `Implementer` 实例 | worktree | 切片提交 | 阶段 | 判定次数 | 结论位置 |
| --- | --- | --- | --- | --- | --- | --- |

- **切片提交**记录该切片产生的 commit，是后续批次的基线来源；未提交时记 `—`。修正切片按自己的 `S#` 独立成行，并标注 `fixes: S#`。
- **结论位置**只记子代理 id 与输出路径，不复制正文。
- 主会话只读两样东西：**是否还有未解决项**，以及每条发现标注的**所属 `S#`**；其余内容留在子代理那里。
- 分发时按 `S#` 标签转发，不读正文、不归类、不判断轻重。状态表可以压缩或重建，结论正文一律不引入、不转述，也不压缩成摘要。
- 报告需要引用某条结论时，转发原文或原文路径，不用自己的话复述。

## 实现阶段

1. 确定基线提交、写入边界与可用 worktree 载体。
2. 算出 ready set：`blocked-by` 为“无”或已满足的切片；超出上限的按 SLICES 顺序截断。
3. 派发前让每个 Implementer 报计划触及的文件 / 契约范围；重叠时拆批或调整，不派可能互相破坏的批次。
4. 并行派发 Implementer，每个只接收本切片的 `S#`、covers、`S#-AC#`、约束和基线提交。
5. 每个切片在自己的 worktree 内完成后，先过切片级门禁（T1）。
6. T1 通过后由该 Implementer 提交并合并进当前基线；提交后该切片冻结。
7. 后续批次以合并后的新提交为基线；直到没有可执行切片。
8. 全部合并成单一提交链后进入候选级收口循环（T2）。

## 两层门禁

### T1 · 切片级

每个切片在自己的 worktree 内完成后执行，**不涉及 Simplifier**：

- Verifier：按 `cstack-verify` 判本切片的 `S#-AC#`。
- Reviewer：按 `cstack-review` 审本切片 diff。
- 两者都是独立实例，可并行；范围限于本切片改动。
- **是合并门禁**：未清不提交、不合并。这是冻结前唯一的修改窗口。
- 产出是切片工作记录，**不是 `EVIDENCE`**，汇总进候选级时标明来源切片。
- **硬上限 2 轮**。超过 2 轮仍不过就停，不延长循环凑通过。先分清是哪种情况：被本切片覆盖的 `AC#` / `S#-AC#` 判不清 → 退回 `cstack-specify`；实现没到位 → 交回，如实报告未收敛。
- **修正切片失败不得再派生**：某个 `fixes: S#` 的修正切片自己没过 T1 时，不许再追加一个 `fixes: <修正切片>`。此时判断只有两种：原切片的前提不成立（回 `cstack-specify`），或 T2 的发现被路由到了错误的切片（交回说明）。再派生一层只会推迟暴露真正的问题。
- **通过即提交**：T1 通过后由该 Implementer 提交本切片，提交即冻结，成为后续批次的基线。

**切片级不派 Simplifier**：一个 helper 在单切片视角下常常显得没道理，合并后才会看到它的第二个调用方。在 T1 判定简化会产生大量误报。

### T2 · 候选级

所有切片合并成单一提交链后执行，每轮派三个独立实例（三者互不依赖，可并行）：**Verifier**、**Reviewer**、**Simplifier**。三者都不改产品代码；Verifier 按 `cstack-verify` 写这份候选的 `EVIDENCE`，Reviewer 与 Simplifier 只报告。

- **Verifier**：按 `cstack-verify` 逐条判断全候选的 `AC#`，产出 `PASS` / `FAIL` / `NOT VERIFIED` 与证据，并写成该候选的 `EVIDENCE`。
- **Reviewer**：按 `cstack-review` 找变更引入的缺陷，并额外覆盖**跨切片视角**——重复定义、同一逻辑的两份实现、契约理解漂移、命名与错误处理不一致。这些不在任何单个切片 diff 里，是 T2 区别于 T1 的唯一理由。
- **Simplifier**：按 `cstack-simplify` 找合并后才暴露的多余复杂度。**只在 T2 派**，正是因为它要的是合并后的全局视野。
- 三者都必须在每条发现上标注**所属 `S#`**，跨切片问题标注 `跨切片`；这是按标签转发的依据，不标就是不合格回报。

**收口判据只由 Verifier 和 Reviewer 定义**：两者都无未解决项即收口成功。Simplifier 不参与这个判定。

**为什么 Simplifier 不参与收口判定**：简化没有自然终止点——“还能更简单”永远可辩。让它参与退出条件，循环就永远退不出来。它的发现进同一个修复队列：Implementer 可以按技术理由不改，理由写进记录，记为「后续项」；涉及已确认契约的，按 `cstack-core` 的 `CRITERIA.md`「发现分级与处置」，由有权方接受风险并记录接受者，不由实现者自行关闭。

**轮次预算：**

- 一轮 = 一次 Verifier 判定 + 一次 Reviewer 判定 + 一次 Simplifier 判定；判定之后才处理发现。
- **上限 3 轮**，因此处理最多 2 次：第 3 轮判定仍有未解决项时不再处理，直接交回。否则会出现“改完却没有轮次再验”的悬空结论。
- **第 1 轮 Simplifier 审全候选；第 2、3 轮只看本轮新增的改动**，不重复审同一份代码。
- Simplifier 可以按用户要求跳过，记为跳过，不视为失败，也不能代替验收或审查。

**发现的处理：**

1. 把三份**原始结论**按 `S#` 标签分发给对应的 Implementer；`跨切片` 的发给负责合并基线的那一个。只发结论与证据，不发主会话的摘要或转述。
2. **发现指向已冻结切片时，不改那个切片**：追加修正切片承载修复，标注 `fixes: S#`，由原 Implementer 实例继续做（上下文连续，不新建、不重新交代背景）。
   **实现者复用 ≠ 切片续做**：新切片是新 `S#`、新提交、新基线，原切片与其提交一律不动。复用的只是那个实例对代码的记忆，不是“接着写原来那个切片”。派发时要按新 `S#` 交代范围与 `fixes` 关系，不能让 Implementer 误以为仍在原切片内追加改动。
3. **发现指向尚未冻结的切片时**，在冻结前正常修，不必追加。
4. Implementer 完成回报改了什么、哪些结论它不认同及技术理由；不认同的按分歧处理，不自动算通过。
5. 修正切片同样要过 T1，通过后提交并合并进基线；然后回到第 1 步，对新候选重新判定。
6. 修复若需要改动已合并的共享契约 → 硬停，交回 `cstack-tech-design`；若冲突牵动需求或验收条件本身判不清，退回 `cstack-specify`。不在循环里就地改契约。

**为什么停在第 3 轮：** 同一批问题经过三次独立判定仍未收敛，通常不是实现细节不够，而是目标、验收条件或共享设计本身没定清。此时继续追加只会把不确定性固化进代码，而不能消除它。交回时的提问要指向根因（哪条 `AC#` 判不清、哪个契约没定、哪处需求有冲突），不是“已经有 3 轮了”。

## 子代理回报契约

每个子代理只回报下列内容，不写完整叙述；回报用于按标签转发，不用于替代报告：

- **Implementer**：`S#`、实际触及的文件与契约、`S#-AC#` 自检结果、未验证项、未决问题与冲突请求。
- **Verifier**：逐条 `AC#` 的结论、候选、方法、证据位置、覆盖限制。
- **Reviewer**：发现的位置、触发条件、影响、证据、所属 `S#`、未覆盖范围。
- **Simplifier**：简化候选及其承担的责任、删除或合并后如何保住这份责任、预期维护收益、所属 `S#`，或 `no_change`。

主会话逐字转发与引用这些结论，包括未验证项；不重写、不归纳成“都通过了”。

## 失败与降级

- **切片发现需要新的共享契约** → 硬停该切片：契约问题交 `cstack-tech-design`，牵动需求或验收条件的退回 `cstack-specify`。不允许 Implementer 自行发明共享契约。
- **T1 超过 2 轮** → 硬停，不延长循环。分清是实现没到位还是 `AC#` 判不清：前者交回并如实报告未收敛，后者退回 `cstack-specify`。不重排切片。
- **已冻结切片需要修正** → 追加修正切片（`fixes: S#`），不回改、不 revert、不重写历史。
- **修正切片自己没过 T1** → 停，不再派生修正切片。归因为原切片前提不成立（回 `cstack-specify`）或发现路由错误（交回说明），不再追加第三层。
- **跨切片冲突** → 不手工解冲突；把后完成的切片在新基线上重放一次。重放产生新提交，该切片退回未冻结状态，要重新过 T1 才能并入候选；仍冲突则把该切片退回串行。
- **切片规模远超预估** → 该切片退回串行，其余批次继续。
- **部分切片失败** → 候选只包含成功切片；失败切片 covers 的 `AC#` 记为 `NOT VERIFIED`，不能因为其他切片通过而省略。
- **Runtime 中途失去隔离能力** → 停止派发，已提交的切片保留为候选，剩余切片退回串行。
- **Implementer 越界写入或改到上游产物** → 该切片结果不并入候选，按失败处理并报告。
- **Implementer 上下文丢失或实例不可续** → 不得用“看起来没问题”替代；如实报告为限制，必要时把该切片退回串行重做。

## 收尾与报告

- 收口成功 = 最后一轮 Verifier 与 Reviewer 都无未解决项，且两者的未运行项都已列明。Simplifier 的跳过、后续项或由有权方接受的风险单独记录，不影响该判定，也不改写成通过。
- **通过数不能合并**：`N` 份 T1 切片记录全绿，不能推出候选通过；候选结论只来自 T2 的 Verifier。切片记录汇总进候选时标明来源切片，不单独构成 `EVIDENCE`。
- 主会话发布完成声明前，逐条引用子代理的原始结论，包括未运行与未验证项；不按票数、轮数或多数结果下判断。
- 报告用下面的最小模板：

  ```markdown
  - 改了什么：
  - 候选：基线提交 + 提交链（S# 提交 + 修正切片提交）；工作树是否有未提交或未跟踪改动
  - 编排：并行批次与切片、上限内分批原因、追加的修正切片、worktree 清理结果
  - 各切片 T1：轮次与结论，或未运行
  - 各切片 `S#-AC#`：结果，或未运行
  - 收口轮次：实际轮数 / 上限 3
  - 最后一轮 cstack-verify：逐 `AC#` 结论，或未运行
  - 最后一轮 cstack-review：发现与处理，或未运行
  - cstack-simplify：候选、`no_change` 或跳过
  - 未验证项与剩余风险：
  ```

- 到达轮次上限仍未收敛时，报告改为：停在哪个问题、涉及哪些 `AC#` / 契约、各轮判定、以及为什么判断是实现没到位还是需求侧没定清。需求侧问题退回 `cstack-specify` 重新确认目标、`AC#` 与验收条件；实现侧问题写明已追加的修正切片为何仍未通过，并说明是否已用尽修正机会（修正切片失败后不得再派生）。不在这份报告里声明完成。
