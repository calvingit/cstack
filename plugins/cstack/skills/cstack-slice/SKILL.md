# cstack-slice · 拆分工作

## 目标

把已明确的工作拆成能实施、能验证的单元，暴露真实依赖和集成风险。拆分是规划方法，不是调度或状态系统。

## 强制约束

- 只拆已确认的 SPEC（和必要的 TECH），不改需求或设计含义。
- 每个切片要能独立演示或验收，是纵向的端到端交付，不是横向层。
- 只有“缺了前一项，后一项会开始错”才算依赖；不为叙事顺序造链，不成环。
- SLICES 是稳定交付契约，不写执行状态、进度或结果。

## 产物

- **读**：SPEC（`R#` / `AC#`）、TECH（`D#`，若存在）、项目现状。
- **写**：SLICES，每项含 `S#`、交付什么、covers（`R#` / `AC#` / `D#`）、blocked-by、本地 AC（`S#-AC#`）、约束。写到 `SLICES` 为止：切片级验证记录留在工作记录里，不写成 `EVIDENCE`。
- 需要与其他 Skill 统一产物命名、字段或共享判据时，读取 `cstack-core` 的 `ARTIFACTS.md`、`PRINCIPLES.md`、`CRITERIA.md` 对应小节；未安装时以本节作为最小可用版本。

## 输入

1. 读完 SPEC 的 Goal、范围、`R#`、`AC#`、非目标与依据，不从头猜范围。
2. 若存在 TECH，读受影响的 `D#` 与集成 / 迁移约束；没有 TECH 时，先判断是否满足 `cstack-tech-design` 的“何时必须做”，需要就先做。
3. 只在会改变切片结果、粒度或依赖时才调查仓库、AGENTS、术语与现有任务约定。
4. 需求、公共契约、范围或验收未定 → 回 `cstack-clarify` / `cstack-specify`；共享技术决定未定 → 回 `cstack-tech-design`。不要把假设写成切片。

## 拆分规则

- **tracer bullet（纵向切片）**：每个切片穿过交付需要的所有层（数据、接口、UI、测试、必要文档），完成即可演示或验收；不是一个“先建所有接口 / 枚举”的横向层。
- **交付完整**：每个切片收尾都要按 `cstack-verify` 和 `cstack-review` 检查本切片，范围限于本切片的改动与 `S#-AC#`；切片记录不构成交付候选的 `EVIDENCE`，最终由一次覆盖全候选的验收和审查收口。`cstack-simplify` 可选。不单列“补所有测试”或“最后清理”这类没有独立交付的切片。
- **真实依赖**：blocked-by 只写真正阻止本切片开始的其他切片；没有就是“无”。无阻塞的切片构成第一批可执行集合。
- **共享契约落在第一个使用它的端到端切片上**；只有真实阻塞（schema 生成、expand–contract、兼容层）才设准备型切片。
- **宽重构例外**：一次机械改动横扫全仓、无法独立变绿时，按 expand → migrate（按包 / 目录分批）→ contract 排，不硬塞纵向切片。
- 切片描述结果，不写会过期的文件路径、代码片段或操作步骤；引用 TECH 时只带适用的 `D#` 与必要约束。

## 拆分检查清单

写之前先检查候选拆分：

1. **标题**：短、面向结果。
2. **交付什么**：这一个切片单独能验证的端到端行为。
3. **covers**：覆盖的 `R#` / `AC#` / `D#`，与上游引用一致。
4. **blocked-by**：真实前置切片，或“无”。
5. **本地 AC**：`S#-AC#` 能通过公开面判定。
6. **约束**：继承 SPEC / TECH 中与本切片相关的约束。

普通粒度和依赖由已确认上游决定，不需要用户逐项确认。如果拆分中暴露出产品、范围、优先级、发布、兼容、验收或共享设计选择，回上游，不要写成切片假设。

## 输出与交接

输出切片清单、真实依赖、每项怎么验证、第一批可执行切片，以及仍阻塞的问题。沿用用户指定的 issue / 任务文件 / 会话形式；未经授权不发布外部任务，也不引入持久化执行图。拆分本身不授权实现；用户已要求实现时，可在授权范围内继续。
