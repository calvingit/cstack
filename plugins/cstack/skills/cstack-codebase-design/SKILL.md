# cstack-codebase-design · 设计深模块

## 目标

把一个具体模块的接口、Seam、依赖方向和测试面设计成可独立判断的局部方案，不扩大成全仓架构审查。

## 强制约束

- 只处理一个已确定的设计点：模块、Interface、Seam、依赖方向或测试面。
- 用项目的领域词与既有契约名；不强行重命名组件、服务或 API。
- 不预设 Clean Architecture、DDD、Hexagonal、MVC、MVVM 等风格，按证据判断归属与边界。
- 只给真实候选，不为了显得完整而凑选项。

## 产物

- **读**：目标模块、代表性生产调用方、组装 / 配置入口、下游依赖、相关测试、SPEC / TECH（若存在）。
- **写**：局部设计判断——当前行为、归属、不变量、候选、推荐与理由，并标注观察 / 推断 / 未知。它不是正式产物；需要多个实现共享的设计决定仍交回 `cstack-tech-design` 写 `TECH`。

## 术语

- **Module**：一个有单一调用者可见 Interface 与 Implementation 的单元，从一个函数到跨层的切片都算。
- **Interface**：调用者必须知道的一切——签名、不变量、顺序、错误、配置、性能；不只是 API 签名。
- **Implementation**：模块内部代码。
- **Adapter**：在 Seam 处连接模块与外部依赖的角色，不表示实现大小。
- **Depth**：每个 Interface 承载多少行为。深模块用很小的 Interface 藏住大量行为；浅模块几乎把实现复杂度暴露给调用者。
- **Seam**：行为可以在不改该处代码的情况下变化的点——公开或内部接口、I/O、进程、外部系统、时钟。位置与实现是分开的决定。
- **Leverage**：调用者每掌握一个 Interface，能获得多少能力。
- **Locality**：变化、缺陷、知识和验证集中在归属方附近，而不是散在调用方。

## 原则

- 把复杂度藏在合适的归属方内部；调用者表达意图，不重复接线、校验、协议或状态机步骤。
- 从可观察行为设计 Interface：先定能力、输入、输出、失败语义、生命周期、并发 / 取消约束；不要从现有类、表或厂商 SDK 反推公共接口。
- 把 Seam 放在真实变化点；现有公开接口、I/O、进程、时钟 / 随机、存储或 UI 边界够用就复用。仅“测试不好写”不足以扩大接口。
- Adapter 放在边缘：隔离厂商 SDK、HTTP、数据库、文件系统和平台 API；不无谓地包住每个依赖。
- 优先 Locality，而非猜测性复用：为多个真实调用方或已有变化点抽象，不为模式名抽象。
- Interface 就是测试面：调用者和测试穿过同一个 Seam；如果要绕过 Interface 测试，模块结构或接口边界可能不对。

## 删除检验（deletion test）

想象删掉这个模块，让调用者直接使用它的下游依赖。如果删掉后抽象能力、约束、稳定性和可理解性都没有明显损失，它就是一个透传层；如果复杂度会在 N 个调用方重新出现（协议、状态、不变量、错误语义、缓存 / 事务边界），它才值得保留。删除检验判断价值与深度，不证明 Seam 或依赖方向一定正确。

## 工作流

1. 命名设计问题、预期调用方，以及要决定的 Module / Interface / Seam；不扩大成全仓架构审查。
2. 读目标模块、代表性生产调用方、组装 / 配置入口、下游依赖和相关测试。
3. 写下当前可观察行为、归属、必须成立的不变量和真实外部边界。
4. 判断 Interface、Depth、Seam、Adapter、依赖方向与 Locality；每条结论标观察 / 推断 / 未知。
5. 有多个真实候选时，给出 2–3 个并列出收益、成本、迁移影响和测试 Seam，说明为什么排除其他方向；只有一个候选成立时，直接推荐并说明理由。
6. 推荐最简单的设计：把必要复杂度放到合适的归属方，不扩大公共面。
7. 停在局部设计判断，按下面的边界路由后续工作。

## 边界

- 整体架构是否成立、是否符合项目约束：`cstack-architecture-review`。
- 需要写 `TECH` 的共享设计：`cstack-tech-design`。
- 需求或行为未定：`cstack-clarify` / `cstack-specify`。
- 缺陷根因：`cstack-diagnose`。
- 行为不变地缩小 diff、或删除已无必要的复杂度：`cstack-simplify`。
