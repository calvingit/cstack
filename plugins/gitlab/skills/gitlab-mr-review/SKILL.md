# gitlab-mr-review · 两阶段评审

## 目标

先让使用者看懂这个 MR 在做什么，再给出有证据的评审发现。默认只读，发表评论必须单独授权。

## 强制约束

- **默认不写任何东西到 MR。** 不发评论、不回复、不解决讨论、不批准、不改标签。评审者自己发。
- **阶段之间必须停。** 第一阶段讲完目标与做法后停下等确认，不许直接进入第二阶段。
- 只评审**本次改动新增的内容**。diff 里标 `+` 的行是作者已经写的，不要建议「加上」它。
- 发现要有可达场景和具体位置；证据不足的标为不确定，不写成结论。
- 不追究格式与命名偏好，除非它导致真实缺陷或确实妨碍理解。

## 流程

### 第一阶段：讲清楚这个 MR 是什么

读取 MR 与 diff：

```bash
glab mr view <iid>
glab mr diff <iid>
git log --oneline <target>...<source>
```

`--raw` 在当前实例不可用，需要结构化 diff 时用：

```bash
# 先按文件列出改动规模，判断从哪里开始读
glab api "projects/<encoded-path>/merge_requests/<iid>/diffs?per_page=100" \
  | jq -r '.[] | "\(.new_path)  +\([.diff | split("\n")[] | select(startswith("+") and (startswith("+++")|not))] | length)  -\([.diff | split("\n")[] | select(startswith("-") and (startswith("---")|not))] | length)"'
```

注意 `diffs` 端点不返回 `new_lines` / `old_lines` 字段，增删行数要从 `diff` 文本里数。

按下面五点向使用者说明，篇幅控制在一屏内：

- **问题**：这个 MR 在修什么或补什么，一两句。
- **改动**：它改了什么来回应这个问题，一两句。
- **机制**：只讲到能看懂为止，不逐行复述 diff。
- **具体例子**：一个前后对比。样本输入到输出、一个用户可见场景、或一小段代码走查。这一项必须有，抽象描述要靠它落实。
- **范围**：改动涉及的主要文件或模块，按关注点分组，不要罗列全部文件。

讲完停下，问一句「要继续深入评审代码吗」。等使用者回答。期间如果他对目标有疑问，留在第一阶段继续解释。

### 第二阶段：有证据的评审

只在使用者确认后开始。

按影响排序，逐项检查：

- **正确性**：逻辑错误、边界条件、空值处理、并发与竞态、差一错误。
- **回归与安全**：行为变化、越权、注入、敏感信息、未处理的错误、N+1 与性能悬崖、迁移与数据风险。
- **测试覆盖**：新增行为有没有对应测试，分支有没有覆盖。
- **架构契合**：是否沿用既有模式，有没有引入可避免的债务或范围蔓延。

每条发现写成：`file:line` — 问题是什么、为什么会发生、具体的失败场景或修法。断言前先读周边代码确认，不要凭 diff 片段猜测。

收尾给明确结论：有没有阻塞项，是否可以合并。评论由使用者自己发。

## 产物

- **读**：MR 元数据、diff、相关源码、已有讨论。
- **写**：评审报告（第一阶段理解、第二阶段发现、结论）。不写平台。

## 输出格式

```markdown
## 评审：<MR 标题> (!<iid>)

### 这个 MR 在做什么
- 问题：
- 改动：
- 机制：
- 例子：
- 范围：

### 发现
**[P1] <标题>**
`path/to/file.ext:42-48` — 问题与影响。

**[P2] <标题>**
`path/to/file.ext:15` — 问题与影响。

### 结论
<可以合并 / 需要修改后再看>，阻塞项：<有/无>
```

没有够格的发现就直说代码看起来没问题，不要为凑数编发现。

## 与写操作的关系

使用者要求把发现发到 MR 上时，读取 `gitlab-core` 的 `SAFETY.md`，逐条确认发什么、发到哪、几条，再用 `glab mr note create` 执行。批量行内评论用 `gitlab-self-review` 的草稿流程。
