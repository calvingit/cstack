# gitlab-mr-review · MR 评审

## 目标

先讲清这次改动是什么，再给出有证据的评审意见与合并风险，让问题在合并前被发现。默认只读，发表评论必须单独授权。

意见要能在 MR 上讲清楚，便于他人接着讨论，级别要同时回答「有多严重」和「要不要现在改」。

## 强制约束

- **默认只读。** 不发评论、不回复、不解决讨论、不批准、不改标签。草稿仅本人可见，攒草稿不算公开；**发布是写操作**，发布前必须逐条确认发什么、发几条。
- 只评审**本次改动新增的内容**。diff 里标 `+` 的行是作者已经写的，不要建议「加上」它。
- 每条意见要有可达场景和具体位置；证据不足的标为不确定，不写成结论。
- 不追究格式与命名偏好，除非它导致真实缺陷或确实妨碍理解。
- 评审结论不构成合并许可，也不替代逐条验收。

## 流程

### 1. 固定范围

三种入口任选其一，先固定基线再读 diff：

```bash
# 入口一：已创建的 MR
glab mr view <iid>
glab mr diff <iid>
git log --oneline <target>..<source>

# 入口二：指定的 diff（给定 base 与 head；单次提交直接看该提交的 patch）
git diff <base>...<head> --stat

# 入口三：指定的分支
git log --oneline <target>..<source>        # 本次独有的提交
git diff <target>...<source> --stat         # 本次引入的变更
```

`log` 配 `..`，`diff` 配 `...`，两者不能互换；`diff` 若用 `..`，会把目标分支的改动算进评审范围。

`glab mr diff --raw` 在当前实例不可用，需要结构化 diff 时按文件列出改动规模，判断从哪里开始读（`diffs` 端点不返回 `new_lines` / `old_lines`，增删行数要从 `diff` 文本里数）：

```bash
glab api "projects/<encoded-path>/merge_requests/<iid>/diffs?per_page=100" \
  | jq -r '.[] | "\(.new_path)  +\([.diff | split("\n")[] | select(startswith("+") and (startswith("+++")|not))] | length)  -\([.diff | split("\n")[] | select(startswith("-") and (startswith("---")|not))] | length)"'
```

读不到范围或 diff 为空是限制，不算评审通过。工作树有未提交改动时，这部分不在范围内，单独说明，不要混进结论。

### 2. 先讲清这次改动是什么

使用者提供了需求文档链接时，先读它；意图概括和清单第 10 项的对齐核对都以它为基准。

按五点向使用者说明，篇幅控制在一屏内：

- **问题**：这次改动在修什么或补什么，一两句。
- **改动**：它改了什么来回应这个问题，一两句。
- **机制**：只讲到能看懂为止，不逐行复述 diff。
- **具体例子**：一个前后对比，可以是样本输入到输出、一个用户可见场景，或一小段代码走查。这一项必须有，抽象描述要靠它落实。
- **范围**：改动涉及的主要文件或模块，按关注点分组，不要罗列全部文件。

讲不清楚，或与 MR 描述（无 MR 时为提交信息）不一致，本身就是一条评审意见，见清单第 10 项。

### 3. 按清单逐项检查

逐项过，不要跳，按影响排序汇报：

1. **能否编译或运行**：改动涉及的模块有没有实际运行过。项目没有 CI 时，这份清单是唯一的验证来源，本地实际运行过才能算数；不要拿「改动不大」当免检理由。
2. **正确性与错误路径**：逻辑错误、差一错误、空值、边界（空集合、零值、超大输入）、异常与超时、并发与竞态、未处理的错误、掩盖失败的静默回退。
3. **回归与兼容**：行为变化；接口签名、返回结构、序列化格式变了会不会影响调用方。
4. **安全**：越权、注入、敏感信息泄露（日志、错误信息、序列化输出）。
5. **配置与迁移**：新增配置项有没有默认值；数据库变更能否回滚。
6. **性能**：N+1、真实负载下的性能劣化。
7. **测试覆盖**：新增行为有没有对应测试，分支有没有覆盖；没有就明确说没有。UX 改动要有端到端证据（截图或录屏），可能影响性能的改动要有 profile，证据优先用前后对比，只给改后证据不算充分；没测的边界要么补测，要么写明。
8. **架构契合**：是否沿用既有模式，有没有引入可避免的债务或范围蔓延。
9. **调试残留**：临时代码、注释掉的逻辑、多余的日志、硬编码路径。
10. **描述与改动一致**：MR 描述（或提交信息）里说的和 diff 里做的是否一致；行为假设和顺手改动必须写进描述。提供了需求文档链接时，以需求文档为准核对改动是否偏离意图。

每条意见断言前先读周边代码确认，不要凭 diff 片段猜测。

### 4. 整理成评审意见

每条写成：

```
[级别] 标题
path/to/file.ext:42 — 问题、触发条件、影响。
```

级别用 P0 到 P3：

| 级别 | 含义 |
| --- | --- |
| P0 | 会导致故障、数据错误或安全问题，合并前必须改 |
| P1 | 很可能导致故障，建议合并前改 |
| P2 | 值得改进，可以后续处理 |
| P3 | 风格与命名偏好，作者可以忽略 |

### 5. 评估合并风险

缺陷之外，按五个维度给这次改动的整体风险定级（⚠️ 风险高 / 👀 存疑 / ✅ 风险低），并给 low / medium / high 总评：

- **对齐**：改动与描述是否一致，行为假设和顺手改动有没有写明。取清单第 10 项的结论。
- **影响面**：改动波及多大范围、离敏感路径多近。认证、权限、支付、个人身份信息（PII）、密钥、数据迁移、依赖升级、基础设施与配置，触及任何一项就抬高风险，与 diff 大小无关。
- **验证**：行为有没有证据。取清单第 1、7 项的结论；UX 改动没有端到端证据，或性能改动没有 profile，都算验证不足。
- **回滚成本**：合并后能否回滚。区分单向门与双向门：破坏性操作、数据变更、难逆转的决策是单向门。
- **故障可发现性**：上线后出现异常，有没有监控或告警能先于用户发现；有没有吞掉错误的静默回退让人误以为一切正常。不适用时标 ✅。

总评以影响面和验证为主导，回滚成本次之。

### 6. 落到 MR（需授权）

使用者要求把意见发到 MR 上时，用草稿把多条评论攒起来一次发布，而不是发出一串碎片评论：

```bash
DRAFT=$(mktemp)
cat > "$DRAFT" << 'EOF'
**[P1] 重试分支没有上限**

第三次重试后仍会再次入队，失败任务会持续堆积。
EOF
glab mr note draft create <iid> --file server/src/OrderService.java --line 88 -m "$(cat "$DRAFT")"
```

管理草稿：

```bash
glab mr note draft list <iid> -F json
glab mr note draft update <iid> <draft-id> -m "新正文"
glab mr note draft delete <iid> <draft-id> --yes
```

**`publish` 会发出该 MR 上本人的所有草稿**，包括之前遗留的。发布前列出全部待发草稿逐条核对：

```bash
glab mr note draft list <iid> -F json | jq -r '.[] | "\(.id) \(.position.new_path):\(.position.new_line) \(.note | split("\n")[0])"'
```

确认后执行，发布后回读核对实际落到 MR 上的内容：

```bash
glab mr note draft publish <iid> -m "评审意见见上方逐条评论。" --yes

glab api "projects/<encoded-path>/merge_requests/<iid>/discussions?per_page=20" \
  | jq -r '.[] | .notes[0] | select(.position) | "\(.position.new_path):\(.position.new_line) \(.body | split("\n")[0])"'
```

## 产物

- **读**：MR 元数据、diff、相关源码与测试、已有讨论。
- **写**：评审报告（意图概括、评审意见、合并风险、结论、未验证范围）。草稿可直接攒，发布需授权，发布后回读。

## 输出格式

```markdown
## 评审：<MR 标题> (!<iid>)
<!-- 未开 MR 时用分支或 diff 范围命名 -->

### 意图概括
- 问题：
- 改动：
- 机制：
- 例子：
- 范围：

### 评审意见
**[P1] <标题>**
`path/to/file.ext:42-48` — 问题、触发条件、影响。

### 合并风险
**总评：<low / medium / high>**
- 对齐：<⚠️ / 👀 / ✅> — <依据>
- 影响面：<⚠️ / 👀 / ✅> — <依据>
- 验证：<⚠️ / 👀 / ✅> — <依据>
- 回滚成本：<⚠️ / 👀 / ✅> — <依据>
- 故障可发现性：<⚠️ / 👀 / ✅> — <依据>

### 结论
<可以合并 / 需要修改后再看>，阻塞项：<有/无>

### 未验证范围
<读不到或无法确认的部分；没有就写「无」>
```

确实没有值得提出的问题时，就直说代码看起来没问题，不要为凑数硬找问题。

## 停止条件

- 使用者只要意图概括或只要意见清单时，交那一部分即可，不要建草稿。
- 属于需求理解分歧的，交回需求侧确认，不自行判定为缺陷。
- 修复要另行授权，本 Skill 只报告。
