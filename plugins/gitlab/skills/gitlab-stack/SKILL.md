# gitlab-stack · 大改动拆成 MR 链

## 目标

把一个太大、评审者无从下手的改动，拆成若干能独立评审、按顺序合并的小 MR。

## 强制约束

- 拆分过程中**每一步都要能编译、测试通过**，中间态必须可用。
- 拆分不改变最终代码内容。拆完后整条链合并的结果必须与拆分前的分支一致。
- `glab stack` 是实验特性。可用时按它操作；不可用时退回手动建链，不要因为工具不可用而中断拆分。
- 不主动推送、不主动建 MR，除非用户明确要求。

## 何时该拆

满足任一条就值得拆：

- diff 超过几百行，或涉及十几个文件。
- 里面混着互相独立的多件事：重构、功能、修 bug、格式化。
- 评审者必须一次看懂全部才能判断任一部分。
- 依赖升级与适配改动搅在一起。

如果是同一件事但改得杂，先考虑精简，不是拆分。

## 流程

### 1. 先固定当前状态

```bash
git status --porcelain
git branch --show-current
git log --oneline origin/HEAD..HEAD
```

工作树有未提交改动时，先让用户决定提交还是暂存，不要在脏工作区上拆。

记录拆分前的最终内容，作为事后核对的基准：

```bash
git rev-parse HEAD > /tmp/stack-original-head
```

### 2. 找出拆分边界

按「可独立描述」切分，不是按文件切分。一个切片应该能用一句话说清它在做什么，并且单独合并后系统仍然自洽。

常见切法：

| 内容 | 切片 |
| --- | --- |
| 先搬代码不改行为 | 第 1 层：重构，无行为变化 |
| 在新位置加能力 | 第 2 层：功能实现 |
| 补测试与文档 | 第 3 层：覆盖与说明 |
| 配置、开关、迁移 | 按依赖顺序插在需要它的那一层之前 |

依赖方向必须单向：后面的层可以依赖前面的层，反过来不行。

### 3. 建链

先看工具是否可用：

```bash
glab stack --help
glab stack list
```

`glab stack` 可用时按它的模型工作：每个切片是一个分支，基于前一层，第一个切片基于目标分支。不可用时手动建：

```bash
git checkout -b feature/part-1 origin/HEAD
# 只挑第 1 层的改动
git checkout -b feature/part-2 feature/part-1
# 只挑第 2 层的改动
```

从已有分支按块挑改动，用交互式暂存控制粒度：

```bash
git checkout feature/all-work -- path/to/file
git reset -p
```

### 4. 逐层验证

每建完一层就验证，不要全部拆完再一起测：

```bash
# 每层都要能独立成立
git stash list          # 确认没有依赖未提交内容
<构建或测试命令>
```

关键检查：这一层单独合并到目标分支后，系统能不能运行。做不到说明切分点选错了。

### 5. 核对最终结果

全部拆完后，确认链的结果与原始改动一致：

```bash
git diff $(cat /tmp/stack-original-head) feature/last-part --stat
```

有差异就修，差异说明拆分过程中改动或丢失了内容。

### 6. 建 MR 链（需授权）

每层的 MR 目标分支指向前一层，第一层指向目标分支：

```bash
MSG=$(mktemp)
cat > "$MSG" << 'EOF'
<本层描述>
EOF
glab mr create --push \
  --source-branch feature/part-2 --target-branch feature/part-1 \
  --title "第 2 层：<做什么>" --description "$(cat "$MSG")"
```

四个标志分工不同，写错会让 MR 指向错误的分支：

| 标志 | 作用 | 链式 MR 里怎么用 |
| --- | --- | --- |
| `-s` / `--source-branch` | 从哪个分支发起 | 本层分支 |
| `--target-branch` | 合入哪个分支 | 上一层的分支 |
| `-R` / `--repo` | MR 建在哪个仓库 | 跨仓库时才需要 |
| `-H` / `--head` | 从哪个派生仓库取源分支 | 用 fork 时才需要，不是用来指定目标仓库 |

`-H` 常被误解成「指定目标仓库」，它实际是选 head 仓库。在同一个仓库内建链式 MR，不要加 `-H`。

顺序很重要：先建第 1 层并确认目标分支，再建第 2 层。前一层合并后，后一层的目标分支会自动重定向到主干，但仍需人工确认。

## 停用实验命令时的判断

`glab stack sync` 会一次性改写多条分支的指向关系。除非用户明确要求并且理解后果，不要运行。手动建链更可控。

## 产物

- **读**：完整 diff、提交记录、构建与测试结果。
- **写**：拆出的多个分支；建 MR 需单独授权。

## 停止与交接

- 找不到能独立成立的切分点时，说明这个改动本质上不可拆，不要强行拆成坏中间态。
- 拆分中发现问题需要先修，停止拆分，先修再拆。
- 建立 MR 链后，后续的评审意见处理转给相应评审流程。
