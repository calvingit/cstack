# gitlab-commit · 提交信息与原子拆分

## 目标

写出让半年后的自己和评审者都能看懂的提交，并且一个提交只做一件事。

## 强制约束

- **项目既有约定优先。** 先看 `git log --oneline -20`，仓库有自己的风格就跟随，本 Skill 的规则只作默认值。
- 一个提交只做一件事。修 bug 时顺带的重构、格式化、依赖升级分开提。
- 提交信息讲**为什么**，diff 已经说明**做了什么**，不要在正文复述改动。
- 不在没授权时提交。生成信息不等于已执行 `git commit`。

## 检测既有约定

```bash
git log --oneline -20
git log -3 --format='%s%n%b%n---'
```

判断三件事：标题是否带前缀（`feat:` / `fix:`）、是否大写开头、正文是否用项目术语。仓库里已有明显风格就照它写，不要强推另一套。

## 标题怎么写

默认规则，社区版 GitLab 用祈使句、大写开头、不加句号：

| 要求 | 说明 |
| --- | --- |
| 祈使句 | 完成句子「这个提交会……」。写「修复重试计数溢出」，不写「修复了」「已修复」 |
| 长度 | 目标 72 字符内，中文按实际宽度算，尽量一行说清 |
| 不加句号 | 标题末尾不写句号 |
| 指向行为 | 讲行为不变量，不写文件名或类名 |

中文项目的写法建议：

- 动词开头：「修复订单同步在重试时重复写入」。
- 避免「【update】」一类无信息量的前缀，除非项目已经在用且团队认可。
- 需要写模块名时放正文，不挤进标题。

## 正文写什么

正文只在需要解释「为什么」时写，用空行与标题分隔：

- 触发问题的条件，以及不修会怎样。
- 为什么选这个做法，放弃了哪些备选。
- 关联的 issue 或 MR，用完整 URL，短引用在跨项目时不可点。

```
修复订单同步在重试时重复写入

MQ 重投时没有校验幂等键，同一订单会被写入两次。
改为在消费入口登记幂等键，重复投递直接丢弃。

Closes https://gitlab.example.com/group/project/-/issues/123
```

关联 issue 用完整 URL 的原因：`#123` 只在当前项目上下文里解析，跨项目或群组页面会是纯文本。

## 原子拆分

一个提交该不该拆，用三个问题判断：

1. **能不能单独回滚？** 只回滚它时不牵连其他改动。
2. **能不能单独描述？** 一句话说得清它在做什么。
3. **评审者能不能跳过它？** 纯格式化、纯重命名这类，评审者可以快速放过。

常见拆法：

| 场景 | 拆成 |
| --- | --- |
| 功能 + 顺带重构 | 先重构（不改行为），再功能 |
| 功能 + 格式化 | 格式化单独一个提交 |
| 修 bug + 加测试 | 可以合并，测试是该修复的证明 |
| 依赖升级 + 适配改动 | 升级一个，适配一个 |
| 多个不相关的小修 | 一修一个提交 |

不该拆的情况：拆分后中间某个提交不能编译或测试不通过，那不是一个合法的中间态。

## 提交前检查

- [ ] 只暂存了属于这次改动的文件（`git status` 确认没有顺手 `add .` 带进来的临时文件）
- [ ] 提交内容能编译、相关测试通过
- [ ] 标题是祈使句，说清行为变化
- [ ] 正文解释了「为什么」，没有复述 diff
- [ ] 关联 issue 用完整 URL
- [ ] 含特殊字符的提交信息用单引号 `git commit -m '...'`

## 产物

- **读**：`git log` 既有风格、`git diff --staged`、项目贡献规范。
- **写**：提交信息文本；获授权后执行提交，不推送。

## 与 MR 描述的分工

提交信息回答「每次改动为什么」，MR 描述回答「整体在做什么、怎么验证」。两者不互相复制，MR 描述读取本分支的提交作为输入之一。
