# 写操作安全约束

## 读写分界

默认只读。下列动作都会在服务器上留下别人能看到的痕迹，需要用户明确授权后才执行：

| 动作 | 影响面 | 默认 |
| --- | --- | --- |
| 发表评论、回复、解决讨论 | MR 上所有人可见，触发通知 | 不做 |
| 批准、请求修改 | 改变审批状态，可能解除合并阻塞 | 不做 |
| 创建 draft note | 只有本人可见，未发布 | 可以攒着 |
| 发布 draft notes | 一次性发出全部草稿并通知 | 不做 |
| 创建、更新、关闭 MR / issue | 改变协作对象状态 | 不做 |
| 推送、建分支 | 改变远端仓库 | 不做 |
| 合并、打标签 | 改变主干与发布状态 | 不做 |

「准备好内容」和「发出去」是两件事：生成评论正文不等于已授权发布。

## 发布前必须确认

发布评论或改变状态的命令，执行前把以下三项说清楚并等用户确认：

1. **发什么**：正文要点，必要时贴出完整内容。
2. **发到哪**：MR 编号、是行内还是讨论回复。
3. **发几条**：单条还是批量发布所有草稿。

批量发布尤其要确认。`draft publish` 会发出该 MR 上**全部**个人草稿，包括之前遗留的。

## 写后回读

退出码 0 不代表写入正确。每次写完回读核对：

```bash
# 核对最新一条评论
glab api "projects/org%2Frepo/merge_requests/123/notes?sort=desc&per_page=1" | jq -r '.[0].body'

# 核对行内位置是否落对
glab api "projects/org%2Frepo/merge_requests/123/discussions?per_page=5" \
  | jq -r '.[] | .notes[0] | select(.position) | "\(.position.new_path):\(.position.new_line)"'
```

回读失败或内容不符，按写入未完成处理，不要说成已发布。

## 可回滚性

| 动作 | 能否撤销 | 撤销方式 |
| --- | --- | --- |
| 一般评论 | 能 | `glab mr note delete <iid> <note-id> --yes` |
| 行内评论 | 能 | 同上 |
| 解决讨论 | 能 | `glab mr note reopen <disc-id> <iid>` |
| 批准 | 能 | `glab mr revoke <iid>` |
| 草稿 | 能 | `glab mr note draft delete <iid> <draft-id> --yes` |
| 推送 | 有条件 | 只能追加提交或强推，强推会改写历史 |
| 合并 | 难 | 需 revert MR |
| 通知 | 不能 | 评论删除后通知已发出 |
| 系统通知 | **不能** | 批准、撤销批准都会留下系统记录，API 删除返回 403 |

**注意参数顺序不一致**，实测确认：

| 子命令 | 实际参数顺序 | 帮助文本写的 |
| --- | --- | --- |
| `note delete` | `<iid> <note-id> --yes` | `<note-id> [<id>]`，与实测相反 |
| `note resolve` | `<disc-id> <iid>` | `[<id>]` 在后，正确 |
| `note reopen` | `<disc-id> <iid>` | 正确 |

`note delete` 的帮助文本会误导，按 `<iid> <note-id>` 写才不会报 `Failed to get merge request <note-id>`。非交互执行还要加 `--yes`。

**系统通知删不掉**，这一点实测确认过：批准后再撤销，MR 上会永久留下「approved」「unapproved」两条系统记录，`DELETE .../notes/<id>` 返回 403。所以**不要在别人的真实 MR 上试批准**，这类痕迹无法清理。

执行前想清楚：这个动作撤销不了的部分是什么。

## 误操作恢复

发现误操作后按顺序处理，不要沉默修补：

1. **立即停止后续写操作。**
2. **撤销可撤销的部分**：删评论、撤销批准、删草稿。
3. **明确告诉用户做了什么、撤销了什么、还剩什么**。
4. **不要用新评论掩盖**：追加一条「更正」评论会在 MR 上留下两条噪音，能删除就直接删除。

## 在别人的 MR 上操作

- 只读评审是默认。要写评论，先确认用户要的是「贴到 MR」还是「给我看」。
- 不要替他人 resolve 讨论，除非用户明确要求。
- 不要在他人的 MR 上改标签、指派人或目标分支。
- 批准他人的 MR 等同于背书，没有授权不做。

## 在自己仓库里测试

需要验证写命令时，建一次性项目或沙箱 MR，用完删除，不要在真实业务 MR 上试。判据：这个操作如果留下痕迹，是否会打扰别人。
