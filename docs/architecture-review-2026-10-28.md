# 第一轮架构审查摘要

日期：2026-10-28。对象：[CStack 研究提案](cstack-proposal-2026-10-28.md)。本文整理首次架构审查的结论，仍属于待讨论建议，不构成已批准规范。

## 最有理由保留的设计

1. 六阶段作为可跳过、可返回的工程地图，判断目标可以区分，不必删除阶段。
2. 证据关联候选、契约、实际观察和环境，相关条件变化后重新判断适用性。
3. 沿用项目 SPEC、CI、分支保护等事实来源，不维护第二份权威状态。
4. 按风险增加检查、限制审查循环，区分合并就绪与发布就绪。

候选方法的职责可以保留，独立 Skill 数量暂缓决定。clarify/specify 共用已确认需求；design/decompose 不强制简单任务交接；diagnose 可以由实现、验证和审查调用；verification-setup 负责项目验证能力，verify 负责本次候选判断。

## 必须补足的四项语义

| 问题 | 已知事实 | 推断与影响 | 未知 | 最小修正与可证伪实验 |
| --- | --- | --- | --- | --- |
| 独立验证 | 提案要求从 AC 独立得出预期，也允许实现者自检并默认最少角色 | 可能无条件增派 Agent，或换角色后仍接受相同错误断言 | 独立执行者相对独立验收依据的增量收益 | 区分预期依据独立与执行者独立；用错误业务断言造成的绿色测试作对照 |
| 候选与实际检查对象 | 已有 candidate、method、environment、observation 字段，但对应关系的核查条件尚未规定 | 报告标注候选 B，实际仍观察构建 A；也可能误拒合法的组合提交检查 | 项目工具能否识别实际产物来源 | 每项证据说明支持什么判断、检查哪个对象及其来源；设置旧服务/新代码和合法组合提交两个对照 |
| 证据适用性 | 提案列出变化类型，要求只核对受影响证据，未规定无法判断时的处理 | 可能错误复用，也可能每次全量重跑 | 通用影响判断的准确率和配置成本 | 有明确依据才复用；不确定时补验或保留 NOT VERIFIED；比较共享配置变化与无关说明修改 |
| 就绪、授权与执行结果 | 提案已经将 Ready 与授权检查分开，但动作对象、副作用和执行前变化未闭合 | 可能把就绪视为执行许可，或将合并许可扩展为自动部署许可 | Runtime 对候选前置条件和动作范围的约束能力 | 三者分别表达；已有授权在范围内持续有效；测试候选变化、合并触发未授权部署、仅入队未完成 |

VERIFY 输出逐 AC 的观察结果与限制，发现问题后交回修复；REVIEW 输出有依据的缺陷、风险和未消除的不确定性，可复用已有检查；SHIP 结合有效证据与项目门禁判断指定交付是否就绪，执行另受授权约束。

风险接受应保留依据和接受者，不能把 FAIL 或 NOT VERIFIED 改写成 PASS。NO-GO 在具有不同后续处理语义前可暂不引入。

## 三个开放决策

| 决策 | 当前推荐 | 改变推荐需要的证据 |
| --- | --- | --- |
| 独立性是否要求独立执行者 | 默认保证验收依据独立；高风险或项目要求时增加独立执行者 | 持续检出关键遗漏，收益足以覆盖成本 |
| 证据复用粒度 | 明确规则下复用，不确定时重验 | 粗粒度重验成为主要成本，且已有可靠影响分析能力 |
| 首版 SHIP 的终点 | 到 Merge Readiness；发布条件按项目识别，暂不执行真实交付 | 判断层显示收益，再通过隔离环境中的授权、竞态和结果确认实验 |

入口命令、目录结构、适配层和仓库迁移晚于上述判断收敛。

## 已开展的最小实验

后续获准运行了 [example-v0](../evals/example-v0/README.md)：两个模型、两种指令条件、六个样例，共 24 次独立任务。最终交付决策与模拟动作均符合预期，尚未证明 CStack 的增量收益。

该实验暴露了验收总标签的范围歧义，以及一处执行自述与保存日志不一致。原始标签分数、证据缺口和限制全部保留。它没有验证真实 GitHub 交付、执行竞态、完整六阶段路由或跨 Runtime 一致性。

## 平台事实的核对范围

首次审查核对了 GitHub 官方文档：必需检查可能针对测试合并提交；合并队列具有组合提交；部分跳过的检查可能满足平台门禁；合并接口支持预期 HEAD 条件，入队不等于完成合并。这些机制说明应复用平台保护，并区分平台可合并与 AC 已验证。

- [Troubleshooting required status checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)
- [Managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)
- [REST API endpoints for pull requests](https://docs.github.com/en/rest/pulls/pulls)

以上为 2026-10-28 的文档核对；本轮未执行平台交付实验。
